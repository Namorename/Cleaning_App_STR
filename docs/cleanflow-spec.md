## 01. Продукт и цели

*Что это за система и какую работу она выполняет*

CleanFlow — SaaS-платформа для операционного управления уборками в краткосрочной аренде (STR). Она соединяет систему бронирования (PMS/channel manager) с бригадой клинеров и техников: брони автоматически превращаются в задания на уборку, задания распределяются по исполнителям, исполнители отчитываются фотографиями и чек-листами через мобильное приложение и WhatsApp, а владелец видит календарь, учёт времени и заявки на ремонт.

### 1.1 Ключевая ценность

Продукт закрывает четыре разрыва, характерные для управляющих компаний STR:

- **Разрыв «бронь → уборка».** Выезд гостя в PMS автоматически создаёт задание на уборку в нужный день с временным окном «выезд → заезд».
- **Разрыв «задание → исполнитель».** Два режима распределения: прямое назначение и «пул» — рассылка предложения нескольким клинерам с принципом «кто первый принял».
- **Разрыв «работа → доказательство».** Пошаговый процесс в приложении клинера: фото до, чек-лист, инвентарь, видео, заметка, фото после — с замером фактического времени.
- **Разрыв «поломка → ремонт».** Клинер прямо во время уборки заводит «Проблему», она попадает в канбан и назначается технику.

### 1.2 Границы системы

| Входит в систему | Не входит (внешние системы) |
| --- | --- |
| Справочник апартаментов, иерархия «объект → юниты» | Каналы продаж (Airbnb, Booking) — приходят через PMS |
| Импорт броней и синхронизация | Ценообразование, динамические цены |
| Генерация, распределение и контроль заданий | Расчёт и выплата зарплат клинерам |
| Учёт рабочего времени по факту (замер в приложении) | Бухгалтерия, инвойсы |
| Заявки на обслуживание (проблемы) | Складской учёт и закупки (есть только «норма» инвентаря) |
| Чек-листы и инвентарные ведомости по объектам | Общение с гостями |
| База знаний для персонала | Замки/умный дом (коды хранятся текстом в названии объекта) |
| Переписка с персоналом в WhatsApp |   |

### 1.3 Масштаб, на который надо проектировать

На обследованном аккаунте: **109 апартаментов** (включая юниты внутри мульти-объектов), **19 сотрудников** (16 клинеров, 3 техника), **~1000+ активных заданий** в выдаче списка, **584 прошедших** задания и 41 проблема. Календарь рисует 109 строк × до 30 дней одновременно. Это ориентир для нагрузочных требований одного тенанта; платформа мультитенантная (в админке есть раздел «Хосты»).

## 02. Роли, аудитории и права

*Четыре роли, три отдельных интерфейса*

Система различает четыре роли (подтверждено политикой конфиденциальности исходного продукта: `Host / Reinigungskraft / Hausmeister / Admin` ). Роль определяет, какой из трёх интерфейсов открывается после входа — маршрут выбирается редиректом с корня.

| Роль | В UI | Интерфейс | Что может |
| --- | --- | --- | --- |
| host — владелец/менеджер | «Inhaber» (владелец) | `/dashboard и весь хост-раздел` | Полный доступ к своему тенанту: объекты, команда, задания, настройки, интеграции, биллинг-данные аккаунта. |
| cleaner — клинер | «Клинер» | `/staff/*` | Видит только назначенные (и предложенные из пула) задания по своим апартаментам; проходит шаги уборки; заводит проблемы; читает базу знаний по своим объектам. |
| technician — техник | «Техник» | `/staff/*` | То же, но ориентирован на проблемы/обслуживание. В обследованном аккаунте техники прикреплены ко всем 109 объектам, клинеры — к 3–12. |
| admin — платформенный | — | `/admin/*` | Кросс-тенантное управление: хосты, клинеры, админы, объявления, аудит, ошибки, экспорты, здоровье системы, метрики, очереди, мета-шаблоны. |

> **Требование к роутингу**
>
> Guard обязан жёстко разводить роли: при обращении хоста к `/staff` , `/admin` , `/welcome` происходит редирект на `/dashboard` без ошибки. Аналогично для остальных ролей. Проверено на живом сервисе — все три маршрута тихо редиректят.

### 2.1 Матрица доступа к данным

Данные изолируются на двух уровнях: **тенант** (аккаунт хоста) и **назначение на апартамент** . Клинер не должен видеть задания, брони, чек-листы, инвентарь и статьи базы знаний по объектам, к которым он не привязан. Реализуется через RLS-политики на уровне БД, а не только фильтрацией в приложении.

## 04. Архитектура и технологический стек

*Что использует оригинал и что рекомендуется*

### 4.1 Стек оригинала (установлено при обследовании)

- **Фронтенд** — Next.js 16.2.4, App Router, React Server Components. Мутации — через Server Actions (публичного REST API в браузере не наблюдается: сеть содержит только RSC-запросы вида `?_rsc=…` ).
- **Стилизация** — Tailwind CSS с кастомными семантическими токенами ( `--status-go` , `--banner` , …), компоненты в стиле shadcn/ui (атрибуты `data-slot` , Radix-примитивы для диалогов и меню).
- **Шрифт** — Geist (self-hosted через `next/font` ), базовый размер 16px, радиус скругления `0.5rem` .
- **Тосты** — Sonner.
- **Бэкенд / БД** — Supabase (PostgreSQL + Auth + Storage), EU-регион. Cookie сессии: `sb-<project-ref>-auth-token` .
- **Файлы** — Cloudflare R2 — хранение фото и видео отчётов.
- **E-mail** — Resend — транзакционные письма.
- **Мессенджер** — Meta WhatsApp Business API.
- **Мониторинг** — Sentry (SDK для Next.js, туннель `/monitoring` , релиз = git-хэш).
- **Локаль** — Хранится в cookie `cf_lang` ; `<html lang>` переключается. Часть состояния UI — в localStorage (пример: `cleanflow.kalender.zugeklappteGruppen` ).
- **Аналитика** — Отсутствует намеренно (нет GA/Pixel — заявлено в политике).

### 4.2 Рекомендации по реализации аналога

Стек можно повторить один в один — он адекватен задаче и даёт быстрый старт. Существенные архитектурные требования, которые нужно заложить независимо от выбора технологий:

- **Мультитенантность на уровне БД.** Каждая таблица содержит `host_id` (тенант); RLS-политики Postgres + отдельная политика «клинер видит только назначенные объекты».
- **Идемпотентный импорт из PMS.** Внешние идентификаторы ( `external_property_id` , `external_unit_id` , `external_reservation_id` ) — уникальные ключи; повторная синхронизация не должна дублировать объекты и задания.
- **Очереди фоновых задач.** Периодическая синхронизация PMS (для Guesty — раз в 15 минут), обработка вебхуков, рассылка пула, ежедневный «Обзор заданий» в WhatsApp, ретраи. В оригинале есть отдельный админ-экран `/admin/queues` — очереди являются первоклассной сущностью.
- **Хранилище медиа отдельно от БД.** Загрузка по предподписанным URL напрямую в объектное хранилище; в БД — только метаданные (тип, размер, шаг процесса, порядок).
- **Аудит-лог всех мутаций** с ретенцией 24 месяца (см. §14).
- **Мобильный клиент** — приложение для клинеров позиционируется как iOS/Android. Практично реализовать веб-версию `/staff` как PWA и обернуть её в нативную оболочку ради камеры, пуш-уведомлений и офлайна.

### 4.3 Требования к офлайну (критично)

Клинер работает в квартире, где связь может отсутствовать. Приложение исполнителя должно: кэшировать список заданий на сегодня/завтра, позволять пройти шаги и снять фото офлайн, ставить выгрузку медиа в очередь и досылать при появлении сети, а также корректно разрешать конфликт, если задание за это время было переназначено.

### 5.3 Типографика и сетка

- **Гарнитура** — Geist (единая для интерфейса и заголовков), запасная — системный sans-serif стек
- **Базовый кегль** — 16px / 1.5
- **Микротипографика** — Служебные подписи: 9–11px, `uppercase` , `letter-spacing ≈ .12em` , цвет `--muted-foreground`
- **Радиус** — `--radius: 0.5rem` ; мелкие бейджи — 3px
- **Ширина меню** — ≈ 288px, фиксированная, всегда развёрнута на десктопе
- **Плотность** — Строка таблицы ≈ 44–56px; карточка задания в списке — 2 строки текста

### 5.4 Обязательные паттерны интерфейса

- **Баннер страницы.** Каждый раздел открывается тёмным блоком `--banner` : круглая иконка, заголовок, подзаголовок-описание, справа — счётчик-«пилюля» (напр. «109 апартаменты») и главная кнопка действия.
- **Пилюли-переключатели** вместо табов: закруглённая группа с активным сегментом (вкладки заданий, «Список / Канбан», «По сотрудникам / По апартаментам»).
- **Модальные формы** с закреплёнными футером и заголовком, прокручиваемым телом; деструктивная кнопка («Удалить») — слева, «Отмена/Сохранить» — справа.
- **Правая выдвижная панель (drawer)** для просмотра результата уборки — в отличие от модалки редактирования.
- **Мастера** с шаговым индикатором «1 — 2 — 3» для создания задания и приглашения сотрудника; последний шаг содержит «Сводку».
- **Пустые состояния** с иконкой, заголовком и объясняющим текстом, который отсылает к настройке (напр. пустая вкладка «Не назначено» объясняет разницу режимов «Вручную» и «Автоматически»).
- **Тосты** в правом нижнем углу для подтверждения автосохранения.

### 7.2 Календарь

#### Хронология объектов — `/calendar`

Ключевой рабочий экран. Матрица: строки — апартаменты, колонки — дни. Баннер: «Хронология объектов — бронирования, уборки и дни смены гостей в одном месте», счётчик «109 апартаменты», кнопка «+ Задание».

#### Панель управления

- **«Сегодня»** — возврат к текущей дате.
- **Стрелки ‹ ›** и подпись диапазона: «4 сент. → 10 сент. 2026 г.».
- **«Фильтр»** (поповер): «КЛИНЕР» — Все / Не назначено / список сотрудников по алфавиту; «СТАТУС» — Все / Открыто / В работе / Выполнено.
- **«Синхронизировать бронирования»** — ручной запуск импорта из PMS.
- **«Сортировать»** — режим перетаскивания: панель «Режим сортировки / Перетащите апартаменты в нужном порядке», нумерованный список всех объектов с ручками drag, кнопки «Сбросить» и «Готово». Порядок сохраняется (тост «Порядок сохранён»).
- **Слайдер глубины:** 1 · 3 · 7 · 15 · 30 дней; подпись «7 Дни».

#### Строки и группы

Мульти-объекты образуют группу: строка-родитель с подписью «Единиц: N», под ней — строки юнитов. Группы сворачиваются, состояние хранится локально ( `cleanflow.kalender.zugeklappteGruppen` ).

#### Содержимое ячейки

- **Верхний слой** — Полоса бронирования: тёмный градиент, бейдж числа ночей («12N»), аватар-инициалы гостя, имя гостя. Полоса тянется через дни проживания.
- **Нижний слой** — Чип уборки: цветная точка статуса, аватар и имя исполнителя (или «Никто» красным), временное окно «10:00–15:00».
- **Доп. чип** — Задача обслуживания — имя техника и своё окно, напр. «Danylo 10:00–11:00».
- **Колонка «сегодня»** — Подсвечена тёплым фоном `--accent-warm` с рамкой.

#### Действия по клику

- **По полосе брони** — модалка: название объекта, «Гость: {имя} · 👥 {N}», «Заезд {дата} → Выезд {дата}», тумблер *«Повторяющаяся промежуточная уборка»* с пояснением «Задания создаются автоматически в течение брони. Дни заезда и выезда остаются свободными». Кнопки «Закрыть» / «Сохранить».
- **По чипу незавершённой уборки** — модалка «Изменить задание» (см. 7.3).
- **По чипу выполненной уборки** — правый drawer «Уборка завершена» (см. 7.3).

> **Производительность**
>
> 109 строк × 30 колонок × до 3 элементов в ячейке. Нужна виртуализация строк и предзагрузка соседних диапазонов дат; горизонтальный скролл — внутри контейнера таблицы, шапка колонок и колонка «Апартамент» закреплены.

### 7.3 Задания

#### Список заданий — `/tasks`

Баннер: «Задания на уборку и проекты — планирование, назначение, контроль», счётчик активных, кнопка «+ Задание».

**Три вкладки:** «Не назначено» · «Назначенные {N}» · «Все активные».

**Панель фильтров:** поле «Поиск апартамента…» и поповер «Фильтр» с тремя селектами: СТАТУС (Все / Открытые / В работе / Выполнено / Отменено / Ожидает назначения), КЛИНЕР, АПАРТАМЕНТ.

**Группировка списка** по времени, с числом в заголовке: СЕГОДНЯ · ЗАВТРА · НА ЭТОЙ НЕДЕЛЕ · СЛЕДУЮЩАЯ НЕДЕЛЯ · ПОЗЖЕ · ПРОШЕДШИЕ. Группы сворачиваются.

**Строка задания:** иконка типа · название апартамента · бейдж SDT (если смена в тот же день) · дата · окно времени · число гостей · тип задания · чип исполнителя · бейдж статуса ( выполнено открытые в работе ).

**Пустое состояние вкладки «Не назначено»:** «Все задания назначены» + пояснение про режимы «Вручную»/«Автоматически» со ссылкой на настройки.

#### Модальное окно «Изменить задание»

Подзаголовок: «Обновить уборку или особое задание».

- **ТИП** — Уборка / Обслуживание / Промежуточная уборка
- **АПАРТАМЕНТ *** — Селект по всем объектам
- **СТАТУС** — Открыто / В работе / Выполнено / Отменено
- **НАЗВАНИЕ** — Текст ≤ 30 символов, счётчик, плейсхолдер «например, весенняя генеральная уборка»
- **ДАТА *** — Датапикер
- **ГОСТИ** — Только чтение. Подпись меняется по ситуации: «Заезжающий гость — данные приходят из системы бронирования и обновляются при каждом изменении брони» либо «Следующей брони нет — число гостей неизвестно (система бронирования не передаёт вместимость)»
- **С / ДО** — Время начала и конца окна
- **ОСОБЫЕ ПОЖЕЛАНИЯ** — Сетка чипов-переключателей (10 системных + пользовательские), необязательно
- **НАЗНАЧЕНИЕ** — Радио из трёх вариантов, см. ниже
- **ЗАМЕТКА** — Многострочное поле, плейсхолдер «Указания для клинера…»

Варианты назначения:

- **Пул — приглашены все.** «Запрос получит 1 клинер, задание достанется принявшему первым.»
- **Назначить напрямую.** «Выбрать конкретного клинера» + селект «Выберите клинера…».
- **Вручную (назначить позже).** «Задание останется без исполнителя — вы назначите клинера сами позже (вкладка "Не назначено")».

Футер: «🗑 Удалить» слева, «Отмена» и «Сохранить» справа.

#### Мастер «Новое задание» — 3 шага

- **Шаг 1 — Что и где** — ТИП, АПАРТАМЕНТ *, НАЗВАНИЕ
- **Шаг 2 — Когда** — ДАТА *, ГОСТИ (подставляются), С / ДО (по умолчанию окно объекта)
- **Шаг 3 — Кто и детали** — Особые пожелания, Назначение, Заметка, блок «СВОДКА»

Валидации шага 2 (обе наблюдались вживую):

- ошибка «На этот день уже есть задание такого типа. Выберите другой день.» — поле даты подсвечивается красным, «Далее» блокируется.
- предупреждение «В этот день выезжает {гость}. Система бронирования сама создаёт здесь уборку — если ваше задание стоит на этот день, свою она создать уже не сможет.»

Блок «СВОДКА» на шаге 3 повторяет: Апартамент, Тип, Дата, Время, Гости, Назначение («Напрямую (клинер ещё не выбран)»). Кнопка «Создать задание».

#### Drawer «Уборка завершена»

Открывается по выполненному заданию. Состав:

- Заголовок со статусом и датой прописью.
- Карточка фактов: АПАРТАМЕНТ · КЛИНЕР · ДЛИТЕЛЬНОСТЬ · ЗАВЕРШЕНО (дата и время) · строка «Выполнил(а): {имя}» с аватаром.
- Эвристика качества Если длительность < 5 минут — жёлтый блок «очень коротко / Меньше пяти минут. Обычно это признак того, что документирование сделали уже после работы».
- Блок «КОРРЕКТИРОВКА ВРЕМЕНИ» с действием «Исправить»: «Если замеренное время неверно, вы можете исправить его здесь. Замер сохраняется.»
- «ВЫПОЛНЕННЫЕ ШАГИ» — список пройденных шагов процесса; при их отсутствии: «Шаги не зафиксированы (клинер пропустил процесс в приложении)».
- «СООБЩЁННЫЕ ПРОБЛЕМЫ» — список или «Проблем нет / Уборка завершена без сообщений о проблемах».

### 7.4 Рабочее время

#### Отчёт по учтённому времени — `/reports/hours?from&to&view`

Баннер с навигацией по месяцам (стрелки + подпись «сентябрь 2026 г.»). Состояние полностью закодировано в URL — отчёт шарится ссылкой.

**Панель:** датапикеры «С» и «По»; пресеты «Текущий месяц», «Последние 7 дней», «Последние 30 дней»; переключатель разреза «По сотрудникам / По апартаментам»; фильтры «Все апартаменты» и «Все клинеры». Под панелью — примечание о неполноте периода: «Сравнение с прошлым месяцем до {дата} — текущий месяц ещё не закончился».

**Виджет «Часы по клинерам / по апартаментам»** — горизонтальные полосы, отсортированные по убыванию, подпись «7 в работе» / «Апартаментов: 22».

**Виджет «Загрузка по дням недели»** — столбцы Пн–Вс; сверху число уборок, снизу часы; подпись «Выходные 0 %».

**Таблица** с колонками: КЛИНЕР (или АПАРТАМЕНТ) · УБОРКИ · УЧТЁННОЕ ВРЕМЯ · МЕДИАНА · ПРИМЕЧАНИЯ. Особенности:

- Бейдж новое у сотрудников, появившихся в периоде.
- Подстрока «из них {X} ч. под вопросом» — доля времени, попавшая под эвристику подозрительно коротких замеров.
- Колонка ПРИМЕЧАНИЯ содержит счётчики аномалий: «3 меньше 5 мин.», «1 без времени».
- Итоговая строка: «Всего {N} уборки / {X} ч.».
- Блок «БЕЗ УБОРОК В ЭТОМ МЕСЯЦЕ»: перечисляет сотрудников, у которых только проблемы — «Danylo — только проблемы (22)», плюс строка «Проблем без клинера: 3».

> **Чего не хватает**
>
> Экспорта нет вообще. В новой версии обязательны выгрузка CSV/XLSX по текущему фильтру и, желательно, расчёт стоимости (ставка сотрудника × время).

### 7.5 Апартаменты

#### Реестр — `/apartments`

**Панель:** поиск «Поиск среди…», счётчик «109 Apartments», кнопки «Синхронизировать автоматически» (импорт из PMS) и «+ Добавить вручную».

**Таблица:** чекбокс · Название (с иконкой типа и шевроном разворота у родительских объектов) · Адрес · Статус ( Активен ) · Клинеры (стек аватаров с «+N») · действия (карандаш → карточка, «…» → меню «Редактировать / В архив / Удалить»).

**Массовые действия** при выделении: панель «выбрано: N», «Снять выделение», кнопки «Сделать активными», «Перевести в обслуживание», «В архив», «Удалить».

**Модалка «Новый апартамент»:** Название *, Адрес («Улица, индекс, город»), Заметки («Внутренние заметки, коды доступа, …»). Кнопки «Отмена» / «Создать».

> **Дефект оригинала**
>
> Поиск не работает с несколькими словами: «Mecislavova» находит, «Mecislavova Modern» — «Ничего не найдено», хотя такая подстрока есть в названии. Требование: полнотекстовый поиск по названию и адресу с разбиением запроса на токены (AND по всем токенам), регистронезависимо, с поддержкой диакритики (Mečislavova ↔ Mecislavova).

#### Карточка апартамента — 6 вкладок — `/apartments/:id`

Шапка: ссылка «← Назад к списку апартаментов», тёмный баннер с названием, адресом и бейджем статуса. Вкладки (горизонтально прокручиваемые): **Информация · Клинеры {N} · Бронирования {N} · Чек-лист · Инвентарь · Обслуживание {N}** . Активная вкладка отражается в query-параметре `?tab=` .

#### Вкладка «Информация»

Три плитки-показателя: ЗАДАНИЯ НА УБОРКУ · ВНЕШНИЙ ID · СТАТУС. Далее секции:

- **ОСНОВНЫЕ ДАННЫЕ** — Название, Статус, Адрес, Родительский апартамент («Без родителя»; подпись: «Делает этот апартамент суб-объектом другого (например, комната в доме)»), Клинер по умолчанию (подпись: «Основной клинер = приоритет 1. Состав и порядок настраиваются в списке апартаментов или на вкладке "Клинеры"»).
- **Окно уборки** — «Стандартные выезд и заезд этого апартамента. Задают временное окно всех заданий: начало = выезд, конец = заезд. Один раз заполняется из PMS — здесь можно изменить в любой момент». Поля «ВЫЕЗД · НАЧАЛО УБОРКИ» и «ЗАЕЗД · КОНЕЦ УБОРКИ», отдельная кнопка «Сохранить окно».
- **Внешние ID (PMS)** — «Для связи с Guesty, Smoobu, Beds24, Apaleo. Обычно задаются автоматически — меняйте вручную только при необходимости»: EXTERNAL PROPERTY ID, EXTERNAL UNIT ID.
- **Внутренние заметки (только для вас)** .
- **Заметки для клинера** — «Показывается клинеру во вкладке "Помощь" и в задании. Подходит для сведений об объекте, которых нет в общей базе».

#### Вкладка «Клинеры»

«Клинеры и приоритет — определите, какие клинеры убирают этот апартамент и в каком порядке они получают задание». Переключатель **«Все одновременно» / «По приоритету»** . Для режима «Все одновременно» подпись: «Все назначенные клинеры получают задание одновременно — оно достаётся принявшему первым». Ниже — упорядоченный список назначенных и секция «ДОБАВИТЬ КЛИНЕРА» со списком остальных сотрудников.

#### Вкладка «Бронирования»

Две секции: «ТЕКУЩИЕ И ПРЕДСТОЯЩИЕ · N» и «ПРОШЕДШИЕ · N». Строка: имя гостя, «{дата} → {дата} · {N} н. · гостей: {N}», бейдж CONFIRMED / CANCELLED .

#### Вкладка «Чек-лист»

«Модули уборки — модулей пока нет, создайте первый. Клинеры видят этот чек-лист в процессе уборки». Действия: «📋 Взять из апартамента» и «+ Новый модуль» (инлайн-поле «например, ванная, кухня, спальня…» + «Создать/Отмена»). Пустое состояние: «Чек-листа пока нет — модули структурируют чек-лист (например, ванная / кухня / спальня). Пункты живут внутри модуля».

Модалка копирования: «Взять Чек-лист из другого апартамента — копирует модули и пункты из другого апартамента сюда. После копирования они независимы — дальнейшие изменения друг на друга не влияют». Показывает текущее состояние («Чек-лист этого апартамента сейчас: пусто») и селект «Источник».

#### Вкладка «Инвентарь»

«Разделы инвентаря — разделов пока нет, создайте первый (например, ванная, кухня, спальня)». Тумблер «Дополнительно», кнопки «Взять из апартамента» и «+ Новый раздел». Пустое состояние: «Разделы делят инвентарь по комнатам. Позиции (с нормой) живут внутри раздела».

#### Вкладка «Обслуживание»

Проблемы по этому объекту, сгруппированные по статусу («ЗАКРЫТА · 2»). Карточка: иконка, заголовок, бейдж приоритета ( СРЕДНИЙ ), описание, дата и время.

**Вкладка «Апартаменты»:** «НАЗНАЧЕННЫЕ АПАРТАМЕНТЫ (12/109)», поиск, «Выбрать все», список с чекбоксами, кнопка «Сохранить назначение».

#### Мастер «Пригласить сотрудника» — 3 шага

- **1 — Контактные данные** — «Эти данные сотрудник увидит потом на экране входа». Имя *, Фамилия, Эл. почта («Нужна клинеру для входа в приложение»), Телефон (для WhatsApp). Предупреждение: без телефона человек не получит WhatsApp-уведомления и увидит новые задания только при следующем входе в приложение.
- **2 — Назначение** — Роль и привязка к апартаментам
- **3 — Проверка данных** — Сводка и отправка приглашения

### 7.7 Входящие (WhatsApp)

#### Переписка с командой — `/inbox`

Баннер: «Переписка в WhatsApp с вашей командой. Реальное время и статус 24-часового окна».

Двухпанельный макет. Слева — «ПЕРЕПИСКИ / активных: N», кнопка «✎ Новая», поиск «Имя, номер или сообщение», фильтр-пилюля «Все · N», список чатов. Пустое состояние: «Сообщений пока нет — как только клинеры ответят на шаблоны WhatsApp, чаты появятся здесь». Справа — окно чата; при отсутствии выбора: «Переписка не выбрана / Выберите слева существующий чат или начните новую переписку» + кнопка «Новая переписка».

**Модалка «Новая переписка»:** «Выберите сотрудника или введите номер». Секция выбора сотрудника с поиском (пустое состояние: «Нет ни одного сотрудника с номером телефона»), разделитель «ИЛИ», секция «Ввести номер напрямую» (селектор страны + номер + «Далее»). Пояснение: «Подходит и для людей вне вашей команды. Если окно 24 ч закрыто, мы автоматически отправим шаблон "Открыть" — ваше сообщение уйдёт, как только человек по нему нажмёт».

> **Требование**
>
> Реализовать индикатор оставшегося времени 24-часового окна на каждом чате и автоматическую подстановку утверждённого Meta-шаблона при закрытом окне. Реальное время — через подписку (websocket/realtime), не поллинг.

### 7.8 Проблемы

#### Заявки на обслуживание — `/problems`

Баннер: «Заявки на обслуживание и сообщения о проблемах от ваших клинеров», счётчик «открытых: N», кнопка «+ Новая проблема».

**Два представления** (переключатель «Список / Канбан») и поиск «Поиск среди 41 проблем».

**Канбан** — пять колонок со счётчиками: ОТКРЫТА · НАЗНАЧЕНА · В РАБОТЕ · РЕШЕНА · ОТМЕНЕНА. Карточка: точка приоритета, заголовок, описание, апартамент (или «Без апартамента»), возраст заявки («8m», «5h», «11h»), чип исполнителя.

**Список** — таблица: чекбокс · Заголовок (с описанием второй строкой) · Апартамент · Приоритет · Статус · Сообщено («9 мин. назад / от {автор}») · инлайн-селекты назначения и статуса.

#### Модалка «Редактировать проблему»

Подзаголовок: «{апартамент} · сообщил(а) {автор}». Поля: Заголовок; Описание (счётчик 0/4000, плейсхолдер «Что случилось? Детали для клинера…»); Приоритет (Низкий / Обычный / Высокий); Назначение; Статус (Открыта / Назначена / В работе / Решена / Прервана); блок **Время (необязательно)** — ДАТА, НАЧАЛО, ОКОНЧАНИЕ с пометкой «С датой, временем и назначением проблема появится в календаре»; **Фото и видео** с счётчиком вложений; **Документация клинера** — пошаговый отчёт исполнителя («Документации по шагам пока нет»).

Футер: подпись «Назначение, статус и фото сохраняются сразу», кнопки «Закрыть» / «Сохранить». *Важно:* часть полей сохраняется немедленно, часть — по кнопке. Это надо либо повторить, либо унифицировать (см. §15).

#### Модалка «Сообщить о новой проблеме»

«Создайте заявку на обслуживание — при желании для апартамента и сразу с исполнителем». Поля: Апартамент (необязательно, «Без апартамента»); Заголовок * («например, течёт кран»); Описание («Детали, которые помогут технику — где именно, как давно, …»); Фото и видео («Фото до 20 МБ, видео до 150 МБ»); Приоритет (чипы); Назначить (необязательно) с пояснением «При назначении человек получит уведомление в WhatsApp»; Время с пометкой «Без апартамента в календаре не отображается — он построен по апартаментам».

### 7.9 База знаний

#### Статьи для персонала — `/knowledge`

Баннер: «Ведите статьи, которые помогают вашим клинерам в работе — общие или по конкретному апартаменту».

**Левая колонка** — дерево: поиск, фильтр «Все / Опубликованные / Черновики», раздел «ОБЩИЕ» со счётчиком и кнопкой «+», затем по одному узлу на каждый апартамент (тоже со счётчиком и «+»). Ссылка «Обзор» возвращает к сводке.

**Правая колонка — сводка:** «База знаний — обзор / {N} статей · {N} Apartments со статьями · {N} без собственных статей», далее сетка карточек по областям (ОБЩИЕ = «ВСЕ АПАРТАМЕНТЫ», остальные = «ДЛЯ КОНКРЕТНОГО АПАРТАМЕНТА») с числом статей и кнопкой «+ Новая».

**Редактор статьи:** панель — переключатель «Черновик», кнопка «✨ Помощь ИИ», «🗑 Удалить», индикатор автосохранения «Сохранено». Поля: Заголовок; Категория («например, техника, ванная, авария»); **Видимость** — «Общая · видна для всех апартаментов» либо конкретный объект, с пояснением «Общая = статью видят все клинеры. Для конкретного апартамента = её видят во вкладке "Помощь" только те клинеры, которые к нему назначены»; **Содержание** — WYSIWYG с кнопками H1 H2 H3, полужирный, курсив, маркированный и нумерованный списки, ссылка, подпись «В приложении отображается ровно так, как вы напишете здесь»; **Изображения** — «JPG, PNG или WebP · макс. 8 МБ на изображение. Первое изображение показывается миниатюрой во вкладке "Помощь" у клинера».

**Модалка «Черновик статьи от ИИ»:** «Опишите тему — ИИ напишет черновик за вас». Поле «О чём должна быть статья?» с плейсхолдером «например, как мыть индукционную плиту, не поцарапав её?»; блок «ПРИМЕРЫ» с готовыми подсказками («Как вставить сменный аккумулятор в пылесос Dyson», «Как убрать следы от воды с гранитной столешницы», «Как подготовить приветственный напиток к заезду: чашка, чай, маленькая конфета», «Мытьё окон губкой и сгоном (без разводов)»); предупреждение «Существующее содержание статьи будет заменено — сохраните его сначала, если хотите оставить»; кнопки «Отмена» / «Создать черновик».

> **Дефект оригинала**
>
> Кнопка «+ Новая» создаёт пустую статью немедленно, без подтверждения и без возможности отменить создание — в базе остаётся мусорный черновик «Новая статья». Требование: создавать запись только при первом сохранении содержимого либо давать явное «Отменить создание».

Хаб `/settings` — сетка карточек с иконкой, заголовком и описанием. В оригинале слаги разделов были на языке разработки; **у нас — английские**: `account` , `cleaning-workflow` , `problem-workflow` , `special-requests` , `integrations` (плюс наш собственный `supplies` , см. §Д1).

### 8.1 Аккаунт

#### Профиль, язык и пароль — `?section=account`

- **Фото профиля** — «JPG, PNG или WebP · макс. 5 МБ · рекомендуется квадратное», кнопка «Загрузить».
- **Эл. почта** — только чтение: «Нужно изменить адрес? Напишите нам — это делается только через поддержку».
- **Имя · Язык · Город · Телефон** .
- **Назначение заданий** — «Определяет, как новые задания на уборку распределяются в вашей команде». Два режима:
  - *Автоматически:* «Если к апартаменту назначен ровно один клинер, задание достаётся ему напрямую. Если несколько — все получают предложение из пула в WhatsApp, и задание достаётся согласившемуся первым».
  - *Вручную:* «Новые задания остаются без исполнителя, пока вы сами не выберете клинера. Они видны в разделе заданий во вкладке "Не назначено"».
- **Задержка перед предложением из пула** — «Предложения из пула (принять/отказаться) уходят клинерам — в WhatsApp и в приложение — только за столько дней до выезда. При 0 дней ("Сразу") они отправляются сразу при поступлении брони. Напрямую назначенные клинеры уведомляются всегда немедленно». Пресеты: Сразу · 1 неделя · 2 недели · 4 недели · Своё значение (в днях).
- **Безопасность** — смена пароля: ТЕКУЩИЙ ПАРОЛЬ («Для подтверждения»), НОВЫЙ ПАРОЛЬ («Мин. 8 символов»), ПОДТВЕРДИТЕ НОВЫЙ ПАРОЛЬ.

### 8.2 Процесс уборки

#### Конструктор шагов — `?section=workflow`

Два глобальных тумблера:

- **Разрешить клинерам загрузку из галереи** — «Выкл.: фото и видео можно снимать только камерой прямо на месте. Вкл.: клинеры могут дополнительно загружать готовые фото и видео из галереи. Действует для заданий на уборку и устранения проблем».
- **Разрешить параллельный старт** — «Вкл.: клинеры могут вести несколько уборок одновременно — для поэтажной уборки, когда один человек работает во всех номерах сразу. Выкл.: учёт времени рассчитан на одну уборку за раз».

**«Как проходит каждая уборка»** — «Ваши клинеры видят эти шаги по порядку в приложении. Обязательный шаг или нет, сколько фото разрешено — всё настраивается прямо в шаге». Каждый шаг: номер, иконка типа, название, стрелки ↑↓ для перестановки, корзина для удаления, а под ним — настройки: переключатель «Обязательный / Необязательный», счётчики «Макс. N фото», «Макс. N видео», «Макс. длительность N мин.», «Мин. N фото».

**Каталог шагов «ДОБАВИТЬ ШАГ»:** Фото до · Чек-лист · Инвентарь · Особые пожелания · Фото после · Видео · Заметка.

Конфигурация обследованного аккаунта: 1) Фото до (необяз., макс. 1 фото) → 2) Чек-лист (обязательный) → 3) Видео-документация (необяз., макс. 1 видео, до 1 мин.) → 4) Заметка (необяз.). У шага «Заметка» подпись: «Клинер отмечает заметку к заданию в приложении строка за строкой. Саму заметку вы задаёте для каждого задания отдельно».

Футер: «Отменить изменения» / «Сохранить».

### 8.3 Процесс устранения проблем

#### Шаги для проблем — `?section=problem-workflow`

Тумблер **«Письмо при новой проблеме»** — «Если клинер сообщает о проблеме во время уборки, вы получаете письмо с апартаментом, деталями и фото».

Конструктор аналогичен, каталог короче: **Фото до · Заметка · Фото после · Видео** . Конфигурация оригинала: 1) Фото проблемы (обязательный, мин. 1 / макс. 4 фото) → 2) «Что было сделано?» (обязательный, заметка) → 3) Фото после (обязательный, мин. 1 / макс. 4 фото).

## 09. Приложение клинера

*Реконструкция по описаниям в хост-интерфейсе*

> **ВНИМАНИЕ — Статус раздела**
>
> Интерфейс исполнителя недоступен из аккаунта хоста (роутер редиректит `/staff` → `/dashboard` ). Раздел собран из маршрутов, текстов настроек и подсказок в интерфейсе владельца. Перед разработкой требуется контрольный проход с реальной учётной записью клинера.

### 9.1 Экраны

| Маршрут | Содержание |
| --- | --- |
| `/staff` | Главная: задания на сегодня, входящие предложения из пула |
| `/staff/tasks` | Список заданий: принятые, предложенные, выполненные |
| `/staff/tasks/:id` | Прохождение процесса уборки шаг за шагом |
| `/staff/calendar` | Личный график по дням |
| `/staff/problems · :id` | Список проблем и прохождение процесса устранения |
| `/staff/help` | «Помощь»: статьи базы знаний (общие + по назначенным объектам) и «Заметки для клинера» из карточки апартамента |

### 9.2 Сценарий уборки

- **1. Предложение** — Пуш/WhatsApp с заданием. Кнопки «Принять» / «Отказаться». Первый принявший забирает задание.
- **2. Старт** — Нажатие «Начать» фиксирует `started_at` . При выключенном «параллельном старте» одновременно может быть активна только одна уборка.
- **3. Шаги** — Последовательное прохождение настроенных шагов: фото до, чек-лист по модулям, инвентарь по разделам, особые пожелания, видео, заметка (отмечается построчно), фото после.
- **4. Проблема** — В любой момент — «Сообщить о проблеме»: фото, описание, приоритет. Владельцу уходит письмо (если включено).
- **5. Завершение** — Фиксируется `finished_at` ; считается длительность; при < 5 минут задание помечается «под вопросом» в отчётах.

### 9.3 Требования к приложению исполнителя

- Полная локализация на все поддерживаемые языки (у сотрудника свой язык, независимый от языка владельца).
- Съёмка камерой обязательна, если владелец не разрешил галерею. Метаданные снимка (время съёмки) сохранять для контроля.
- Крупные тач-цели, работа одной рукой, читаемость при ярком свете.
- Офлайн-режим и очередь выгрузки (см. §4.3).
- Показ окна времени, числа гостей, особых пожеланий и заметки в карточке задания.

## 11. Интеграции с PMS

*Механика импорта и синхронизации*

### 11.1 Что импортируется

- **Объекты и юниты** → `apartment` с `external_property_id` / `external_unit_id` . Мульти-юнитовые объекты приходят как родитель + дети.
- **Время выезда и заезда** → однократно заполняет «Окно уборки» объекта. Далее значение принадлежит CleanFlow и не перезаписывается («Один раз заполняется из PMS — здесь можно изменить в любой момент»).
- **Брони** → `reservation` : гость, число гостей, даты, статус. Вместимость может не приходить.

### 11.2 Режимы синхронизации

| Механизм | Провайдеры | Поведение |
| --- | --- | --- |
| Периодический опрос | Guesty (каждые 15 мин.), Smoobu | Фоновая задача в очереди; окно синхронизации ≥ горизонта планирования |
| Вебхуки | Smoobu, Beds24 | Мгновенное обновление при изменении брони; обязательна проверка подписи и идемпотентность по `external_id` |
| Ручной запуск | Все | Кнопки «Синхронизировать бронирования» (календарь) и «Синхронизировать автоматически» (апартаменты) |

### 11.3 Правила разрешения конфликтов

Это самая тонкая часть логики; она прямо видна в интерфейсе оригинала.

1. Задание, созданное автоматически, следует за бронью: изменение дат в PMS переносит задание, изменение числа гостей обновляет поле «Гости».
2. Если владелец **вручную** изменил дату или время задания, ручное значение приоритетнее. Расхождение фиксируется флагом `pms_conflict` и выводится на дашборде: «Дата или время были заданы вручную, а система бронирования теперь сообщает другое значение. Ваше значение остаётся — проверьте, актуально ли оно».
3. Если на день выезда уже есть **ручное** задание того же типа, автоматическое не создаётся. Мастер создания предупреждает об этом заранее.
4. Отмена брони не удаляет уже выполненное задание; бронь остаётся в истории объекта со статусом CANCELLED .

> **Требование к доработке**
>
> Кнопка «Проверить задания» в оригинале ведёт на общий список `/tasks` без фильтра — найти конфликтующее задание невозможно. Нужен отдельный фильтр/вкладка «Расхождения с PMS» и пометка конфликта прямо на строке задания с показом обоих значений (ваше / из PMS) и действием «Принять значение PMS».

## 12. WhatsApp и уведомления

*Основной канал связи с исполнителями*

WhatsApp — не дополнение, а несущая конструкция продукта: через него уходят предложения из пула, назначения, ежедневный обзор заданий и переписка. Обязателен Meta WhatsApp Business API с утверждёнными шаблонами.

### 12.1 Сценарии сообщений

| Событие | Кому | Канал | Содержание |
| --- | --- | --- | --- |
| Предложение из пула | Всем клинерам объекта | WhatsApp + push | Объект, дата, окно, число гостей, кнопки «Принять» / «Отказаться». Уходит за `pool_offer_lead_days` до выезда |
| Прямое назначение | Конкретному клинеру | WhatsApp + push | Отправляется **всегда немедленно** , задержка пула не применяется |
| Обзор заданий | Клинерам с включённой опцией | Только WhatsApp | Все принятые задания на ближайшие дни: дата, время, апартамент, заметки, особые пожелания |
| Назначение проблемы | Технику | WhatsApp | «При назначении человек получит уведомление в WhatsApp» |
| Новая проблема | Владельцу | E-mail | Апартамент, детали, фото |
| Приглашение сотрудника | Новому сотруднику | E-mail (+ повторная отправка) | Ссылка на вход в приложение |

### 12.2 Правило 24-часового окна

Свободные сообщения можно слать только в течение 24 часов после последнего ответа человека. Требования:

- Хранить `window_expires_at` на каждом диалоге и показывать оставшееся время в интерфейсе «Входящих».
- При закрытом окне автоматически отправлять утверждённый шаблон «Открыть»; исходящее сообщение ставится в очередь и уходит, как только человек нажмёт кнопку в шаблоне.
- Вести реестр шаблонов и их статусов модерации (админ-раздел `/admin/meta-templates` ).
- Отдельно обрабатывать сотрудников без телефона — интерфейс обязан помечать их бейджем «без WhatsApp» и объяснять последствия.

## 13. Ключевые алгоритмы

*Формализация бизнес-правил*

### 13.1 Генерация задания из брони

```
при импорте/изменении брони R для апартамента A:
  если R.status = cancelled → снять незавершённые авто-задания, историю сохранить
  D := R.check_out                       // день выезда
  если существует ручное задание типа cleaning на A в день D:
      → авто-задание не создаём, помечаем reservation.skipped_reason
  иначе:
      создать task{ type: cleaning, apartment: A, date: D,
                    time_from: A.window_start, time_to: A.window_end,
                    guests: следующая бронь после D → guests_count,
                    reservation_id: R }
  is_same_day_turnover := существует бронь R2 на A c R2.check_in = D
  если R.recurring_midstay_cleaning:
      для каждого дня d в (check_in, check_out) по правилу периодичности:
          создать task{ type: midstay, date: d }   // заезд и выезд исключены
```

Обратите внимание: число гостей в задании — это **заезжающий** гость (следующая бронь), а не выезжающий: уборка готовит квартиру под следующее заселение.

### 13.2 Распределение исполнителя

```
mode := task.assignment_mode ?? host.default_assignment_mode

manual_later → assignee = NULL, статус awaiting_assignment,
               задание попадает во вкладку «Не назначено»

direct       → assignee = выбранный клинер,
               уведомление отправляется немедленно

pool / auto  → кандидаты := apartment_cleaners(A)
               если |кандидаты| = 1 → прямое назначение
               иначе:
                 offer_at := task.date − host.pool_offer_lead_days
                 если A.assignment_strategy = all_at_once:
                     разослать всем кандидатам одновременно
                 если = by_priority:
                     слать по одному по возрастанию priority
                     с таймаутом ожидания ответа
                 первый «Принять» выигрывает; остальным —
                 сообщение «задание уже занято»
```

Фильтр по доступности: кандидат исключается, если день недели задания не входит в его `availability_days` (пустой массив = доступен всегда).

### 13.3 Эвристики качества учёта времени

| Правило | Порог | Где проявляется |
| --- | --- | --- |
| «Очень коротко» | длительность < 5 минут | Предупреждение в drawer завершённой уборки; счётчик «N меньше 5 мин.» в отчёте; сумма «из них X ч. под вопросом» |
| «Без времени» | нет `started_at` / `finished_at` | Счётчик «1 без времени» в отчёте; медиана «—» |
| «Шаги не зафиксированы» | нет записей прогресса | Текст «клинер пропустил процесс в приложении» |
| Корректировка | — | Ручная правка длительности; **исходный замер сохраняется** и должен оставаться доступным в аудите |

### 13.4 Метка SDT (same-day turnover)

Задание помечается SDT , если в день уборки есть и выезд, и заезд. Это операционно самый рискованный тип уборки: окно жёстко ограничено. В обследованных данных 64 из 92 сегодняшних заданий имели эту метку. Требование: SDT участвует в сортировке (выше в списке), фильтруется отдельно и подсвечивается цветом `--status-flight` .

### 13.5 Группировка списка заданий

```
СЕГОДНЯ            date = today
ЗАВТРА             date = today + 1
НА ЭТОЙ НЕДЕЛЕ     today+2 … конец текущей недели
СЛЕДУЮЩАЯ НЕДЕЛЯ   следующая календарная неделя
ПОЗЖЕ              всё, что дальше
ПРОШЕДШИЕ          date < today  (сортировка по убыванию)
```

## 14. Нефункциональные требования

*Локализация, безопасность, данные, производительность*

### 14.1 Локализация

**Наш набор языков: русский, английский, чешский** (`ru` / `en` / `cs`). Оригинал поддерживает двенадцать, включая арабский с RTL — нам это не нужно, объём сознательно сужен под реальный состав команды и портфель объектов (Чехия, Казахстан). Набор расширяемый: добавление языка не должно требовать правок кода, только новый файл переводов.

Язык владельца и язык каждого сотрудника задаются независимо; уведомления уходят на языке получателя.

> **ДЕФЕКТ ОРИГИНАЛА — Главная системная проблема оригинала**
>
> Локализация оригинала выполнена частично: значительная часть интерфейса осталась на языке разработки даже при выбранном другом языке. Затронуто было почти всё: подписи чипов, названия шагов процесса, подсказки форм, форматы дат, служебные страницы, слаги разделов настроек, ключи localStorage.
>
> Требование к нашей системе: **все** пользовательские строки — только через файлы переводов, ни одной вшитой строки в компонентах; все даты — через `Intl.DateTimeFormat` с локалью пользователя; автотест в CI, падающий при появлении «сырой» строки. Языковое наследие оригинала (немецкие слаги и подписи) в наш проект не переносится — везде используются нейтральные английские идентификаторы.

### 14.2 Безопасность и приватность

- Изоляция тенантов на уровне БД (RLS), а не только в коде приложения.
- Учётные данные PMS — шифрование в покое, вывод только по маске, журналирование изменений.
- Аудит всех мутаций: актор, сущность, действие, дифф, укороченный IP.
- Смена e-mail — только через поддержку (сознательное ограничение оригинала; можно заменить на подтверждение по обоим адресам).
- Пароль — минимум 8 символов, смена с подтверждением текущего.
- Медиафайлы — приватный бакет, доступ по подписанным ссылкам с коротким TTL.

### 14.3 Хранение и удаление данных

| Категория | Срок хранения |
| --- | --- |
| Данные аккаунта | 30 дней после завершения договора |
| Задания на уборку и обслуживание, включая фото | 12 месяцев после завершения задания |
| Журнал аудита | 24 месяца |
| Расчётные и бухгалтерские данные | 10 лет |

Обязательны механизмы GDPR: выгрузка данных субъекта в машиночитаемом формате, удаление по запросу, реестр субпроцессоров.

### 14.4 Производительность

- Календарь: первая отрисовка ≤ 2 с при 109 строках × 30 днях; виртуализация строк; закреплённые шапка и первая колонка.
- Список заданий: серверная пагинация; текущий оригинал отдаёт «1000» одним куском — это верхняя граница, а не решение.
- Отчёт по времени: агрегаты считать на сервере, не в браузере.
- Загрузка медиа: прямая в объектное хранилище, с клиентским сжатием фото до отправки.

### 14.5 Доступность

- Контраст текста ≥ 4.5:1 в обеих темах; в оригинале тёмная тема уже описана токенами, но переключателя в интерфейсе нет — его следует добавить.
- Видимый фокус на всех интерактивных элементах (токен `--ring` ).
- Полная клавиатурная навигация в модалках и командной палитре.
- Статус не должен передаваться только цветом — везде дублировать текстом (в оригинале это соблюдено).

1. Новая бронь с выездом через 10 дней создаёт задание в тот же день, с окном объекта и числом гостей заезжающей брони; при отсутствии следующей брони поле «Гости» пусто с корректной подсказкой.

6. Уборка длительностью 3 минуты помечается «под вопросом» в drawer и в отчёте; после ручной корректировки исходный замер доступен в аудите.

8. Календарь на 109 объектах и 30 днях отрисовывается ≤ 2 с и прокручивается без подвисаний.
9. Приложение исполнителя проходит полный цикл уборки в авиарежиме и досылает медиа при восстановлении сети.
10. Сообщение в закрытое 24-часовое окно ставится в очередь, шаблон отправляется, доставка происходит после ответа получателя.

## Д1. Заявки на расходники — НАШЕ ДОПОЛНЕНИЕ

*Функции нет в оригинале CleanFlow. Требование наших процессов.*

> **Статус раздела**
>
> Всё ниже — не реверс-инжиниринг, а наше собственное требование. В CleanFlow
> такой функции нет: там инвентарь существует только как справочник «норма на
> объект» (§6.7 `inventory_item.par_level` ), без механизма запроса пополнения.
> Раздел написан в том же формате, что и остальной документ, чтобы работать с ним
> одинаково.

### Д1.1 Задача

Клинер во время работы обнаруживает, что заканчивается или отсутствует то, чем она
работает: химия, тряпки, мешки для мусора, расходники для гостей. Сейчас это
решается звонком или сообщением в мессенджер — заявка нигде не фиксируется, её
легко потерять, невозможно посчитать расход и непонятно, привезли уже или нет.

Нужен отдельный канал: клинер оставляет заявку в приложении, она попадает
менеджеру списком с количествами, менеджер её обрабатывает.

### Д1.2 Почему это отдельная сущность, а не «Проблема»

Это разные процессы с разными исполнителями, и смешивать их нельзя:

| | Проблема (§7.8) | Заявка на расходники (Д1) |
| --- | --- | --- |
| Что это | Что-то сломано в квартире | Нужно привезти материалы |
| Кто обрабатывает | Техник | Менеджер / снабжение |
| Привязка | К апартаменту, к месту поломки | К клинеру; апартамент необязателен |
| Результат | Выезд и ремонт | Закупка и передача |
| Срочность | Влияет на заезд гостя | Влияет на работу клинера |

Поэтому: **отдельная таблица, отдельная вкладка, отдельный поток.** В интерфейсе
техника заявки на расходники не показываются вовсе.

### Д1.3 Модель данных

`supply_request` — шапка заявки:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid PK | |

> **Связь со справочником инвентаря**
>
> В оригинале уже есть `inventory_item` с полем «норма» ( `par_level` ) по объектам.
> Позиция заявки может ссылаться на него — тогда название и единица подставляются, а
> не набираются вручную. Это ускоряет ввод с телефона и даёт сопоставимую статистику
> расхода. Свободный ввод при этом остаётся обязательно: клинер не должен упереться
> в неполный справочник.

### Д1.4 Экран клинера — `/staff/supplies`

Отдельная вкладка в приложении исполнителя, рядом с «Мои задания» и «Проблемы».

**Список моих заявок.** Группировка по статусу: сначала активные ( `new` ,
`accepted` , `ordered` ), ниже свёрнутый блок завершённых. Карточка: дата создания,
объект (или «Общая»), первые 2–3 позиции с количеством и «+ ещё N», бейдж статуса.

**Создание заявки.** Кнопка «+ Запросить расходники». Форма:

- **Апартамент** — необязательно, по умолчанию подставляется объект текущего
  задания, если заявка создаётся из него.
- **Позиции** — построчный ввод: название, количество, единица. Кнопка
  «+ Добавить позицию». Минимум одна позиция, иначе сохранение недоступно.
  Выбор из справочника инвентаря объекта, если он заполнен, плюс свободный ввод.
- **Срочность** — переключатель «Обычная / Срочно» с подписью, объясняющей разницу,
  а не только цветом.
- **Комментарий** — свободное поле.
- **Фото** — необязательно, до 3 снимков (показать пустую упаковку, марку химии).
  Лимиты — как у фото проблемы (§A.20).

**Что клинер может после отправки:** редактировать и удалять заявку, пока она в
статусе `new` . После того как менеджер перевёл её в `accepted` — только смотреть,
иначе список у менеджера «уезжает» под руками.

### Д1.5 Экран менеджера — `/supplies`

Баннер в общем стиле (§5.4): иконка, заголовок «Заявки на расходники», подзаголовок,
счётчик новых, — и **отдельный пункт в левом меню, в группе «ОПЕРАЦИИ»**.

**Вкладки-пилюли:** «Новые {N}» · «В работе» · «Выполненные» · «Все».

**Таблица:** дата · клинер (аватар + имя) · объект или «Общая» · позиции (свёрнуто:
«Химия для стёкол ×2, мешки ×1 и ещё 3») · срочность · статус · действия.
Разворот строки показывает полный список позиций с количествами и комментариями.

**Действия менеджера:** сменить статус, отклонить с обязательной причиной,
отредактировать количества (клинер попросил 5, выдаём 2 — правка фиксируется в
аудите), объединить несколько заявок в одну закупку (на будущее, не в первой версии).

**Сводка для закупки** — ключевая функция, ради которой всё и делается: кнопка
«Свести к закупке» по выбранным заявкам показывает суммарный список позиций
по всем заявкам с суммированием одинаковых наименований и выгрузкой в CSV.

> **ВНИМАНИЕ — Что сознательно НЕ делаем в первой версии**
>
> Складской учёт, остатки, поставщики, цены и бюджет — вне объёма. Система
> фиксирует запрос и его судьбу, а не ведёт склад. Это граница, которую легко
> перейти незаметно и получить второй продукт внутри первого.

### Д1.6 Права доступа (RLS)

- Клинер видит **только свои** заявки — ни чужие, ни по объектам, к которым
  привязана. Здесь видимость уже, чем у заданий: заявка — личная.
- Клинер создаёт заявку только от своего имени: `requested_by` проставляется
  сервером из сессии, а не приходит с клиента.
- Клинер меняет заявку только в статусе `new` , и только свою.
- Менеджер и админ видят и меняют все заявки своего тенанта.
- **Техник не видит заявки на расходники вообще** — это не его поток.
- Всё изолируется двумя уровнями: тенант ( `host_id` ) и автор.

### Д1.7 Уведомления

| Событие | Кому | Канал |
| --- | --- | --- |
| Новая заявка | Менеджерам тенанта | Push + лента `/notifications` |
| Срочная заявка | Менеджерам тенанта | Push немедленно, отдельная пометка |
| Смена статуса заявки | Автору заявки | Push |
| Отклонение | Автору заявки | Push с причиной — молчаливый отказ недопустим |

### Д1.8 Статистика

Заявки — источник данных, которого нет ни в одном разделе оригинала:

- расход по объектам за период (какая квартира «съедает» больше расходников);
- расход по клинерам — с осторожностью в трактовке: высокий расход может значить и
  небрежность, и просто больше уборок, поэтому нормировать на число заданий;
- частота повторных заявок на одну позицию — сигнал, что норма ( `par_level` )
  занижена и объект надо дозаправлять регулярно, а не по запросу;
- среднее время от заявки до выполнения — метрика качества снабжения.

### Д1.9 Место в плане работ

Функция зависит от приложения исполнителя (Э5 в §16.1) и от роли менеджера.
Разумное место — **после Э5, вместе с Э7 «Проблемы и знания»**: у них общая
механика (создание из приложения → обработка в панели), их логично делать одним
заходом и переиспользовать компоненты списка, карточки и смены статуса.

Минимальная версия для запуска: создание заявки клинером, список у менеджера,
смена статуса, push. Сводка к закупке, объединение заявок и статистика — вторым
шагом.

## C. Что не проверено

*Границы достоверности этого документа*

Обследование велось в режиме «только чтение» с аккаунта владельца: формы открывались, но не отправлялись, деструктивные и синхронизирующие действия не выполнялись. Соответственно, следующие области описаны по косвенным признакам и требуют отдельной проверки перед разработкой:

- **Приложение клинера и техника** — нужен доступ под ролью исполнителя; критично для §9.
- **Админ-панель платформы** — состав экранов взят из карты маршрутов, содержимое неизвестно.
- **Структура чек-листов и инвентаря на уровне пунктов** — в обследованном аккаунте не заполнены ни у одного из 109 объектов; поля пунктов (описание, фото-эталон, обязательность) предположительны.
- **Интерфейс «Входящих» в активном состоянии** — на аккаунте нет ни одного чата.
- **Экраны входа, восстановления пароля и онбординга** — редиректят авторизованного пользователя.
- **Поведение синхронизации PMS** — кнопки не нажимались; логика восстановлена по текстам интерфейса и правилам конфликтов.
- **Тарификация и биллинг** — в интерфейсе владельца не обнаружены; вероятно, вынесены в админ-панель или во внешнюю систему.
- **API** — публичного REST-контракта в браузере не наблюдается (всё через RSC/Server Actions), поэтому схема данных восстановлена по интерфейсу, а не по ответам API.

В ходе обследования в базе знаний была создана одна пустая статья-черновик («Новая статья») — кнопка «+ Новая» создаёт запись без подтверждения. По решению заказчика она оставлена как есть. Других изменений данных не производилось.
