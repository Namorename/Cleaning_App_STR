# Публичный API woom v1 — проект

Ветка `public-api-v1-1028` (от `origin/main` 9bedd62). Задача владельца 28.10: API для его
скриптов, ИИ-агентов и будущих компаний-клиентов. Каждая компания видит только своё. Права
выбираются на каждый ключ. Документация собирается из одного файла спецификации, а правило
паритета не даёт новой функции продукта пройти мимо API.

Hostaway остаётся источником истины. API читает нашу копию его данных и ничего в Hostaway не пишет.

Этот документ — проект. Реализация в той же ветке: что именно сделано и чем проверено, записано в
§14.

## 1. Что входит в v1

| Метод | Путь | Право | Что под ним |
| --- | --- | --- | --- |
| GET | `/v1/me` | любой действующий ключ | сам ключ: имя, префикс, пресет, действующие права, объекты, срок, компания |
| GET | `/v1/properties` | `properties:read` | объекты и комнаты (`properties`), названия без кодов дверей |
| GET | `/v1/properties/{id}` | `properties:read` | один объект |
| GET | `/v1/cleanings` | `cleanings:read` | уборки, осмотры и ремонты (`tasks`): диапазон дат, объект, исполнитель, статус, вид |
| GET | `/v1/cleanings/{id}` | `cleanings:read` | одна уборка |
| POST | `/v1/cleanings/{id}/assign` | `cleanings:assign` | назначить или снять исполнителя — через `save_task` |
| GET | `/v1/cleanings/{id}/media` | `media:read` | фото и видео уборки, только метаданные |
| GET | `/v1/tasks` | `tasks:read` | задания (`problems`, бывшие «Проблемы») |
| GET | `/v1/tasks/{id}` | `tasks:read` | одно задание |
| POST | `/v1/tasks` | `tasks:create` (+ `tasks:assign`, если сразу назначить) | создать задание для техника — через `report_problem` и `assign_problem` |
| POST | `/v1/tasks/{id}/assign` | `tasks:assign` | назначить техника и день — через `assign_problem` |
| GET | `/v1/tasks/{id}/media` | `media:read` | фото и видео задания, только метаданные |
| GET | `/v1/staff` | `staff:read` | сотрудники: id, роль, активность; имя — только с `staff:read_names` |
| GET | `/v1/staff/{id}` | `staff:read` | один сотрудник |
| GET | `/v1/bookings` | `bookings:read` | брони: даты, объект, комнаты, канал, статус, число гостей; без имён, контактов и цены |
| GET | `/v1/bookings/{id}` | `bookings:read` | одна бронь |
| GET | `/v1/settings` | `settings:read` | настройки компании: язык, пределы видео, галерея, параллельный старт |

Итого 17 операций: 15 на чтение и 2 вида записи (назначить исполнителя; создать задание). Слова
API — те же, что в интерфейсе (`docs/rename-table.md`): Tasks — это `problems`, Cleanings — это
`tasks` всех видов, включая ремонт техника по заданию (`type = maintenance`). Внутренние имена
таблиц наружу не выходят.

**Почему не больше записи.** Каждая запись идёт той же серверной функцией, что и в панели. Через
неё срабатывают журнал (`task_events`, `problem_events`), пуши и проверки ролей. Прямой вставки в
таблицы нет. В v1 вошли только те записи, о которых просил владелец. Остальные права
зарезервированы (§3.2).

## 2. Где работает API

| | Next.js route handlers на Vercel (`apps/web/app/api/v1`) | Edge Function Supabase (`supabase/functions/api`) |
| --- | --- | --- |
| Безопасность | на Vercel понадобится ключ `SUPABASE_SECRET_KEY`. Сейчас его там нет: правило CLAUDE.md держит серверные секреты только в Edge Functions. Взлом проекта Vercel дал бы полный доступ к базе | ключ уже живёт в окружении каждой функции; соль хеша ключей (`API_KEY_PEPPER`) добавляется туда же. Панель секретов не получает |
| Холодный старт | Node-функция: сотни миллисекунд, Fluid compute сглаживает | изолят Deno: десятки–сотни миллисекунд |
| Задержка до базы | регион функции Vercel не обязательно совпадает с регионом базы | функции крутятся рядом с базой проекта |
| Хранилище лимитов запросов | нужен внешний KV (Upstash/Redis через Marketplace — новый сервис) или та же база | та же база Postgres: таблица окон, новых сервисов нет |
| Стоимость | по прайсу Vercel: 1 млн вызовов в месяц входит, дальше ≈ $0,60 за миллион плюс активный CPU | Supabase Pro: 2 млн вызовов в месяц входит, дальше $2 за миллион ([billing](https://supabase.com/docs/guides/platform/org-based-billing)) |
| Тестируемость | vitest панели, моки Next | `deno test` (`npm run test:fn`), обработчик — чистая функция с подменяемой базой; против стенда — `deno run` на порту |
| Деплой | **каждый push в `main`**: API уехал бы в прод вместе с панелью, и его нельзя выкатить отдельно от неё (правило «push в main — прод») | отдельная команда `supabase functions deploy api` — выкатывается словом, независимо от панели |
| Адрес | `https://woom-bnb.vercel.app/api/v1/...` | `https://<ref>.supabase.co/functions/v1/api/v1/...`; красивый адрес — позже, rewrite панели или свой домен (§12) |

**Рекомендация: Edge Function `api`.** Решают три вещи:
- секрет базы не покидает Supabase;
- лимиты живут в той же базе без нового сервиса;
- API выкатывается отдельно от панели и не уезжает в прод случайным push в `main`.

Цифры цен — со страниц прайсов на 28.10; перед выкатом их стоит перепроверить.

Вторая функция, `api-keys`, нужна только панели. Она выпускает ключ, потому что соль хеша живёт в
окружении функций, а не в базе: панель зовёт её с токеном админа, функция проверяет токен,
генерирует ключ, считает HMAC и отдаёт ключ панели один раз. Список ключей, смену прав и отзыв
панель делает обычными RPC с проверкой админа в базе — соль для них не нужна.

Документация (`/developers`) живёт в панели. Это статическая страница из файла спецификации,
секретов ей не нужно.

## 3. Права ключа

### 3.1 Реестр

Единый реестр — `packages/shared/src/api/registry.json`. Из него берут данные:
- форма создания ключа в панели (группы, галочки, пояснения, пресеты);
- база — таблица `api_scopes`, её строки миграция кладёт блоком между метками `-- api-scopes:begin/end`. Тест сверяет блоки всех миграций с реестром;
- спецификация OpenAPI — у каждой операции `x-woom-scope` и `security: [{ apiKey: [<право>] }]`. Таблицы прав, пресетов и запретного списка в `info.description` генерирует `npm run api:docs`, тест падает, если они устарели.

Право — `ресурс:действие`. Уровень чувствительности:
- **обычное**: данные о работе, без персональных данных и без доступа к зданию;
- **чувствительное**: персональные данные сотрудников, адреса объектов. Такое право включается только галочкой вручную, ни в «Только чтение», ни в «Оператор» оно не входит.

| Право | Группа | Уровень | Статус | Что даёт |
| --- | --- | --- | --- | --- |
| `properties:read` | объекты | обычное | выставлено | объекты и комнаты, безопасные названия |
| `properties:read_address` | объекты | **чувствительное** | выставлено | поле `address` |
| `cleanings:read` | уборки | обычное | выставлено | уборки, осмотры, ремонты |
| `cleanings:assign` | уборки | обычное, запись | выставлено | назначить или снять исполнителя |
| `tasks:read` | задания | обычное | выставлено | задания |
| `tasks:create` | задания | обычное, запись | выставлено | создать задание |
| `tasks:assign` | задания | обычное, запись | выставлено | назначить техника и день |
| `staff:read` | сотрудники | обычное | выставлено | id, роль, активность |
| `staff:read_names` | сотрудники | **чувствительное** | выставлено | поле `full_name` |
| `bookings:read` | брони | обычное | выставлено | брони без гостя и цены |
| `media:read` | медиа | обычное | выставлено | метаданные фото и видео |
| `settings:read` | настройки | обычное | выставлено | настройки компании |

### 3.2 Зарезервированные права

Право есть в реестре, но выдать его пока нельзя: метода под ним ещё нет. Когда метод появится,
право станет «выставлено» и попадёт в пресеты по своим правилам (§3.3).

`cleanings:create`, `cleanings:cancel`, `cleanings:read_steps`, `tasks:update`, `tasks:resolve`,
`tasks:cancel`, `bookings:read_prices` (чувств.), `media:download` (чувств.), `settings:write`
(чувств.), `checklists:read`, `checklists:write` (чувств.), `supplies:read`, `supplies:write`,
`analytics:read`, `chat:read` (чувств.), `chat:write` (чувств.), `properties:write` (чувств.),
`staff:write` (чувств.), `webhooks:manage` (чувств.).

### 3.3 Пресеты

Ключ хранит пресет, а не развёрнутый список. Действующие права вычисляются при каждом вызове из
реестра в базе, поэтому «включая будущие» работает без переписывания ключей.

| Пресет | Состав | Будущие права |
| --- | --- | --- |
| «Только чтение» (`read_only`) | все выставленные `…:read` уровня «обычное» | входят, если обычные и на чтение |
| «Оператор» (`operator`) | «Только чтение» + права с пометкой `operator` в реестре: `cleanings:assign`, `tasks:create`, `tasks:assign` | входят обычные на чтение и помеченные `operator` |
| «Полный доступ» (`full`) | все выставленные права, включая чувствительные | входят все, кроме запретного списка — его в реестре прав нет вовсе |
| «Свой набор» (`custom`) | ровно отмеченные галочки | не входят |

К «Только чтение» и «Оператору» можно добавить чувствительные права галочками. Они хранятся в
`scopes` ключа и складываются с пресетом.

«Полный доступ» по тексту задачи — все права, кроме запретного списка, значит и чувствительные.
Панель предупреждает: «это как пароль админа». Создание и повышение до него требуют повторного ввода
имени ключа; база проверяет это сама (`p_confirmation`), а не только форма. Если вы хотели «Полный»
без чувствительных — это вопрос в отчёте.

### 3.4 Запретный список — «Что API никогда не делает»

Этих прав нет в реестре выдаваемых, их не даёт ни один пресет. База отклоняет ключ, в котором они
названы (`apiErrors.scopeForbidden`).

| Запрет | Почему |
| --- | --- |
| `api_keys:manage` — создавать, читать, отзывать ключи | ключ, выпускающий ключи, переживает свой отзыв: утечка одного стала бы вечной |
| `staff:manage_privileged` — учётные данные и роли админов и менеджеров | захват компании: ключ сделал бы себе админа или сменил пароль владельцу |
| `staff:read_contacts` — почты и телефоны сотрудников | персональные данные; для работы API хватает id |
| `guests:read_personal` — имена, контакты, переписка гостей | персональные данные гостей; брони отдаются без них |
| `access_codes:read` — коды дверей, сейфов, замков | физический доступ в объект; F27 выносит коды в отдельные поля, API их не отдаёт никогда (§6.4) |
| `integrations:read_secrets` — секреты и токены Hostaway, вебхуков, push-токены устройств | чужие учётные данные; утечка = доступ к Hostaway или рассылке пушей |
| `hostaway:write` — запись в Hostaway | Hostaway — источник истины, API его только читает (через нашу копию) |
| `data:destroy` — необратимое удаление | в v1 только отмена и архив; удаление нельзя отменить, а ключ могут украсть |
| `security:write` — настройки безопасности (вход, роли, хранение, политики ключей) | ключ не должен ослаблять защиту, которая его же ограничивает |
| `tenants:cross` — данные других компаний | изоляция компаний; `host_id` берётся только из ключа (§5.2) |

### 3.5 Ключ и его создатель

- Ключ создаёт только админ (`profiles.role = 'admin'`). Его права ключа — не больше прав
  создателя: любая запись идёт от его имени через те же функции, что проверяют роль.
- Ключ работает, пока создатель — **активный админ той же компании**. Это проверяется при каждом
  вызове. Если создателя деактивировали или понизили до менеджера, ключ приостанавливается: ответ
  `401 key-suspended`, в панели статус «Приостановлен: создатель неактивен». Вернули создателю роль
  или активность — ключ снова работает. Другой админ может отозвать такой ключ и выпустить свой;
  передачи ключа в v1 нет (§12).
- Записи из API стоят в журналах от имени создателя ключа. В журнале вызовов API лежит id ключа и
  id созданного объекта, поэтому «кто и каким ключом» восстанавливается.

## 4. Ограничения ключа

- **Объекты.** `property_ids` — список id объектов, `null` — все. Комнаты выбранного здания
  входят сами: проверка идёт по объекту и его родителю. Ключ с ограничением:
  - не видит задания без объекта;
  - получает `404` на чужой объект при чтении одного объекта;
  - получает `403 property-not-allowed` при записи на объект вне списка;
  - видит список сотрудников и настройки компании: они не привязаны к объектам.

  Ограничение проверяет база внутри функций API, тем же `host_id` из ключа, поэтому изоляцию
  компаний оно не усложняет.
- **Срок.** `expires_at` (30, 90, 365 дней или «бессрочно»; в форме по умолчанию 90). Просроченный
  ключ получает `401 key-expired`.
- **Список IP** — только дизайн (§12).

## 5. Модель безопасности

### 5.1 Ключ

- Формат: `woom_` + 43 знака base64url из 32 случайных байт (`crypto.getRandomValues`). Префикс для
  показа — первые 12 знаков (`woom_AbCdEfG`).
- В базе только `key_digest` = HMAC-SHA256(`API_KEY_PEPPER`, ключ) в hex. Соль живёт в секретах
  функций, в базе её нет: дамп таблицы не даёт ни ключей, ни способа их проверить.
- Ключ показывается один раз, в ответе `api-keys`. Панель держит его в памяти до закрытия окна и
  нигде не сохраняет.
- Ключ передаётся только заголовком `Authorization: Bearer <ключ>`. Ключ в адресе (`?key=`,
  `?api_key=`, `?access_token=`) — `400 key-in-url`: адреса оседают в логах прокси.
- Сравнение: строка ищется по `key_digest` (уникальный индекс). Найденный дайджест функция ещё раз
  сравнивает с вычисленным за постоянное время (`timingSafeEqual`). Тайминг поиска по индексу ничего
  не даёт: дайджест — HMAC с неизвестной атакующему солью, подобрать вход к нужным байтам нельзя.
- Ключ не попадает в логи и ошибки. Функция не логирует заголовки, ответы с ошибкой не повторяют
  ключ, журнал вызовов хранит `key_id`.

### 5.2 Изоляция компаний

- Все функции API в базе (`api_v1_*`) принимают дайджест ключа, а не `host_id`. Компания, создатель,
  права и ограничение по объектам берутся из строки ключа в той же транзакции. Каждый запрос
  фильтруется по этому `host_id`.
- Функции `api_v1_*` и `api_gate` — `security definer`. Выполнять их может только `service_role`
  (`revoke all … from public, anon, authenticated`), то есть Edge Function. Браузер и телефон их не
  видят.
- Таблицы ключей и журналов клиентским ролям не выдаются (`revoke all`, матрица
  `table_grants.sql`).
- Запись идёт от имени создателя. Функция API ставит на время своей транзакции
  `request.jwt.claims = {"sub": <создатель>, "role": "authenticated"}` и зовёт ту же функцию, что и
  панель (`report_problem`, `assign_problem`, `save_task`). Их проверки (`current_host_id()`,
  `is_manager()`), триггеры журналов и пушей видят создателя, как будто он нажал кнопку в панели.
  Задание никогда не остаётся без автора: `reported_by` — создатель ключа (§6.5).

### 5.3 Лимиты

- **На ключ:** 120 запросов в минуту, фиксированное окно в Postgres (`api_rate_windows`).
  Заголовки:
  - на каждом ответе: `RateLimit-Policy: "default";q=120;w=60` и
    `RateLimit: "default";r=<осталось>;t=<секунд до сброса>` (черновик IETF httpapi-ratelimit-headers);
  - для привычных клиентов дублируются `X-RateLimit-Limit`, `X-RateLimit-Remaining`,
    `X-RateLimit-Reset`.
- **Неудачные авторизации на IP:** 20 за 10 минут. Дальше `429` на любой запрос с этого IP до конца
  окна, ключ даже не ищется. IP хранится только как HMAC, окна живут сутки.
- Превышение — `429 rate-limited` с `Retry-After`.
- Окна чистит задание pg_cron.

### 5.4 Журналы

- `api_request_log`: ключ, компания, `operationId`, метод, статус, длительность, id объекта записи,
  время. Нет тел запросов, строк запроса, IP и персональных данных. Хранится 90 дней (pg_cron).
- `api_key_events`: создание, смена прав, отзыв — кто, когда, «было» и «стало» (пресет, права,
  объекты, срок, имя).
- `last_used_at` ключа обновляется не чаще раза в минуту, чтобы не писать на каждый запрос.

### 5.5 Что в ответах не бывает никогда

- имён, телефонов, почт и переписки гостей;
- цены брони;
- почт и телефонов сотрудников;
- кодов дверей (§6.4);
- заметок горничной к объекту (`cleaner_notes`) и заметок уборки (`notes`): в свободном тексте бывают
  коды и данные гостя;
- путей файлов в хранилище и подписанных ссылок на медиа (зарезервировано `media:download`).

## 6. Данные

### 6.1 Общие правила

- Поля в `snake_case`. Ответ одного объекта — `{"data": {...}}`, списка —
  `{"data": [...], "next_cursor": "…" | null}`.
- Время — ISO 8601 в UTC с `Z`, точность до секунды: `2026-10-28T09:15:00Z`.
- Календарные дни (день уборки, заезд, выезд) — `YYYY-MM-DD` в часовом поясе объекта, без времени.
  Часы окна уборки — `HH:MM` по местному времени объекта. Пояс объекта — поле `timezone`.
- Неизвестные клиенту поля и значения перечислений клиент обязан пропускать (§8).

### 6.2 Пагинация и фильтры

- Курсор непрозрачный (base64url). Внутри — последняя пара ключа сортировки и отпечаток фильтров.
- `limit` от 1 до 200, по умолчанию 50. Конец списка — `next_cursor: null`.
- Курсор с другими фильтрами — `400 invalid-cursor`.
- Сортировка постоянная:
  - объекты — `id`;
  - уборки — `scheduled_date, id`;
  - задания — `created_at, id`;
  - сотрудники — `id`;
  - брони — `arrival_date, id`.
- Фильтры:
  - **объекты:** `status` (список через запятую), `parent_id`, `updated_since`;
  - **уборки:** `date_from`, `date_to` (по `scheduled_date`, включительно, не больше 366 дней между ними), `property_id`, `assignee_id`, `status`, `type`, `updated_since`;
  - **задания:** `status`, `priority`, `property_id`, `assignee_id` (исполнитель живой работы), `created_from`, `created_to`, `include_archived`, `updated_since`;
  - **сотрудники:** `role`, `active`;
  - **брони:** `date_from`, `date_to` (бронь пересекает диапазон), `property_id`, `channel`, `status`, `updated_since`.

### 6.3 Идемпотентность POST

- Заголовок `Idempotency-Key` (1–255 видимых ASCII) **обязателен** у всех POST. Без него —
  `400 idempotency-key-required`: агент, повторивший запрос после обрыва, иначе создаст второе
  задание.
- Ключ запоминается на 24 часа в пределах API-ключа вместе с отпечатком тела и ответом. Повтор с тем
  же телом получает тот же ответ и заголовок `Idempotent-Replayed: true`. Тот же ключ с другим телом —
  `422 idempotency-key-reused`.
- Одновременные повторы сериализует уникальный индекс: второй ждёт первого и получает его ответ.
- Ответ с ошибкой не запоминается: ошибку можно исправить и повторить с тем же ключом.

### 6.4 Названия объектов и коды дверей (F27)

- В облаке 42 из 114 названий объектов подходят под шаблон кода: «|code - ####|», «door ######»,
  «lockbox ####», «keypad #######», «Unit # - ####», «# - ####». Чтение 28.10 по форме — каждая
  цифра заменена на `#`, сами названия не выводились. В ROADMAP F27 упомянуты 18 (раньше было 15), но
  шаблон «номер комнаты — четыре цифры» встречается и у комнат, и он тоже похож на код.
- API отдаёт `name` через `api_safe_property_name()`:
  - убирает отрезки «code / door / lockbox / keypad / pin / kód / код + цифры» вместе с рамкой `|…|`;
  - заменяет на `••••` любую оставшуюся отдельную серию из 4 и более цифр;
  - схлопывает лишние разделители.

  Поле `name_masked: true` говорит, что маска сработала.
- Сырое название наружу не выходит ни при каком праве.
- Связь с F27: F27 переносит коды в структурные поля, их видимостью управляет менеджер. После этого
  названия чистит ночной синк из Hostaway. Маска остаётся страховкой на случай, если код снова
  впишут в название. Структурные коды API не отдаёт никогда (`access_codes:read` в запретном
  списке).

### 6.5 Автор задания

Задание, созданное через API, получает `reported_by` = создатель ключа. Пустого автора не бывает.
Это обходит найденное в проекте отзывов падение панели и телефона на задании без автора (исправление
ещё не в проде). Служебный профиль компании не понадобился: создатель ключа — живой админ, иначе
ключ приостановлен (§3.5).

## 7. Ошибки — RFC 9457 `application/problem+json`

```json
{
  "type": "urn:woom:problem:insufficient-scope",
  "title": "The key lacks the scope this operation needs",
  "status": 403,
  "detail": "listCleanings needs cleanings:read",
  "code": "insufficient-scope",
  "required_scope": "cleanings:read",
  "request_id": "6f1c…"
}
```

- `type` — URN `urn:woom:problem:<code>`. Он не зависит от домена: адрес панели ещё сменится.
- `code` дублирует хвост для удобства.
- Причина отказа из серверной функции — `reason` (стабильный ключ, например
  `serverErrors.taskAssigneeInvalid`), её параметры — `params`.
- Текст ошибки базы наружу не идёт, только `code`, `reason` и `params`.

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `invalid-request` | параметр не той формы; `errors[]` — `{name, message}` |
| 400 | `invalid-cursor` | курсор битый или от других фильтров |
| 400 | `key-in-url` | ключ в строке запроса |
| 400 | `idempotency-key-required` | POST без `Idempotency-Key` |
| 401 | `missing-key` | нет заголовка `Authorization: Bearer` |
| 401 | `invalid-key` | ключ неизвестен или искажён |
| 401 | `key-expired` / `key-revoked` / `key-suspended` | срок вышел / отозван / создатель неактивен |
| 403 | `insufficient-scope` | нет права; `required_scope` назван |
| 403 | `property-not-allowed` | запись на объект вне списка ключа |
| 404 | `not-found` | нет такого объекта в этой компании или в объектах ключа; неизвестный путь |
| 405 | `method-not-allowed` | метод не тот; заголовок `Allow` |
| 409 | `conflict` | состояние не позволяет: уборка закрыта, задание решено и т. п.; `reason` |
| 413 | `payload-too-large` | тело больше 16 КБ |
| 415 | `unsupported-media-type` | POST не `application/json` |
| 422 | `rejected` | бизнес-правило: исполнитель не из компании, ремонт не горничной; `reason`, `params` |
| 422 | `idempotency-key-reused` | тот же ключ идемпотентности с другим телом |
| 429 | `rate-limited` | лимит; `Retry-After` |
| 500 | `internal` | всё прочее; подробности только в логе функции, без ключа и тел |

Ошибки серверных функций сопоставляются по `errcode` и `hint`:
- `check_violation` при известном `hint` → 409 (уборка или задание закрыто, перенесено, архивно) или 422 (остальное);
- `insufficient_privilege` → 403;
- `no_data_found` → 404.

## 8. Версии и политика изменений

- Версия — в пути: `/v1`. Внутри v1 изменения только **добавляющие**: новые поля, методы,
  необязательные параметры, значения перечислений, права. Клиент обязан не падать на неизвестном
  поле и значении.
- Ломающее изменение — переименование или удаление поля, смена типа или смысла, новый обязательный
  параметр. Оно идёт в `/v2`. `/v1` живёт после выхода v2 не меньше 12 месяцев. Его ответы несут
  `Deprecation` (RFC 9745) и `Sunset` (RFC 8594) с датой, а также `Link` на заметку о переезде.
- История изменений — раздел «Changelog» в `info.description` спецификации; `info.version` — semver
  спецификации (`1.0.0`).

## 12. На потом (только дизайн)

- **Исходящие вебхуки** «задание создано» (`task.created`) и «уборка завершена» (`cleaning.completed`):
  - **хранение:** таблица подписок `api_webhooks` — компания, URL `https`, события, секрет подписи
    (хранится зашифрованным, показывается один раз), статус;
  - **очередь:** события берутся из существующих журналов (`problem_events`, `task_events`) триггером
    в очередь `raw.api_webhook_outbox`; доставляет pg_cron + pg_net или функция `api-webhooks`;
  - **подпись:** `Woom-Signature: t=<unix>,v1=<HMAC-SHA256(secret, t + "." + тело)>`. Получатель
    проверяет подпись и отбрасывает запросы старше 5 минут;
  - **повторы:** 5 попыток с ростом паузы (1 мин → 6 ч), после 50 подряд неудач подписка выключается
    и менеджер видит причину;
  - **тело:** `{id, type, created_at, data: {<объект как в GET>}}` — тех же полей, без персональных
    данных;
  - **право:** `webhooks:manage` (чувствительное, зарезервировано).
- **Список IP ключа:** `allowed_cidrs cidr[]`; запрос не из списка — `403 ip-not-allowed`. Нужно
  сначала проверить на проде, какому заголовку с IP клиента можно верить за шлюзом Supabase.
- **Передача ключа** другому админу при уходе создателя, служебный профиль компании.
- **Свой адрес** `api.<домен>`: rewrite панели на функцию или свой домен Supabase (платное
  дополнение — не подключаем без слова).
- Подписанные ссылки на медиа (`media:download`), цены броней (`bookings:read_prices`).
