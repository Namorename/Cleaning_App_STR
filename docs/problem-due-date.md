# Дата выполнения заданий техников (CORE), 26.11

Промпт владельца 26.11, часть Б («чтобы можно было назначать на будущее»), без присмотра. Миграция
`supabase/migrations/20261126130000_problem_due_date.sql`, набор `supabase/tests/problem_due_date.sql`,
общий модуль `packages/shared/src/problems/queue.ts`. Выкат — `docs/rollout/boards-dates-chats-1126.md`.

## Данные и права

- `problems.due_on date` — необязательная «дата выполнения» (только день). Ставит **офис** (менеджер,
  админ, Reception): при создании (`report_problem(…, p_due_on)`; форма «Новое задание» в панели —
  обычная и с каталогом категорий; форма менеджера на телефоне) и потом в самом задании
  (`set_problem_due_date`, `null` — убрать). Отчёт с поля (горничная, техник, главный техник) с датой
  сервер отклоняет (`problemDueOfficeOnly`); без даты — как раньше.
- Дата — от вчерашнего дня до года вперёд (`problemDueInvalid`; «вчера» — потому что вечер компании
  в Праге уже следующий день сервера).
- Журнал задания изменение даты не пишет (новый вид события сломал бы старые клиенты, как и при
  правке текста 19.11); уведомлений нет новых и существующие не менялись.
- Старые телефоны и API v1 зовут `report_problem` без даты — аргумент последний, по умолчанию `null`
  («ничего не сказано»); отдельный тест зовёт функцию по-старому.
- **API v1**: подходящего поля срока у задания нет (`work.scheduled_date` — день выезда техника, это
  другое), поэтому `set_problem_due_date` записана в `coverage.json` как внутренняя с причиной;
  ответы API не изменились.

## Порядок очереди

Одно правило для всех очередей обоих приложений (`orderQueue`):

1. **эффективная дата** — дата выполнения, а без неё — день создания (по часовому поясу объекта);
   раньше — выше, поэтому запланированное на будущее стоит ниже сегодняшней работы;
2. **срочность** — критическая, высокая, обычная, низкая;
3. **время создания** — старше выше.

Где: доска «Задания техников» в панели (колонки «Открыто», «Назначено», «В работе»; «Выполнено» —
по времени закрытия, как раньше: это история), список заданий в панели (живые по очереди, закрытые
после них), «Мои задания» техника, доска главного техника и менеджера на телефоне.

На карточке и в строке видна дата: «Сегодня», «Завтра» или сама дата; у техника на телефоне перед
заданиями на будущие дни — заголовок «Запланировано».

## «Висит N дней» и «Просрочено»

Правило 05.11 (`OVERDUE_AFTER_DAYS = 3` в `packages/shared/src/schedule/job-tail.ts`) считает от дня
работы техника. Теперь — от **более поздней** из двух дат: день работы и дата выполнения
(`plannedTail`/`tailDay`). Задание, запланированное на будущее, не «висит» и не просрочено до своего
дня, как бы рано ни назначили выезд.

Места, где это правило применяется (сверены по коду):

Панель:

1. **Карточка доски «Задания техников», строка списка, страница задания** —
   `features/problems/schema.ts` `repairTail` (в `problem-card.tsx`, `problems-table.tsx`, блок работы на
   странице задания): `plannedTail(день работы, due_on, сегодня по поясу объекта)`.
2. **Правило ремонта для календаря и дашборда** — `features/tasks/repairs.ts`: `isRepairOverdue` через
   новый `repairTailOf` (`plannedTail` с `problem.due_on`), новый `repairTailDay`;
   `overdueRepairsByProperty().since` — от `repairTailDay`. Читатели берут дату задания: `fetchLiveRepairs`
   (`problem:problem_id(due_on)`), `fetchTasksBetween` (`problem:problem_id(title, priority, critical, due_on)`).
3. **Календарь** — значок объекта (`calendar-view.tsx` через `overdueRepairsByProperty`) и «Просрочено» на
   плашке ремонта (`task-chips.tsx` `isRepairOverdue`) — через п. 2.
4. **Дашборд** — `dashboard/counts.ts` `stuckRepairs` (дни — `repairTailOf`, просрочка — `isRepairOverdue`,
   порядок — `repairTailDay`), `repairCounts` следом; `stuck-repairs.tsx` показывает `repairTailDay`, чтобы
   «Висит N дней» совпадало с показанным днём.
5. **«Уборки»** — `tasks/schema.ts` `tailOf`/`isOverdue`: только уборки (ремонты ушли из «Уборок» 05.11),
   без изменений.
6. **Стенд календаря** (`calendar/stand-tasks.ts`) — без изменений: строки читаются с `due_on = null`.
7. Гости и доски менеджеров — правила «висит» по ремонту у них нет (у карточек досок свой срок).

Телефон:

8. **Карточка доски главного техника и офиса** — `features/board/board-card.tsx` `repairTail` →
   `plannedTail` с `problem.due_on`.
9. Других мест `jobTail`/`OVERDUE_AFTER_DAYS` на телефоне нет («просрочено» у видео — ожидание загрузки,
   другое).

## Интерфейс

- Панель: «Новое задание» (обычное и с каталогом) — поле даты (сегодня…+366 дней по дню браузера) с
  подсказкой; страница задания — блок «Дата выполнения» над работой техника: «Без даты» / дата /
  «Сегодня · дата», «Выбрать/Изменить дату», «Убрать дату» (у живого задания); форма назначения
  техника по умолчанию ставит дату выполнения, если она сегодня или позже.
- Телефон: форма «Создать задание» у менеджера, админа и Reception — выбор дня сеткой месяца (без
  нативных зависимостей); экран задания — факт «Дата выполнения», у офиса — «Выбрать дату» листом и
  «Убрать дату» (только при связи); «Мои задания» техника — живые по очереди, будущие под заголовком
  «Запланировано»; на карточке — «Дата: Сегодня/Завтра/04.12». Свои отчёты горничной — по-прежнему
  новые сверху (очередь — для техников).
- Старый кэш телефона без `due_on` читается (`.default(null)`); отчёт, поставленный в очередь старой
  сборкой, уходит без даты.

## Оставлено (записано)

- Отчёт офиса с датой, отправленный без связи и дошедший, когда день уже вне диапазона, сервер
  отклонит (три повтора, потом сбой) — редкость.
- Лист назначения главного техника на телефоне по-прежнему предлагает «сегодня» (не дату выполнения).
