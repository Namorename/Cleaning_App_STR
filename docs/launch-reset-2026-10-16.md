### Порядок удаления (проход 2) и почему такой

1. **`push_tokens` уходящих.** Push-триггеры (`push_on_task_change`, чат) сразу выходят, если
   токенов в базе нет; у оставляемого менеджера их нет. Так очистка не поставит ни одного push
   в очередь.
2. **`supply_requests`.** `requested_by → profiles` — `restrict`, иначе удаление учёток упадёт.
3. **Ремонты** (`tasks.problem_id is not null`) до заданий. `tasks.problem_id → set null`:
   ремонт без задания выглядел бы ручной работой. Удаление ремонта переоткрывает задание
   (`mirror_problem_status`), а запись в `problem_events` уходит в шаге 4.
4. **`problems`.** `reported_by → profiles` — `restrict`. Каскадом уходят `problem_events`,
   `task_media` заданий и ветки чата заданий.
5. **Уборки до 15.10 и демо-уборки.** Каскадом уходят `task_steps`, `task_media`, ветки,
   сообщения, прочтения, `task_events`, `raw.push_outbox`. Обнуляются `problems.task_id`,
   `supply_requests.task_id`, `problem_events.task_id` — к этому шагу этих строк уже нет.
6. **Демо-объект.** `tasks.property_id → cascade`. Триггер `properties_delete_units` удаляет
   его комнаты (их нет).
7. **Снять назначения уходящих с остающихся уборок.** `tasks.assignee_id → set null` вместе с
   CHECK `tasks_assigned_has_assignee` уронил бы удаление учётки с живым назначением. Закрытые
   (`done`/`cancelled`/`expired`) теряют только исполнителя, `assigned`/`accepted` становятся
   `unassigned`. Начатые (`in_progress`/`paused`/`blocked`) — застава, проход остановится.
8. **Брони до 15.10.** Каскадом уходит `reservation_units`; `tasks.reservation_id → set null`
   (0 строк, проверено). Затем сырые копии (вопрос 2).
9. **`auth.users` уходящих.** `profiles` уходят каскадом, за ними `property_cleaners`,
   `chat_threads`/`chat_reads` личных веток, `push_preferences`, `raw.push_outbox`,
   `raw.push_tickets`. Колонки авторства (`created_by`, `completed_by`, `author_id`,
   `actor_id`…) становятся `null`.
10. **События, которые записал сам проход** (шаг 7 пишет `unassigned`), удаляются (вопрос 5).
11. **Заставы после.** Любое расхождение откатывает весь проход.

Каскады проверены прогоном всех проходов на локальном стенде в транзакции с `ROLLBACK`
(16.10, ниже «Проверка скриптов»).

### в) Триггеры при удалении броней и уборок

- **На `DELETE` у `reservations` и `reservation_units` триггеров нет.**
  - Удаление брони только обнуляет `tasks.reservation_id` у остающихся уборок, а таких 0.
    Даже если бы были: журнальные триггеры (`tasks_journal_cleaning_update`,
    `tasks_journal_repair`) слушают статус, исполнителя, день, объект и время, а не
    `reservation_id`.
  - Statement-триггер `tasks_push_update` срабатывает на каждое такое `UPDATE`, но выходит
    сразу: push-токенов к этому шагу нет.
  - Уборки ничто не пересоздаёт: генератор зовут только Edge Functions синка, не триггеры.
- **На `DELETE` у `tasks` срабатывает только `tasks_mirror_problem`.** Для живого ремонта он
  переоткрывает задание и пишет `problem_events`; оба уходят шагом 4. `task_events` при удалении
  не пишутся, push не ставится.
- **Пишет журнал ровно один шаг — снятие тестовых людей с остающихся уборок** (сейчас 12
  отменённых). Это `unassigned` с `cause = 'system'` и `params.from` = id удалённого.
  Проход удаляет эти события в конце той же транзакции: `at ≥ начала прохода`,
  `kind = 'unassigned'`, `params.from` из списка уходящих (`task_events.at` по умолчанию
  `clock_timestamp()`). Отключать триггеры не нужно.
- **Защиты `guard_task_fields` и `guard_task_transitions`** под `db query` выходят сразу:
  `auth.uid()` пуст.

### г) «Отключение снимает назначения» и удаление учёток

- `profiles_release_work` срабатывает только на `UPDATE OF is_active` из `true` в `false`
  (`20261004100000_staff_disable.sql:453-457`). На `DELETE` у `profiles` и `auth.users`
  триггеров нет. Удаление учётки работу не освобождает, а живое назначение его роняет
  (CHECK выше).
- Поэтому проход сам снимает назначения (шаг 7), а начатую работу пропускает только через
  заставу.
- **Отключать учётки перед удалением не нужно и не стоит.** `release_work_of_inactive` пишет
  события `staff_inactive`, а при живых привязках и токенах ставит push `cleaning_free` другим
  тестовым людям.

- Обязательны только `id` (bigint, без последовательности — это id листинга Hostaway) и
  `name`.
- `host_id` берётся из умолчания `default_host_id()` (единственная компания).
- `timezone` по умолчанию `UTC`, нужно `Europe/Prague`: по нему считается день ремонта.
- `status` по умолчанию `active`.
- Адрес, город, время заезда и выезда, `parent_id`, `hostaway_unit_id` необязательны.
- Триггеров на вставку нет, кроме `properties_guard_hierarchy`, а он при пустом `parent_id`
  ничего не делает.

**Синк и генератор его не тронут.**
- `sync_hostaway_listings` пишет только присланные id, `status` не трогает и ничего не удаляет
  (`20260912120000_property_units.sql:127-135, 187-198`).
- Синк броней только сверяет id объектов.
- Генератор рождает уборки только из броней (`20260927120000_pinned_rooms.sql:568-595`), а у
  «Hotel» их не будет.
- Периодических работ по объектам нет.
- id `800000000001` (решение владельца 16.10: «Hotel» входит в статистику).
  - Он лежит выше всех листингов Hostaway (98 352–601 842, медиана 355 788) и ниже комнат
    (10¹² + id, сейчас 1 000 000 018 007–1 000 000 064 305).
  - Он вне тестовой полосы аналитики `900000000000…999999999999`.
  - Других особых диапазонов в коде нет: синки, генератор, RLS и приложения номера объектов
    по величине не делят (проверено 16.10).

**Техники и главный техник.**
- Задание на «Hotel» создаёт **менеджер в панели**: `report_problem` с объектом доступен
  менеджеру или привязанному к объекту (`20260908130000_problems.sql:228-236`).
- Отдаёт его технику менеджер или главный техник (`assign_problem`,
  `20261003130000_head_tech_dispatch.sql:99, 448-453`).
- Привязать техника к объекту нельзя совсем: триггер `property_cleaners_no_tech`. Привязка и
  не нужна: техник видит объект и работу через назначение (ветка исполнителя в
  `staff_property_ids()`).
- Главный техник видит все задания и их ремонты. Объект он видит, как только на нём есть
  задание.
- Создать задание на «Hotel» ни техник, ни главный техник не могут: кнопки нет, а
  `report_problem` их откажет. Решение владельца 16.10: правок нет.

**Аналитика** (id вне тестовой полосы — «Hotel» считается везде; правок панели нет).
- **Задания и ремонты** на «Hotel» входят в цифры заданий и в таблицу техников

## 6. Восстановление, если что-то пойдёт не так

**Проход 2 — одна транзакция.** Ошибка, застава или обрыв связи откатывают его целиком, данные

1. **Вся база — платформенная копия Pro.**

     03:00 UTC). Проект на время восстановления недоступен — порядка 10–30 минут при нашем
     размере, точнее скажет Dashboard.

     −7…+90 или ручной вызов `sync-reservations?daysBack=N`), уборки от генератора (родятся
     снова), работа в приложении и панели, push-история, события журнала.

     проходом 1, — нет; их надо залить заново из `storage/task-media/…` нашей копии.

  запускается одна, по слову.
- **Схема облака ≠ `main`.** В облаке две миграции, которых нет в `main` (§1). Скрипты очистки
  их колонок не трогают; при следующем `db push` сверять полный список сухого прогона.
- **Как снималась копия.**
  - Временная роль `cli_login_postgres` — механизм CLI, общий с `migration list`.
