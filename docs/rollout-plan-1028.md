## 3. Миграции и каталог

**Как ведёт себя `db push` (CLI 2.115):**
1. **В облаке есть версия, которой нет в каталоге** — `main` без `20261010100000` и `20261011100000`.
   - Push отказывает: «Remote migration versions not found in local migrations directory».
   - CLI предлагает `migration repair --status reverted`. **Этого не делать:** repair пометит
     применённые миграции откатанными, и история облака перестанет совпадать с базой.
   - Лечение одно — вернуть файлы в каталог, то есть слить `phone-1-2-0` в `main`.
2. **Локальный файл старше головы облака и не применён.** Push отказывает: «Found local migration
   files to be inserted before the last migration on remote database» и предлагает `--include-all`.
   - **`--include-all` не берём** (решение 23.09, `docs/chat-plan.md`): облако применит файл ПОСЛЕ
     головы, а `db:reset` — по имени, раньше. Порядок в облаке и на стенде разойдётся, и зелёные
     тесты перестанут отвечать за облако.
   - Лечение — новый номер в день собственного выката.
   - Это ждёт базу знаний (`20261017100000`) и отзывы (`20261017110000`): после видео (`20261023…`) и
     API (`20261028…`) обе окажутся позади головы.
   - Документ видео (§4) ещё советует для них `--include-all` — этот совет отменён тем же решением.
3. **Файл новее головы** — обычный push. Видео (`20261023100000`) новее головы `20261015120000`.
   API (`20261028100000`) новее видео. Поэтому порядок «видео → API» сохраняет оба номера как есть.
   Обратный порядок потребовал бы перенумеровать видео.

**Перенумеровка (шаги 4 и 5)** — по рецепту `docs/chat-plan.md` («Рецепт выката окна 2», шаг 0):
- номер — метка дня выката, новее головы облака на тот момент; взаимный порядок «база знаний →

**Застава** (`docs/units-plan.md`, «Эксплуатация выката»), исправленная под новый компьютер:
- голову читает `cloud-read` (роль только для чтения), а не `db query --linked`;
- разбор делает `node`, а не `python` — Python на этой машине нет;
- вывод сухого прогона — `--output-format json` явно, а не через переменную `CLAUDECODE`.

Если любой разбор не удался, строка пуста и застава закрывается, а не открывается.

```bash
# из корня дерева main; HEAD_WANT — голова облака сейчас; LIST_WANT — всё, что должно уехать, через пробел
HEAD_WANT=20261015120000
LIST_WANT="20261023100000_video_limits_live.sql"
[ "$(node scripts/cloud-read.mjs docs/rollout/remote_head.sql |
     node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{try{process.stdout.write(String(JSON.parse(s)[0].head))}catch{}})")" = "$HEAD_WANT" ] &&
[ "$(npx supabase db push --linked --skip-vault --dry-run --output-format json |
     node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{try{process.stdout.write(JSON.parse(s).migrations.join(' '))}catch{}})")" = "$LIST_WANT" ] &&
npx supabase db push --linked --skip-vault
```

`db push`, запущенный агентом, подтверждения не спрашивает (CLAUDE.md). Застава — единственная
проверка, и она неотделима от push.

1. **Шаг 0 — `phone-1-2-0` (+ доки `launch-reset-1016`) в `main`.** Без него не пройдёт ни один push из

   Состояние `main` после шага собрано в репетиции: tsc обоих приложений — 0.
2. **Шаг 1 — видео** (приоритет владельца 1). Маленькая миграция: две функции `create or replace`, те
   же подписи и ACL, `lock_timeout 3s`. Плюс OTA №8.

     горничные сейчас получают число компании.
   - Миграция убирает саму возможность снова застрять, если поле кто-то заполнит. Поэтому видео
     первым: оно готово, мало и не зависит от остального.
3. **Шаг 2 — ручное время уборки:** ветки нет. Когда появится — §5, шаг 2.
4. **Шаг 3 — API.** Независим от базы знаний и отзывов. Его правило паритета задевает их, а не
   наоборот: идя раньше, API получает на своём слиянии только `release_push_token`. Нужны секрет,
   миграция, две новые функции и раздел панели.
5. **Шаг 4 — база знаний.** Слияние с API в настройках (секции `access` + `isAdmin`) отрепетировано.
   - Миграция — перенумеровать.

     правки видео (`3147c11`, `3c8df45`), и OTA из неё откатило бы видео.

   Всё выключено до слова владельца (`tasks_enabled`, задания крона `sync-reviews-daily` и
   `classify-reviews-daily` — неактивны).

## 6. Репетиция

### 6.1 Временная база

База `rehearsal_1028` в контейнере `supabase_db_azpvpzqkseluzbtlnlkb`, рядом с общим стендом.
Стенд не тронут, `db:reset` не запускался. Как собрана:
1. `create database … template template0 owner postgres`.
2. Схемы платформы — `pg_dump --schema-only` стенда без `public`, `raw`, `supabase_migrations`.
   - Вырезаны наши объекты в чужих схемах (2 политики `storage.objects`, 2 триггера `auth.users`),
     глобальное умолчание `postgres` для функций и `pg_cron`.
   - `pg_cron` живёт только в базе `postgres`; вместо него заглушка схемы `cron` с `job`,
     `job_run_details`, `schedule`, `unschedule`, `alter_job` теми же подписями.
3. Схема `public` — как её готовит образ (`init-scripts/00000000000000-initial-schema.sql`): `grant usage`
   и умолчания от `postgres` и `supabase_admin`.
4. Все 116 файлов каталога по порядку имён, каждый одной транзакцией от `postgres`. Строку
   `create extension pg_cron` заменяет заглушка.

Сверка с облаком по 112 общим миграциям — §1: тела функций, колонки и ACL совпали. Скрипт —
`docs/rollout/rehearsal-db-1028.mjs` (`create`, `suites`, `drop`; запускать из корня дерева, чей каталог
репетируется). Им же повторён весь SQL-прогон: те же 49 наборов, 1 красный, 2219 проверок. Базу
после репетиции удалили, в контейнере остались только прежние базы.

**Красная проверка и причина.** В `table_grants.sql` правило «no function that touches raw is callable
by a client role» ловит `public.review_run_status()`. Это definer-функция отзывов: она читает
`raw.review_runs` и отдаёт `authenticated` время последнего прогона для строки «обновлено» на экране.
Наружу уходят только времена своей компании и только менеджеру. Но правило 23.09 запрещает
клиенту любую дверь в `raw` без исключений. Ветка отзывов `test:rls` не запускала (её обзор:
«`table_grants.sql` упадёт… в этой ветке не запускать»). Варианты — §8, вопрос 1.
