## 0. Коротко

- **Hostaway отдаёт отзывы полностью, но только опросом.** `GET /v1/reviews`:
  оценка 0–10, оценки по категориям, публичный текст, приватный отзыв хозяину,
  ответ хозяина, `listingMapId` и `reservationId` у 100 % отзывов. Фильтры по
  типу, статусу и дате отправки проверены живыми запросами, до 500 строк за
  запрос. **Вебхука на отзыв нет** и фильтра «изменённые с» нет — раз в день
  забираем опубликованные с момента прошлой загрузки (1–2 запроса в день).
- **Поток у нас:** ≈ **410–480 опубликованных отзывов в месяц** (апрель–август
  2026) по 82 листингам, из них с текстом ≈ 340–440. Airbnb — ⅔ потока; у
  **40 % отзывов Airbnb есть приватный отзыв хозяину**, у Booking.com приватного
  нет вовсе, а 44 % его отзывов — одна оценка без текста. Оценки высокие:
  у Airbnb 76 % — 5 звёзд, у Booking.com медиана 9 из 10.
- **Проблем в отзывах немного, но они есть.** Грубая эвристика по словам в
  en/ru/cs/de нашла признаки поломки, безопасности, вредителей или проблем с
  доступом у **7,2 % отзывов с текстом — ≈ 20–37 в месяц** на 65 листингах;
  у 22 % из них признак только в приватном тексте, у 26 % — при высшей оценке.
  Треть текстов — на языках вне en/ru/cs/de (немецкий сам по себе — пятая
  часть), поэтому одних правил мало.
- **Модель стоит копейки.** При ≈ 450 отзывах в месяц классификация обходится в
  **$0,13–2,7 в месяц** (самые дешёвые модели — меньше доллара), догрузка года
  истории — $1,4–28. Выбор решают не деньги, а условия обработки данных и
  качество на размеченном наборе.
- **Решено (владелец, 2026-10-16, §7):**
  - гибрид: правила работают всегда и без передачи данных, а модель
    **Claude Haiku 5.5** по API Anthropic разбирает каждый текст, включая
    приватный, после удаления имён;
  - **вариант C**: на старте находки ждут подтверждения менеджера на экране
    «Отзывы», автомат включается по видам, когда накопится статистика;
  - задание технику дают только поломка, безопасность, вредители и доступ;
    уборка и расходники — только статистика на дашборде;
  - **цитату видит только менеджер**; технику и главному технику — краткая
    формулировка на их языке (en, cs, ru).

  Из рекомендаций плана остаются:
  - ежедневная загрузка — **pg_cron → Edge Function**, как все наши синки
    (Vercel Cron не годится: ключи Hostaway не должны покидать Edge Functions);
  - задание создаётся **тем же внутренним путём, что `report_problem`**, с
    меткой «из отзыва».
- **Порядок:**
  - До запуска сотрудников не делаем ничего.
  - **Шаг 0** — **после недели пилота** и после миграций дашборда. Это
    загрузка отзывов **без текстов и без имён** (оценки, категории, канал,
    даты, объект, бронь, флаги «есть текст») с историей за 12 месяцев.
    - Сразу даёт рейтинги на дашборд (К-8 «оценка чистоты из отзывов» сейчас
      «нет»).
    - Телефон и панель не трогает.
    - ≈ 1–1,5 нашего дня.
  - Тексты (шаг 2) и модель (шаг 4) — только после обновлённого уведомления
    для гостей (черновик — раздел 10).
- **Шаги 0–5, ≈ 10–13 наших дней**, после каждого можно остановиться
  (раздел 6). Ни одному шагу не нужна нативная сборка; телефон меняется только
  в шаге 1 (метка, OTA). Второй PMS — не раньше чем через месяц после запуска.

## 1. Hostaway: что отдаёт API отзывов

### 1.1 Эндпоинты и параметры

Источник — документация `api.hostaway.com/documentation` (исходники в GitHub
`Hostaway/api`, правка от 2026-10-09) и наши запросы. Где документация и живой
ответ расходятся, верен живой ответ.

| Что | Как | Проверено запросом |
|---|---|---|
| Список | `GET /v1/reviews` → `{status, result[], count, offset}` | да |
| Один отзыв | `GET /v1/reviews/{id}` | нет |
| Ответ хозяина | `POST /v1/reviews/{id}/respond` (только опубликованный отзыв гостя Airbnb, Booking.com, Vrbo; один раз) — **нам не нужен, запись не делаем** | — |
| Тип | `type=guest-to-host` / `host-to-guest` | **да**: 21 836 / 13 280 из 35 116 |
| Статус | `statuses[]=published` (и `awaiting`, `pending`, `scheduled`, `submitted`, `expired`) | **да** |
| Дата отправки | `submittedAtStart` / `submittedAtEnd` | **да**: с 01.10 — 172, совпало с нашим счётом |
| Даты выезда и проживания | `departureDateStart/End`, `stayDateStart/End` | нет |
| Листинг | только `listingMapIds[]` с квадратными скобками; **`listingMapId` без скобок молча игнорируется** и отдаёт все отзывы аккаунта | игнор — да; скобки — нет |
| Бронь, канал | `reservationId`, `channelReservationIds[]`, `channelIds[]` | нет |
| Оценка | `ratingMin` / `ratingMax` (0–10), `hasHostReply` | нет |
| Страница | `limit` (по умолчанию 100, **максимум 500** — на `limit=1000` пришло 500), `offset` | да |
| Порядок | `sortBy` (в том числе `submittedAt`), `sortOrder`. Документация: по умолчанию `desc`; **на деле без `sortBy` — по возрастанию id**, старые первыми | да |
| «Изменённые с» | **нет** ни фильтра, ни сортировки по `updatedOn` | — |
| Вебхук на отзыв | **нет**: единые вебхуки шлют только «бронь создана/изменена» и «новое сообщение» | — |
| Лимит | документация 2026: 200 запросов за 10 с на аккаунт и на IP; наш клиент держит 15 за 10 с — с запасом | — |

Загрузчик должен сверять ответ с запросом (например, что все `listingMapId` из
ответа — те, что просили).

### 1.3 Жизненный цикл и задержки

- **Строка отзыва появляется задолго до отзыва.** Hostaway заводит её при
  брони со статусом `awaiting`: у опубликованных `insertedOn` — медиана на
  19–24 дня **раньше** `submittedAt`. Поэтому «новый отзыв» — это
  `status = published` и `submittedAt`, а не новая строка и не рост `id`.
- Статусы: `awaiting` (ждём), `pending` (ждём канал), `scheduled` (авто-отзыв
  хозяина в очереди), `submitted` (Airbnb, двойное слепое окно — текст ещё не
  виден), `published` (читаем), `expired` (гость не оставил).
- В выборке из 7 500 последних строк отзывов гостей: опубликовано 3 218,
  истекло 2 539, `pending` 932, `awaiting` 808, `submitted` 3; скрыто 1 489
  (почти все — истёкшие, опубликованных скрытых 5).
- Задержка «выезд → отзыв» (опубликованные):

| Канал | Медиана | p90 | Максимум |
|---|---|---|---|
| Airbnb | 1 день | 4 дня | 14 дней (окно Airbnb) |
| Booking.com | 1 день | 27 дней | 88 дней (Booking принимает ≈ 3 месяца) |

  Значит, задание из отзыва почти всегда приходит **после** выезда и часто уже
  после следующего заезда — горничная или следующий гость могли заметить
  поломку раньше (это учитывает проверка дублей, раздел 4.7).

### 2.3 Как устроена наша интеграция Hostaway сейчас

- **Функции.** `sync-listings` (ночью и по кнопке менеджера), `sync-reservations`
  (ночная сверка: выезды −7…+90 дней), `hostaway-webhook` (приём, Basic Auth,
  всё пишет в журнал), `process-webhook-events` (каждые 2 минуты, обрабатывает
  только брони, тело вебхука не доверяет — перечитывает бронь из API).
- **Общие модули** `_shared/`: `hostaway.ts` — клиент (выпуск токена на каждый
  запуск, темп 15 запросов за 10 с, повтор 429 и 5xx, `listAll` по
  offset/limit), `env.ts`, нормализаторы `listing.ts` и `reservation.ts`,
  `reservation-sync.ts`.
- **SQL.** `sync_hostaway_listings`, `sync_hostaway_reservations` (definer,
  только `service_role`); сырые `raw.hostaway_listings`,
  `raw.hostaway_reservations`; журнал вебхуков `raw.webhook_events` с полем
  `source default 'hostaway'` — единственное место, где источник уже назван.
- **Расписание.** pg_cron → `invoke_edge_function()` (адрес и ключ из Vault,
  `net.http_post`, «выстрелил и забыл»): листинги 03:00, брони 03:15 UTC.
  Журнала запусков синков и оповещений о сбое нет (F13 открыт); есть только
  `raw.generator_runs` у генератора уборок.
- **PMS-независимого слоя нет.** Первичные ключи `properties.id` и
  `reservations.id` — это id Hostaway; комнаты — id юнита со сдвигом 10¹²;
  `channel_id` — нумерация Hostaway; переменные `HOSTAWAY_*` общие, не на
  компанию. Миграция `20260905094000_tenant_host_id.sql` прямо пишет, что до
  второй учётной записи нужна «фаза B» (суррогатные ключи и
  `unique (host_id, external_id)`) — это F25.
- **Что выделить для второго PMS** (только когда он реально появится): клиент
  → интерфейс провайдера; учётные данные → на компанию; нормализаторы → по
  провайдеру; имена `sync_hostaway_*` и `raw.hostaway_*`; внешние id → фаза B.
  **Для отзывов это не нужно сразу**: таблица отзывов с первого дня держит
  `source` + `external_id`, а адаптер Hostaway — первый из адаптеров.
- Второй PMS противоречит строке «вне объёма» в ROADMAP.
  - Решение владельца (§7, п. 8): **не раньше чем через месяц после запуска**.
  - До тех пор строка остаётся.
  - Условие подключения — фаза B F25.
  - Какой PMS — пока не назван. От этого зависит, будут ли отзывы: у Lodgify,
    Smoobu и Cloudbeds их в API нет (2.1).

## 3. Как находить проблемы

### 3.1 Три варианта

| | (a) Правила | (b) Модель | (c) Гибрид |
|---|---|---|---|
| Как | словарь корней на языках, отрицание рядом | каждый текст после удаления имён → модель → JSON | правила всегда; модель — для каждого текста; расхождение — на подтверждение |
| Языки | только те, на которые написан словарь (≈ 65 % наших текстов) | все | все |
| Отрицание, сарказм, «уже починили» | плохо | хорошо | хорошо |
| Краткая формулировка на en/cs/ru | нет (только вид) | да | да |
| Передача данных наружу | нет | да (обработчик по договору) | да |
| Цена | 0 | ≈ $0,13–2,7 в месяц | то же |
| Если сервис модели недоступен | работает | стоит | правила продолжают, модель догоняет |
| Мерить качество | по решениям менеджера | то же | то же + доля расхождений |

**Решено — (c)** (владелец, 16.10, §7, п. 5).

- **Правила остаются первым слоем:**
  - бесплатно и без передачи данных;
  - ловят очевидное и безопасность;
  - дают базовую линию и работают без модели.
- **Модель получает каждый отзыв с текстом, включая приватный**, а не только
  «подозрительные». Почему:
  - четверть находок — при высшей оценке;
  - пятая часть — только в приватном тексте;
  - треть текстов — на языках вне словаря;
  - а цена всего потока — меньше чашки кофе в месяц.
- **Условия:**
  - имена вырезаются до отправки (3.6);
  - модель включается только после публикации обновлённого уведомления для
    гостей (раздел 10).

### 3.4 Что возвращает классификация

Модель зовётся с требованием структурированного ответа (инструмент или
JSON-схема); ответ проверяет zod в Edge Function, неверный — в журнал, отзыв
повторяется в следующий запуск.

```ts
// набросок контракта, не код
type ReviewAnalysis = {
  language: string;                 // ISO-код языка текста
  findings: Array<{
    kind: 'repair' | 'safety' | 'pests' | 'access'          // задание технику
        | 'cleaning' | 'supplies'                            // уборка и расходники: только статистика (16.10)
        | 'noise' | 'neighbourhood' | 'wish' | 'other';      // без задания, в статистику
    subject: 'hot_water' | 'heating' | 'air_conditioning' | 'plumbing_leak'
           | 'drain_toilet' | 'electric' | 'appliance' | 'internet_tv'
           | 'lock_door' | 'window_blind' | 'furniture' | 'mould_damp' | 'other';
    urgency: 'low' | 'normal' | 'high';
    still_relevant: 'likely' | 'fixed_during_stay' | 'unclear';
    summary: { en: string; cs: string; ru: string };   // ≤ 120 знаков, без имён и цитат; три языка одним вызовом, без de (16.10)
    evidence: string;               // ≤ 200 знаков, ДОСЛОВНО из присланного (уже обезличенного) текста
    evidence_source: 'public' | 'private' | 'category_comment';
    confidence: number;             // 0–1
  }>;
};
```

- **Вид → действие** решает наша таблица настроек, не модель. Решение
  владельца (§7, п. 2):
  - `repair`, `safety`, `pests`, `access` → задание;
  - `cleaning`, `supplies` → **пока только статистика на дашборде** (О-15);
    заметка к следующей уборке (F20) — возможна позже, отдельным решением;
  - `noise`, `neighbourhood`, `wish`, `other` → только статистика.
- **Срочность** — подсказка модели, правило поверх: `safety` → high; отопление
  и горячая вода в холодный сезон, протечка, замок → high; `still_relevant =
  fixed_during_stay` → без задания, только в статистику.
- **Проверки ответа:** `evidence` должен быть подстрокой присланного текста
  (иначе находка отбрасывается как выдумка); в `summary` не должно быть ни
  одного токена из списка имён (3.6); `confidence` ниже порога — находка
  хранится как «отброшена», задания нет.
- В модель уходят:
  - публичный текст (у Booking — части «понравилось» и «не понравилось»);
  - приватный (решение п. 5);
  - комментарии к категориям и оценки по категориям;
  - канал и месяц выезда;
  - **вид объекта** (квартира или комната).

  Всё — после удаления имён. Не уходят адрес, название объекта, имя гостя и
  данные брони.

### 3.5 Трудные случаи

- **Многоязычие.** Модель читает любой язык и отвечает на трёх; языки, где
  правил нет (fr, pl, es, it, nl…), — треть наших текстов.
- **Отрицание и сарказм** («ничего не сломалось», «отопление „работало“») —
  сила модели; правила здесь дают ложные находки, поэтому в автомате правило
  без согласия модели задания не создаёт.
- **Жалоба не на объект** — соседи, улица, стройка, район, парковка, погода:
  вид `noise` или `neighbourhood`, без задания.
- **Пожелание вместо поломки** («не хватало посудомойки», «хорошо бы штору
  поплотнее»): вид `wish` — в отдельный список владельцу, не технику.
- **Уже починили при госте** («вечером не было воды, утром всё сделали»):
  `still_relevant = fixed_during_stay` — без задания.
- **Один отзыв — несколько проблем:** несколько находок, у каждой своя проверка
  дублей.
- **Листинг-здание** (один листинг на 286 отзывов за восемь месяцев): если у
  брони есть `reservation_units`, задание ставится на комнату, иначе — на
  здание с пометкой «комната не известна».
- **Коды и пароли в тексте** (гость повторил код двери): удаляются вместе с
  именами (3.6).

### 3.6 Как убирать имена до отправки

В Edge Function, в памяти, до любого внешнего вызова; результат же хранится у
нас вместо исходного текста (шаг 2).

1. **Известные имена** этого отзыва: `guestName`, `reviewerName` → по словам;
   совпадение без учёта регистра и диакритики, с хвостами склонений для cs и ru
   (основа от 4 букв) → `[GUEST]`.
2. **Имена сотрудников** компании (`profiles`, имя и фамилия) — в отзывах часто
   хвалят или ругают горничную по имени → `[STAFF]`.
3. **Названия объекта** (в 15 названиях есть коды) → `[PROPERTY]`.
4. **Шаблоны:** почта, телефон, ссылки, @-имена, последовательности из 4+ цифр
   → `[EMAIL]`, `[PHONE]`, `[URL]`, `[NUMBER]`.
5. **Слова с заглавной после обращений** («спасибо X», «thanks to X», «děkujeme
   X», «danke X») → `[NAME]`.
6. Инструкция модели: имён не выводить; проверка ответа (3.4) отбрасывает
   находку, в которой осталось имя из пунктов 1–3.

Остаточный риск — посторонние имена (сосед, таксист). Он приемлем: получатель —
обработчик по договору, без обучения на данных, и мы шлём только текст отзыва,
без имени гостя, брони и адреса.

### 3.7 Что сказать в политике конфиденциальности

Сегодня `docs/privacy-policy-draft.md` написан для сотрудников:
- гостевых данных в нём нет;
- Hostaway в списке обработчиков не значится;
- пункт 10 «только для владельца» уже говорит, что гостям нужно отдельное
  уведомление.

**Черновик уведомления для гостей об отзывах и оценках — раздел 10** (три
языка, где его показывать, сверка с черновиком политики). Коротко, что в нём:

- **Что берём:** оценки и отзыв, оставленные на площадке бронирования, в том
  числе отзыв, адресованный только хозяину; получаем через Hostaway.
- **Зачем:** находить и устранять неисправности в квартирах; сводная
  статистика качества. Основание — законный интерес, ст. 6(1)(f); короткая
  оценка законного интереса — в записях компании.
- **Кто ещё обрабатывает:** Anthropic (решение п. 5):
  - получает текст без имён, по договору обработки;
  - не обучает на нём модели;
  - хранит до 30 дней.
- **Сколько храним:** тексты отзывов — 18 месяцев (решение п. 7). Срок
  хранения оценок — вопрос владельцу (4.12).
- **Права:** доступ, исправление, удаление, ограничение, возражение — контакт
  компании; жалоба — в ÚOOÚ.
- **В политику сотрудников** — одна строка: их имена из отзывов гостей
  заменяются до хранения и до передачи модели, и по отзывам система не строит
  оценок сотрудников (дашборд «Персонал — нейтрально»). Текст строки — в
  10.4.

Текст — предложение, не юридическая консультация; окончательная формулировка —
за владельцем.

### 3.8 Как мерить качество

- **Метрики:** точность (доля находок, которые менеджер принял), полнота (доля
  реальных проблем, которые нашлись), ложных заданий на 100 отзывов, пропусков
  на 100 отзывов — по видам и по языкам.
- **Размеченный набор ≈ 300 отзывов** за последние полгода: все совпадения
  правил (≈ 150), 100 случайных ниже высшей оценки, 50 случайных с высшей.
  Размечает менеджер **в нашей панели** (режим разметки на экране «Отзывы»):
  есть ли проблема, вид, нужна ли работа техника. Разметка — строки нашей
  таблицы.
- **Безопасно:** набор не выгружается — ни в репозиторий, ни в тесты, ни в
  фикстуры, ни в разговор с ИИ-помощником разработки. Тесты кода — только на
  выдуманных фразах на четырёх языках. Прогон Claude Haiku 5.5 по набору —
  это уже обработка, поэтому только после договора и уведомления (3.3, 10).
- **Цели для автомата:** точность ≥ 0,9 по виду за последние 60 дней при ≥ 50
  решениях; полнота ≥ 0,8 на наборе.
- **Дальше — само собой:** в режиме подтверждения каждое решение менеджера —
  новая метка (точность считается постоянно); полноту раз в месяц проверяет
  выборка из 30 отзывов «без находок».

## 4. Архитектура

### 4.1 Где запускать ежедневную задачу

| | pg_cron → Edge Function | Только Edge Function | Vercel Cron (Pro) |
|---|---|---|---|
| Расписание | cron из 5 полей, UTC; уже так работают все наши синки | своего планировщика нет — это тот же pg_cron | `vercel.json`, UTC, от 1 минуты |
| Секреты | Vault (адрес и ключ функции) + секреты функций — **ключи Hostaway и модели уже там** | то же | переменные Vercel — **ключи Hostaway и сервисный ключ пришлось бы вынести в Vercel**, против правила «серверные секреты только в Edge Functions» |
| Повтор при сбое | автоматического нет; повтор даёт сама конструкция: необработанное остаётся в очереди до следующего запуска | то же | «Vercel не повторяет упавший cron»; возможен пропуск и двойной запуск |
| Журнал запусков | `cron.job_run_details` видит только отправку; своя таблица запусков (как `raw.generator_runs`); логи функций — 1 день Free, 7 дней Pro | то же | логи 1 день на Pro (30 — за доплату) |
| Длительность | функция: 150 с на Free, 400 с на платном, 2 с CPU (ожидание сети не считается) | то же | 300 с по умолчанию, до 800 |
| Цена | в тарифе | в тарифе | в тарифе Pro панели |

**Рекомендация — pg_cron → Edge Function** с собственной таблицей запусков:
один путь со всеми синками, секреты не покидают Supabase, повтор — за счёт
состояния в таблицах, а не планировщика. Суточный объём (1–2 запроса к
Hostaway и ≈ 15 вызовов модели) укладывается в 150 с даже на Free; догрузка
истории идёт порциями по запуску.

### 4.4 Поля в заданиях

```sql
create type public.problem_source as enum ('staff', 'review');
alter table public.problems
  add column source            public.problem_source not null default 'staff',
  add column review_finding_id uuid unique references public.review_findings(id) on delete set null,
  add column category          public.problem_category,   -- общий с дашбордом (dashboard-metrics §3 п. 3)
  add column title_i18n        jsonb,                      -- перевод заголовка, как x / x_i18n
  alter column reported_by drop not null,
  add constraint problems_reporter_or_review check (reported_by is not null or source = 'review');
```

- **Источник** — для метки и фильтра; **ссылка на находку** — через неё отзыв,
  уверенность и фрагмент (в задание уверенность не копируем — она читается
  встраиванием); **категория** — нужна проверке дублей и уже предложена
  дашбордом (срез «что ломается чаще», З-11).
- **`reported_by`** сегодня `not null` — системного автора у заданий нет (у уборок
  есть: `tasks.created_by is null` — значит сервер). Делаем так же: у задания из
  отзыва автор null, а кто принял — в находке и в журнале `problem_events`
  (ключ `problems.history.system` уже есть).
- **Заголовок** пишет модель: `title` — на языке компании, `title_i18n` — en, cs,
  ru; читается перевод на языке сотрудника, иначе `title`. Это тот же шаблон,
  что у названий, которые вводит менеджер. У обычных заданий `title_i18n` — null.
- Телефон и панель читают новые колонки через строки `select` → обновить
  `READERS` в тестах `postgrest-select` и `postgrest-embeds` и схемы
  `readCached` с `.default` (правило CLAUDE.md, `buster` не трогать).

### 4.5 Создание задания тем же путём

Кнопка «Новое задание» в панели (`apps/web/src/features/problems/problems-view.tsx`)
→ `NewProblemDialog` → `report_problem` (`20260908130000_problems.sql:251`). Телефон
зовёт тот же RPC. Но **`report_problem` нельзя вызвать с сервера**: автор и
компания берутся из `auth.uid()`, под `service_role` это null.

- Тело `report_problem` выносится во внутреннюю функцию (без грантов) с явными
  компанией, автором, источником и находкой; та же проверка текста
  (`validate_problem_text`), тот же выбор объекта (`resolve_report_property`),
  та же вставка в `problems`. `report_problem` остаётся с прежней подписью и
  зовёт её.
- `create_problem_from_finding(p_finding_id)` — definer, только `service_role`
  (автомат) и `accept_review_finding(p_finding_id, …)` — менеджер (подтверждение).
- Вставка в ту же таблицу значит, что срабатывают **те же триггеры**: журнал
  `problem_events`, push главным техникам (`push_on_problem_reported`), зеркало
  статуса. Новых путей в обход нет.
- Ошибки — по правилу «текст не на сервере»: английский `message`, ключ
  `serverErrors.reviewFinding*` в `hint`, параметры в `detail`.

### 4.6 Идемпотентность

- Отзыв: `unique (host_id, source, external_id)`, повторная загрузка — upsert.
- Находка: детерминированный id (uuid v5 от отзыва, вида и предмета) и
  `unique (review_id, kind, subject)` — повторный разбор той же версией
  ничего не плодит.
- Задание: `problems.review_finding_id unique` и id задания = uuid v5 от id
  находки; RPC на повтор возвращает ту же строку — тот же приём, что у
  `report_problem` с id, придуманным телефоном.
- Новая версия правил или модели (`analysed_version`) разбирает отзыв заново,
  но не создаёт второго задания: находка с тем же видом и предметом уже
  связана.
- **История не превращается в задания.** Догрузка прошлых отзывов
  (шаг 0) идёт с отметкой «разобран без заданий»; задания — только по отзывам,
  пришедшим после включения шага 3 или 4.

### 4.7 Дубли

Перед созданием в той же транзакции:

1. Открытое задание (`open`, `assigned`, `in_progress`, не в архиве) на том же
   объекте — или на его здании и комнатах — с той же категорией → находка
   связывается с ним (`duplicate`), в журнал задания — событие «упомянуто в
   ещё одном отзыве», нового задания нет.
2. То же, решённое **после** выезда гостя → `already_fixed`, задания нет
   (поломку уже нашли горничная или техник).
3. Две находки одного вида в одном запуске (два гостя подряд) → вторая — дубль
   первой.
4. Иначе — новое задание (или ожидание подтверждения, 4.9).

### 4.8 Отзыв задания и обратная связь

- Кнопка **«Ложное срабатывание»** — на карточке задания с источником «отзыв»
  и в списке находок. `reject_review_finding(p_finding_id, p_reason)`:
  находка → `rejected` с причиной; если задание создано этой находкой и
  работа не начата — отмена и перенос в архив (архив у нас и есть корзина
  «тест, дубль, шутка»); если техник уже начал — отказ с ключом ошибки,
  менеджер решает вручную.
- Причины — коды, не текст: ложная находка, не про объект, уже починено,
  дубль, не стоит задания.
- Менеджер может поправить вид и предмет — это та же метка для разметки.
- Решения копят набор (3.8): точность по видам видна рядом с переключателем
  автомата; отклонённые примеры — материал для правки инструкции модели
  (версия `prompt-vN` в `detector`).

### 4.9 Варианты A, B, C

| | A — сразу в пул | B — ждёт подтверждения | C — B, потом автомат по видам |
|---|---|---|---|
| Ложное задание | уходит в пул и пушит главным техникам, ночью тоже | не доходит до техников | на старте как B; в автомате — только виды с доказанной точностью |
| Нагрузка на менеджера | разбирать ложные уже в пуле | ≈ 1 находка в день, ≈ минута | так же, потом меньше |
| Скорость | мгновенно | до решения менеджера | как B, потом мгновенно |
| Сложность | меньше всего | + список находок и две кнопки | + переключатель по виду и цифры точности |

**Решено — C** (владелец, 16.10, §7, п. 1). Почему:

- Сегодня в облаке **10 заданий за всё время**, а находок будет 20–37 в месяц.
  В режиме A они займут большую часть пула, и каждая разбудит главного
  техника push-уведомлением (триггер срабатывает на вставку).
- Отзыв приходит через 1–27 дней после выезда — проблему часто уже нашли
  или починили. Менеджер это знает, модель — нет.
- Точность заранее неизвестна: правила грубые, а модель ещё не мерили на
  наших данных.
- Автомат включается **по виду** (например, сначала «безопасность» и
  «протечка»), когда за 60 дней ≥ 50 решений и ≥ 90 % принятых. Цифры видны
  рядом с переключателем; выключить можно в один щелчок.

### 4.10 Экран «Отзывы» в панели

Раздел для менеджера и админа. Главному технику — нет: ему достаточно заданий.
Обезличенный фрагмент отзыва виден **только здесь** (решение п. 3).

- **Обзор.** Средняя оценка 0–10 по объектам и по месяцам, по каналам; средние
  по категориям (чистота, заезд, точность, удобства); доля низких оценок;
  объекты без отзывов. Фильтры: период, объект или здание, канал, оценка.
- **Найдено.** Находки, ждущие решения, сверху срочные. У каждой: вид, предмет,
  формулировка на языке менеджера, фрагмент (обезличенный), уверенность,
  канал, дата выезда, объект, кнопки «Создать задание» (с правкой заголовка и
  срочности) и «Ложное срабатывание»; вкладки «Принятые», «Отклонённые»,
  «Дубли».
- **Все отзывы.** Список с оценкой, каналом, объектом, датой; текст
  (обезличенный) раскрывается по нажатию, приватный помечен «только хозяину»;
  кнопка «Создать задание из отзыва» вручную — работает и без модели.
- **Настройки:**
  - включено ли;
  - режим по видам (подтверждение или автомат) с цифрами точности;
  - какие виды дают задание: по решению 16.10 — поломка, безопасность,
    вредители, доступ; уборка и расходники — статистика;
  - время последней удачной загрузки и предупреждение, если её не было 48 ч.

### 4.11 Метка в панели и в телефоне

- **Метка** — ключ в общих `locales` во всех трёх языках, например
  `problems.source.review`: en «From a guest review», cs «Z recenze hosta»,
  ru «Из отзыва гостя». По умолчанию — английский (решения 14.10 и 16.10,
  п. 4); немецкого нет.
- **Панель:** значок рядом со срочностью на карточке доски, в таблице и в
  шапке задания; строка как «Найдено во время уборки» (`fromTask`): «Из отзыва
  гостя · Airbnb · выезд 12.10 · 3★» со ссылкой на отзыв на экране «Отзывы»;
  фильтр «Источник».
- **Телефон** (только JS, OTA): тот же значок на карточке и в задании.
- **Цитата технику и главному технику не показывается (решение п. 3).**
  - Технику нужно, что чинить, а не слова гостя: краткая формулировка модели
    на его языке, вид, предмет и дата выезда.
  - Цитата — это персональные данные и иногда эмоции или оскорбления; через
    отзыв можно узнать гостя.
  - Обезличенный фрагмент видят только менеджер и админ на экране «Отзывы».
- Push главным техникам — существующий `problem_new`, без новых видов. Новый
  вид push менеджеру «найдено в отзыве» (например, для `safety`) — потом,
  отдельным шагом: это правка `send-push` и копии ключей `push.*`.

### 4.12 Хранение, права, наблюдение

- **Хранение (F24):**
  - **Тексты отзывов и фрагменты находок — 18 месяцев** (решение п. 7), затем
    обнуляются ночной задачей. Задача входит в шаг 2: обещание уведомления
    должно работать с первого сохранённого текста.
  - **Оценки, категории, виды находок и решения** — статистика.
  - **Предложение:** через те же 18 месяцев снимать у отзыва связь с гостем:
    `reservation_id`, `external_reservation_id` и `external_id`. Остаются
    объект, месяц, канал и оценки. Тогда уведомление может честно сказать
    «дальше — только обезличенная статистика».
  - Хранить связь бессрочно — тоже вариант, но тогда так и написать в
    уведомлении. Это решает владелец (10.2, п. 6).
- **Права:** таблицы отзывов и находок — только менеджер и админ; техник видит
  задание с формулировкой, но не отзыв.
- **Наблюдение:** `raw.review_runs` + время последней удачной загрузки на
  экране; мониторинг и оповещения — вместе с F13.
- **Токены Hostaway:** наш клиент выпускает новый токен на каждый запуск
  (открытая проблема F13); ещё один запуск в сутки картину не меняет.

## 6. Что заложить сейчас, шаги, риски

### 6.1 Минимальная схема и шаг 0

**Шаг 0 — только загрузка, без текстов и без модели.** Таблица
`guest_reviews` **без текстовых колонок** (оценки, категории, канал, даты,
объект, бронь, флаги «есть текст», «есть приватный», «есть ответ»),
`sync_guest_reviews`, функция `sync-reviews`, pg_cron в 03:25 UTC,
`raw.review_runs`, догрузка 12 месяцев (решение п. 6: ≈ 12–15 запросов по
500, один раз, порциями, с паузами). Имя гостя и тексты не сохраняются нигде.
**Когда — после недели пилота** (решение п. 6), до запуска — нет.

- Даёт сразу: О-1…О-7 и О-14, К-8 — рейтинги на дашборд.
- Не трогает: телефон, панель, `problems`, `report_problem`, `_shared/`.
- Персональных данных — минимум: оценка, привязанная к брони (псевдоним), без
  имени и текста.
- Уведомление гостям обновляется перед шагом 2 (решение п. 7), и его текст
  (раздел 10) уже покрывает оценки. Но по ст. 14(3)(a) GDPR гостю сообщают в
  разумный срок, не позже месяца после получения данных. Если шаг 2 отстанет
  от шага 0 больше чем на месяц, уведомление лучше опубликовать раньше.
- Порядок выката: в облаке ждут миграции дашборда (голова 20261011100000) —
  миграция шага 0 едет после них или в одном окне с ними, с сухим прогоном по
  правилу «`db push` неотделим от проверки».
- Чистка перед запуском (`docs/launch-reset.md`) новую таблицу не задевает;
  сверить при её выполнении.

### 6.2 Шаги

| Шаг | Что | Объём (наших дней) | Зависит от | Что выкатывается |
|---|---|---|---|---|
| **0** | Загрузка отзывов без текстов, история 12 месяцев (6.1) | ≈ 1–1,5 | неделя пилота, миграции дашборда в облаке | миграция, новая функция, cron |

| **5** | Дашборд: раздел «Отзывы» (раздел 5), с уборкой и расходниками (О-15) | ≈ 1–1,5 | 0 (и 1, 3 — для заданий и О-15) | функции фактов, панель |

Итого ≈ **10–13 наших дней**: в шаге 4 больше нет сравнения поставщиков. Остановиться можно после любого шага:

- после **0** — рейтинги;
- после **1** — источник и категория у заданий (полезно и без отзывов);
- после **2** — ручная работа с отзывами;
- после **3** — полуавтомат без внешней передачи данных.

Второй PMS — отдельная дорожка, не раньше чем через месяц после запуска
(решение п. 8): адаптер отзывов ≈ 1–2 дня, но только после фазы B F25. Нативная сборка не нужна ни одному шагу.

### 6.3 Риски

- **Тихий фильтр Hostaway.** Неверное имя параметра снимает фильтр без ошибки
  (`listingMapId`); порядок по умолчанию не совпадает с документацией. Лекарство —
  сверка ответа с запросом и тест на записанных ответах.
- **Поздние отзывы.** Booking.com принимает отзыв до ≈ 3 месяцев; окно опроса
  по `submittedAt` с запасом, еженедельная сверка 100 дней.
- **Ложные задания** — шум в пуле и push ночью. Лекарство — режим подтверждения
  (C) и точность по видам.
- **Задания по старым отзывам.** Год истории дал бы ≈ 200–300 находок о давно
  починенном. Лекарство — догрузка без заданий (4.6).
- **Персональные данные:** новая категория (тексты гостей, имена сотрудников в
  них), новый обработчик (поставщик модели). Лекарство — тексты только с
  шага 2 и после уведомления, удаление имён, ретенция 18 месяцев, договор.
- **Выдумки модели и ошибки перевода.** Лекарство — фрагмент обязан быть
  подстрокой, режим подтверждения, версия инструкции в каждой находке.
- **Расходы.** Ошибка в цикле может слать один отзыв много раз. Лекарство —
  предел вызовов за запуск и за сутки, лимит расходов в консоли поставщика.
- **Зависимость от полей Hostaway.** `reviewCategory` в документации не описан
  (мы видели `category`, `rating`, `comment`); схема может поменяться — zod на
  входе, сбой в журнал.
- **Правка `report_problem`** — центральный RPC телефона и панели. Лекарство —
  подпись не меняется, тело переезжает во внутреннюю функцию, тесты
  `problems.sql` гоняются до и после.
- **Листинг-здание.** Задание на здание без комнаты; уточнение через
  `reservation_units`.

### 6.4 Чего не делать до запуска сотрудников

- Не включать создание заданий из отзывов, ни в каком режиме: пул и push
  главным техникам в первые недели должны показывать работу людей.
- Не подключать модель и не отправлять наружу ни одного отзыва до договора и
  уведомления гостям.
- Не трогать `problems`, `report_problem` и строки `select` телефона в окне
  запуска: это OTA и риск для главного сценария горничной и техника.
- Не хранить тексты отзывов до шага 2.
- Не заводить второй PMS и не начинать фазу B ради отзывов (решение п. 8 — не
  раньше чем через месяц после запуска).
- **Шаг 0 — тоже нет:** по решению п. 6 он идёт после недели пилота, в очереди
  после миграций дашборда.

1. **Режим — C.**

3. **Цитату видит только менеджер** — обезличенный фрагмент на экране «Отзывы».

     по-немецки.
5. **Модель — Claude Haiku 5.5 по API Anthropic.**
   - Имена вырезаются до отправки (3.6).
   - Приватный отзыв хозяину **отправляется**.
   - Модель включается только после публикации обновлённого уведомления для
     гостей (раздел 10).
   - Сравнения поставщиков в шаге 4 нет — только замер Haiku на размеченном
     наборе (3.8). Запасной — Sonnet 5.5 того же поставщика, по слову
     владельца (3.2).
6. **Шаг 0 — после недели пилота**, история — **12 месяцев**.
   - ≈ 12–15 запросов по 500, один раз, порциями, с паузами.
   - До запуска сотрудников не делается ничего.
   - Миграция шага 0 по-прежнему едет после миграций дашборда.
7. **Тексты хранятся 18 месяцев**, затем обнуляются ночной задачей (4.12).

   записи текста. Черновик — раздел 10.
8. **Второй PMS — не раньше чем через месяц после запуска.**
   - До того строка «вне объёма» в ROADMAP остаётся.
   - Подключение упирается в F25 (фаза B).
   - Таблица отзывов с первого дня держит `source` + `external_id`.
