# Сигналы гостей — проектный документ

2026-10-31, ветка `guest-signals-design-1031` от `origin/main` (`8087f14`). Только исследование и
документ: кода механизма, миграций, деплоев и записей в облако и Hostaway нет. Тексты гостей не
печатались и не сохранялись: ответы облака и Hostaway шли через конвейер в локальный счётчик, который
выводил только числа и имена полей (§11).

**Сигнал гостя** — то, что гость сам сообщил о квартире через PMS: отзыв после выезда или
сообщение в переписке (чат Hostaway). Механизм находит в сигналах поломки и превращает их в задания
для техника. Отзывы уже спроектированы и написаны (`docs/reviews-to-tasks.md`, ветки
`reviews-to-tasks-1017` и `integration-rehearsal-1030`, миграция `20261030110000` ещё не в облаке);
этот документ делает из них общее ядро и добавляет второй вид сигнала — сообщения.

## 0. Коротко

- **Ядро уже наполовину общее.** Ключ по HMAC, нейтральная строка, правила, обезличивание, очередь
  кандидатов, режимы «на одобрение» и «сразу», журнал и сроки хранения в отзывах не знают Hostaway.
  Hostaway протекает в пяти местах: значение `review_source = 'hostaway'`, id листинга, комнаты и
  брони Hostaway как наши первичные ключи, `hostaway_unit_id` в поиске «семьи» объекта, жёсткий
  `SOURCE = "hostaway"` в функциях и обязательный второй запрос за бронью (§2).
- **Обобщать нужно сейчас, до выката шага 5.** Ключ HMAC, уникальные ключи и колонки, которые читает
  телефон, после выката меняются дорого. Шаг 5 всё равно пересобирается после 4e (техники видят всю
  базу знаний), так что окно бесплатное. Правки миграции — §2.4.
- **Объём сообщений небольшой** (30 дней, 1–31.10): 136 сообщений гостей и 68 разговоров в сутки;
  42 % — от дня заезда до дня выезда. Признак поломки по простым правилам — у 2,5–3,2 % сообщений:
  **3,2–3,9 кандидата в сутки**, в 90 % дней не больше 7–9; во время проживания — 2,5–3,0 (§4).
- **Модель стоит копейки и здесь:** Haiku 5.5 на все сообщения проживания — около $0,4 в месяц, на все
  сообщения вообще — около $1 (цены 16.10, сверить). Решают приватность и ложные срабатывания, не
  деньги (§8.4).
- **Текст переписки не хранится.** Вебхук кладёт только ключи и время; текст перечитывается из PMS в
  момент разбора, обезличивается, проходит правила и модель в памяти функции и забывается. Хранятся
  вид, предмет, срочность, нейтральное резюме и ссылка на разговор в PMS — у менеджера (§5).
- **Попутная находка:** сегодня `raw.webhook_events` уже держит тела всех сообщений гостей 30 дней
  (4 116 строк, никто их не читает). Вырезать тело при приёме можно раньше всего остального (§5.6,
  этап 2).
- **Реальное время:** вебхук приходит за 7 с (p90 8 с); склейка пачки сообщений — 5 минут тишины
  в разговоре; срочное (доступ, вода, газ, протечка, электричество) — без ожидания. От сообщения до
  карточки менеджера — около 7 минут, срочное — 2–3 минуты (§6). Сообщения — новая ветка в нынешнем
  диспетчере вебхуков, не вторая функция: он забирает все ожидающие события (§3.3).
- **Решения владельца приняты 31.10** — §10; открытое, прежде всего правовое основание (нужно мнение
  юриста), — §10.1. Этап 2 (приём без тела сообщения) — ветка `guest-signals-intake-1031`.

**Где протекает Hostaway:**

1. `review_source` с единственным значением `'hostaway'` и `SOURCE = "hostaway"` в ОБЩ/db.ts и
   `sync-reviews/index.ts`.
2. `properties.id` — это id листинга Hostaway, `reservations.id` — id брони Hostaway, комната — это
   10¹² + `listingUnitId` (`property_id_for_unit`). Адаптер отдаёт ядру `listing_id`, `room_id`,
   `reservation_id` уже нашими ключами — значит, знает схему id Hostaway; второй PMS так не сможет.
3. `review_place_family` ищет комнаты через `p.hostaway_unit_id` (МИГ 1160), панель встраивает
   `properties(name, hostaway_unit_id, …)`. Проверено в облаке: у всех 31 комнат заданы и `parent_id`, и
   `hostaway_unit_id`, у 83 прочих объектов — ни то, ни другое; значит, `parent_id` один различает
   комнату, и `hostaway_unit_id` из ядра уходит без потерь.
4. Обязательный `bookingOf`: имена гостя и комната приходят вторым запросом — это свойство Hostaway,
   не каждого PMS.
5. 404 брони распознаётся регулярным выражением по тексту ошибки клиента (`/\bHTTP 404\b/`).
6. Окна опроса (водораздел − 3 дня, воскресенье — 100 дней, первый раз — 365) — форма «нет вебхука и
   нет modified-since» у отзывов Hostaway.

### 2.2 Ядро и адаптер

```
            ┌──────────── адаптер PMS (знает PMS) ────────────┐
вебхук PMS ─┤ parseWebhook → NeutralMessageEvent               │
опрос PMS  ─┤ listActiveConversations / fetchConversation / fetchReviews    ├─► нейтральные записи
            │ namesOf (в памяти), conversationUrl, capabilities       │
            └──────────────────────────────────────────────────┘
                                   │
            ┌──────────── ядро (не знает PMS) ─────────────────┐
            │ guest_signals: ключи, место, бронь, фаза, время  │
            │ разбор: обезличивание → правила → модель          │
            │ signal_findings → решение → задание (problems)   │
            │ журнал, сроки, обратная связь, режимы, права      │
            └──────────────────────────────────────────────────┘
```

**Нейтральные записи** (что адаптер отдаёт ядру; все внешние id — строки):

```ts
type Provider = 'hostaway' | 'fake';              // enum signal_provider; новый PMS — новое значение
type SignalKind = 'review' | 'message';
type SignalChannel = 'airbnb' | 'booking' | 'vrbo' | 'direct' | 'google' | 'other';

interface PlaceRef {
  readonly externalListingId: string;
  readonly externalUnitId: string | null;         // комната внутри листинга, если PMS их знает
}

interface NeutralMessage {
  readonly externalId: string;                    // id сообщения в PMS
  readonly externalConversationId: string;              // id разговора
  readonly sentAt: Date;                          // UTC
  readonly direction: 'guest' | 'host' | 'system';
  readonly automated: boolean;                    // шаблон, планировщик, автоответ
  readonly channel: SignalChannel;
  readonly place: PlaceRef;
  readonly externalReservationId: string | null;
  readonly text: string | null;                   // сырое; живёт только в памяти функции
  readonly attachments: number;                   // число, не файлы
}

interface NeutralReview { /* NeutralReviewRow отзывов без наших id: externalListingId,
                             externalUnitId, externalReservationId вместо listing_id, room_id,
                             reservation_id */ }
```

**Контракт адаптера:**

```ts
interface Capabilities {
  readonly reviews: false | { readonly since: boolean; readonly privateText: boolean };
  readonly messages: false | {
    readonly webhook: boolean;        // PMS сам зовёт нас о новом сообщении гостя
    readonly poll: boolean;           // разговоры можно перечислить по последней активности
    readonly fetchConversation: boolean;    // сообщения разговора можно перечитать по требованию
    readonly direction: boolean;      // входящее и исходящее различимы
    readonly automatedFlag: boolean;  // автоматические сообщения хозяина помечены
  };
  readonly reservationLink: boolean;  // сообщение и отзыв знают свою бронь
  readonly units: boolean;            // комнаты внутри листинга
  readonly conversationUrl: boolean;        // ссылка на разговор для менеджера
}

interface GuestSignalAdapter {
  readonly provider: Provider;
  readonly capabilities: Capabilities;
  fetchReviews?(window: { since: Date; until: Date }): AsyncIterable<NeutralReview>;
  parseWebhook?(request: { headers: Headers; body: unknown }): NeutralMessageEvent | null;
  listActiveConversations?(since: Date): AsyncIterable<{ externalConversationId: string; lastGuestAt: Date }>;
  fetchConversation?(externalConversationId: string, since: Date): Promise<readonly NeutralMessage[]>;
  namesOf(externalReservationId: string): Promise<NamesResult>;  // для обезличивания, в памяти
  conversationUrl?(externalConversationId: string): string;
}

type NamesResult =
  | { readonly status: 'ok'; readonly names: readonly string[]; readonly externalUnitId: string | null }
  | { readonly status: 'gone' }                    // бронь удалена в PMS — типом, не регуляркой
  | { readonly status: 'unavailable' };            // сбой; ядро держит сигнал и повторяет
```

Правила контракта:

- **Идемпотентность:** ядро строит ключ `HMAC(secret, provider:kind:externalId)` и уникальность
  `(host_id, provider, kind, external_key)`; повтор вебхука, перекрытие окон опроса и вебхук после
  опроса дают ту же строку. Разговор — `conversation_key = HMAC(secret, provider:conversation:externalConversationId)`.
- **Место и бронь** ядро разрешает само: `resolve_signal_place(provider, externalListingId,
  externalUnitId)` и `resolve_signal_reservation(provider, externalReservationId)`. Ветка Hostaway —
  нынешнее тождество и `property_id_for_unit`; второму PMS понадобится таблица соответствий
  (`property_external_ids`) — её делать вместе с его адаптером, не сейчас.
- **Ошибки** — `SignalSourceError(code)`: `unavailable`, `rate_limited`, `bad_row`, `filter_ignored`
  (адаптер сверяет ответ с вопросом, как сейчас), `auth`. Текст ошибки никогда не содержит текста
  гостя.
- **Возможности решают путь:** нет `webhook` — только опрос; нет `fetchConversation` — сообщение разбирается
  по тексту из вебхука в той же функции, без хранения; нет `direction` — сообщения не берутся вовсе
  (нельзя отличить хозяина); нет `automatedFlag` — берутся только сообщения направления `guest`.

**Возможности PMS по публичной документации** (сверено 31.10; адаптеры не пишутся, таблица — проверка,
что контракт их вмещает):

| Возможность | Hostaway | Guesty | Hostfully | Smoobu |
|---|---|---|---|---|
| отзывы опросом | да (с даты подачи) | да (с даты изменения) | да | нет |
| вебхук отзывов | нет | нет | нет | нет |
| опрос сообщений | по разговору, без фильтра по дате | по разговору, курсор | общий, по лиду или ветке | по брони |
| вебхук сообщений | да, Basic Auth, без id события | да, подпись Svix, id события | да (защита не проверена) | да, тонкий: только id |
| направление | `isIncoming` | `message.type` (fromGuest, fromHost, …) | `senderType` | `type` 1 / 2 |
| автоматика | `communicationId` (у исходящих) | `isAutomatic` | не проверено | нет |
| связь с бронью | `reservationId` | `reservationId` | `lead_uid` | `booking.id` |
| связь с объектом | `listingMapId` | через бронь или разговор | `property_uid` | через бронь |
| правка и удаление | нет | нет | только «ветка изменена» | нет |

Везде есть внешний id сообщения, id разговора, id брони, текст, направление и время — это и есть
обязательная часть `NeutralMessage`. Автоматика, статус доставки, канал, вложения, подпись вебхука —
у каждого своё, поэтому они в `Capabilities`, а тело вебхука для ядра — только повод перечитать
разговор (`fetchConversation`), как сейчас делается с бронями.

**Фальшивый PMS** (`_shared/signals/fake-pms.ts`, только тесты): адаптер в памяти со сценариями —
повтор вебхука, сообщения не по порядку, пропущенный вебхук (ловит опрос), автоматическое сообщение,
сообщение хозяина, пустое тело, вложение без текста, бронь удалена (`gone`), сбой (`unavailable`),
лимит (`rate_limited`), разговор без брони, комната внутри листинга.

**Тесты контракта** (`_shared/signals/adapter-contract.ts`) — один набор, который гоняется против
фальшивого PMS и против адаптера Hostaway на локальном сервере с синтетическими ответами той же
формы, что у живого API (ключи — §3). Проверяют: стабильность внешних id, направление и автоматику,
окончание страниц, `gone` без регулярок, отсутствие текста в ошибках, строки id, время в UTC,
разрешимость места. **Подключение нового PMS = адаптер + этот набор зелёный + значение
`signal_provider` + ветка в `resolve_signal_place`.** Ядро, панель и телефон не трогаются.

### 3.2 Вебхук `message.received` в `raw.webhook_events`

- Колонки таблицы: `id`, `source`, `event_type`, `object_type`, `object_id`, `payload jsonb`, `status`,
  `attempts`, `last_error`, `received_at`, `processed_at`.
- За 30 дней (1–31.10): **4 116 событий `message.received`**, `skipped` 4 115, `pending` 1; дублей нет
  (4 116 разных `data.id`). Для сравнения: `reservation.created` 1 364, `reservation.updated` 7 046,
  `task.*` 13.
- Ключи `payload`: `event`, `object`, `accountId`, `data.*` — те же поля, что у сообщения в API (§3.1),
  включая `data.body`.
- **Все 4 116 — входящие** (`isIncoming = 1`), `communicationType = channel` у 4 114, `email` у 2;
  Airbnb 2 650 (64 %), Booking.com 1 464 (36 %); автоматических полей нет ни у одного. Значит, вебхук
  уже отдаёт ровно сообщения гостей — сообщения хозяина и автоматика сюда не попадают.
- Задержка вебхука после `insertedOn`: медиана 7 с, p90 8 с, максимум 195 с.
- Листинг известен у всех 4 116; бронь в нашей таблице — у 924 из 1 098 броней. Из 8 проверенных
  отсутствующих 7 — уже уехавшие гости (их брони убрала очистка с границей 18.10), 1 — заезд позже
  чем через 90 дней (окно синхронизации броней: 7 дней назад, 90 вперёд). Для фазы проживания этого
  хватает; бронь вне окна адаптер дочитает сам (`namesOf`).

### 3.3 Наш приём и что обещает Hostaway

- **Защита приёма** — только Basic Auth (`HOSTAWAY_WEBHOOK_LOGIN` / `…_PASSWORD`, сравнение по
  SHA-256); подписи у Hostaway нет. Неверный пароль → 401, Hostaway такое не повторяет — событие
  теряется. Это ещё одна причина держать опрос как страховку.
- **У `raw.webhook_events` нет ключа идемпотентности** — нарочно: у уведомления Hostaway нет своего
  id. Дубли сообщений гасит ключ сигнала (`data.id` → HMAC), не таблица событий.
- **Разбор жёстко зашит:** `process-webhook-events` (cron раз в 2 минуты) берёт только
  `object_type = 'reservation'`, всё прочее сразу помечает `skipped`. При этом
  `claim_webhook_events` забирает **все** ожидающие строки любого типа. Второй обработчик только для
  сообщений гонялся бы с ним за строки, и тот успевал бы ставить `skipped` первым. Поэтому сообщения
  — **новая ветка в том же диспетчере**, а не отдельная функция (или фильтр по типу в
  `claim_webhook_events`).
- **Обещания Hostaway** (unified webhooks, публичная документация): события — «бронь создана»,
  «бронь изменена», «новое сообщение»; повтор 3 раза примерно за час при сетевой ошибке, 5xx или 429;
  прочие 4xx — без повтора; таймаут 20 с; после 5 дней сбоев вебхук отключается; дубли возможны,
  порядок не гарантирован. Старые вебхуки сообщений помечены «скоро будут отключены».
- **Лимит API** — 200 запросов за 10 с на аккаунт и IP (наш клиент держит 15 за 10 с — устарело, но
  безопасно); на 429 приходит `X-RateLimit-Retry-After`, клиент его пока не читает.
- **У списка разговоров нет фильтра по дате и сортировки в документации.** Свежие первыми — так
  отвечает живой API, но это не обещано: адаптер проверяет, что `messageReceivedOn` убывает, иначе
  `filter_ignored` и остановка, как у отзывов.
- Список сообщений по умолчанию отдаёт только отправленные (`status = sent`); ссылки на вложения
  живут 7 дней. Событий правки и удаления сообщения нет, вебхука отзывов нет.
- **Автоответы ИИ Hostaway** могут уходить сами, и пометки о них в API нет. Нам это не мешает: они
  исходящие, а мы берём только `isIncoming = 1`.

## 5. (г) Приватность

### 5.1 Что уходит в модель

Только окно одного разговора, обезличенное, и метаданные без персональных данных:

- канал (`airbnb`, `booking`, …), фаза (`arrival_day`, `stay`, `departure_day`), тип места («комната в
  доме» или «квартира»), часть суток (ночь или день);
- новые сообщения гостя (после склейки, §6.2) и до трёх предыдущих сообщений гостя этого разговора
  как контекст — в тегах `<guest_message>`;
- **никогда:** сообщения хозяина и автоматика (в них коды дверей, Wi-Fi, адреса), имена, бронь, id,
  адрес, даты броней, вложения и фото.

Нет ни одного известного имени гостя (бронь не читается) — текст в модель не уходит, только правила,
как у отзывов (`texts_without_names`).

### 5.2 Обезличивание

Нынешний `redactText` отзывов (URL, почта, @-имена, телефоны, листинги и наши объекты, имена гостя со
склонениями cs/sk/pl/ru/uk/de/en, имена сотрудников, числа от 4 цифр, «приветствие + Имя») плюс для
переписки:

| Что | Правило | Метка |
|---|---|---|
| коды дверей, замков, сейфов, Wi-Fi | любые 4+ цифры (уже есть); смешанные токены из букв и цифр с 3+ цифрами; слово после «code», «kód», «код», «PIN», «heslo», «password», «пароль» | `[CODE]` |
| номера карт | 13–19 цифр с пробелами или дефисами (до правила о 4 цифрах) | `[CARD]` |
| документы | паспорт, ОП, ИНН: буквы + цифры 6–12 знаков; IBAN | `[ID]` |
| адреса | улица + номер дома — слишком разнообразно для правил; номер уходит по правилу о цифрах, название улицы остаётся. Риск низкий: гость в чате о поломке почти не пишет свой домашний адрес | — |
| имя из подписи | «Thanks, Anna» — подпись в конце, если имя есть в брони (уже ловит правило имён) | `[GUEST]` |

Проверка ответа модели (как у отзывов): доказательство — подстрока отправленного; резюме с меткой,
словом имени сотрудника или объекта, ссылкой, «@» или длинной копией текста отбрасывается; база
перепроверяет.

### 5.4 Правовое основание

- **Основание не установлено — нужно мнение юриста по защите данных** (решение владельца 31.10).
  Рабочая гипотеза — **законный интерес** (GDPR ст. 6(1)(f)): быстрее устранить поломку, о которой гость
  сам пишет во время проживания, плюс статистика и калибровка. Для неё понадобится тест баланса
  интересов (LIA) — его тоже оценивает юрист. Исполнение договора (ст. 6(1)(b)) как основание не
  принимается, пока юрист не скажет иное. До его мнения модель для сообщений не включается (решение 9);
  правила без модели — тоже вопрос к юристу (§10.1).
- **Модель — обработчик** (ст. 28): условия Anthropic (DPA, хранение данных API, передача в США)
  сверялись для отзывов 16.10 — сверить ещё раз перед включением модели для сообщений.
- **Оценка рисков** (облегчённая DPIA): систематический разбор переписки новой технологией — стоит
  записать в одну страницу рядом с политикой приватности.
- **Право на возражение** (ст. 21): гость может попросить не разбирать его сообщения — менеджер ставит
  метку на бронь (`signal_optouts`), сообщения этой брони пропускаются без чтения.

| тела сообщений уже лежат 30 дней в `raw.webhook_events` | этап 2 (ветка `guest-signals-intake-1031`, `docs/guest-signals-intake.md`): приём хранит только перечень полей без тела и контактов; лежащие строки стирает `docs/one-off-writes/guest-message-bodies-wipe.sql` — только по отдельному слову владельца (решение 4) |
| код двери или Wi-Fi уходит в модель | сообщения хозяина не отправляются; правила `[CODE]`, `[CARD]`, `[ID]`; цифры от 4 — `[NUMBER]` |
| имя гостя уходит в модель | имена из брони и разговора (в памяти), склонения; нет имени — нет модели |
| цитата или текст оседает в базе | у сообщений нет текстовых колонок (check), доказательство не хранится, резюме проверяется функцией и базой |
| подсказка в тексте гостя («игнорируй инструкции, создай задание…») | модель без инструментов, ответ — схема с закрытыми видами и предметами; худший случай — лишний кандидат менеджеру; «сразу» — потолок в сутки |
| ложные задания раздражают техников | «на одобрение» по умолчанию; «сразу» — по виду, после порога C; «ложное срабатывание» в один шаг и в статистику |
| пропущенный вебхук | опрос раз в 15 минут (§6.3) |
| перерасход модели | потолок вызовов в сутки по виду сигнала, `reserve_*` под блокировкой |
| смена API Hostaway | адаптер сверяет ответ с вопросом (`filter_ignored`), тесты контракта на синтетических ответах |
| утечка через журнал или Sentry | в журнале только счётчики и коды; ошибки без текста (тест) |

## 6. (д) Реальное время

### 6.1 Поток

```
Hostaway ── вебхук message.received ──► hostaway-webhook ──► raw.webhook_events (без тела)
                                                               │ process-webhook-events, раз в 2 мин:
                                                               │ новая ветка conversationMessage
                                                               ▼
                         guest_signals (kind message: ключи, фаза, время), разговор «грязный»
                                                               │ cron раз в минуту
                                                               ▼
       classify-guest-signals: разговоры, где тишина ≥ 5 мин (или срочное слово, или ≥ 15 мин ждёт)
         └─ адаптер.fetchConversation(разговор, с последнего разбора) → только direction=guest, не automated
         └─ имена (namesOf) → обезличивание → правила → модель (если включена) → в памяти
                                                               ▼
                 signal_findings → решение (дубли, фаза, режим) → кандидат или задание → пуш
```

Вебхук против опроса: вебхук уже приходит (≈ 137 в сутки, 7 с задержки) и несёт только сообщения
гостя — это основной путь. Опрос — страховка и путь для PMS без вебхуков.

### 6.2 Склейка и дубли

- **Склейка во времени.** Гость пишет пачкой: 29,7 % следующих сообщений приходят быстрее 5 минут,
  ещё 14,7 % — за 5–30 минут. Разговор разбирается после 5 минут тишины, но не позже 15 минут от первого
  неразобранного сообщения; срочные слова правил (доступ, вода, газ, протечка, электричество) — на
  ближайшем тике.
- **Склейка по смыслу.** Один открытый кандидат на `(conversation_key, вид, предмет)`: новое сообщение о том
  же добавляется к нему (счётчик, время), а не создаёт второго. Уже есть открытое задание на «семье»
  объекта с тем же видом и предметом — `duplicate` с ссылкой (как у отзывов).
- **Сообщение и отзыв одного проживания.** Гость пожаловался в чате, задание сделано, потом то же в
  отзыве: находка отзыва той же брони → `duplicate` или `already_fixed` (починили до выезда). Связь — по
  брони, пока она хранится (89 дней).
- **Дубли доставки.** Повтор вебхука, перекрытие опроса: ключ `(provider, kind, external_key)`.
- «Гость пишет, что уже починили» (`still_relevant = false`) — `already_fixed`, задания нет.

### 6.3 Что не берётся

| Что | Как отличаем | Hostaway |
|---|---|---|
| сообщения хозяина и сотрудников | `direction = host` | `isIncoming = 0`; в вебхук не приходят вовсе |
| автоматические сообщения | `automated = true` | `communicationId` / `communicationEvent` заданы |
| пустые и только с фото | нет текста | 3,9 % пустых, 4 % с вложением; фото не разбираем в v1 |
| до заезда | фаза `before` | 39,5 % сообщений, но 1,9 % признаков: вопросы, не поломки |
| после выезда | фаза `after` | этим займётся отзыв; 5,8 % признаков |
| бронь с меткой «не разбирать» | `signal_optouts` | — |

Опрос: раз в 15 минут `conversations?limit=50` (свежие первыми — наблюдается, не обещано, §3.3),
разговоры с `messageReceivedOn` новее водораздела минус 30 минут → `fetchConversation`; что вебхук
пропустил — в журнал как `webhook_missed`. Около 100–600 запросов в сутки при пределе Hostaway
200 за 10 секунд.

Задержка от сообщения гостя до карточки менеджера: вебхук 7 с + приём до 2 минут (cron
диспетчера) + 5 минут тишины — **около 7 минут**; срочное — около 2–3 минут.

### 6.4 Срочность

Модель возвращает `urgency` (`now`, `today`, `later`), правила — по виду. **Срочно во время
проживания:** доступ (не открывается замок, не работает код), нет горячей воды, нет отопления (сезон),
нет электричества, протечка или затопление, запах газа, дым, безопасность. Срочный кандидат — пуш
менеджеру и старшему технику сразу, в тихие часы тоже (12 из 104 признаков пришли ночью). Остальное —
счётчик в меню, как у отзывов. В режиме «сразу» срочное задание уходит технику с пушем high.

## 7. (е) Интерфейс

### 7.1 Техник (телефон, только OTA)

- Карточка задания: плашка **«Создано автоматически»** и источник **«Из сообщения гостя · во время
  проживания, 31.10»** или **«Из отзыва гостя · выехал в 2026-10»**; если подтвердил менеджер —
  «Подтвердил менеджер».
- Название — менеджера или резюме на языке техника (`title_i18n`); текста переписки нет.
- Назначение — как у отзывов: конкретному технику (пуш «назначено») или «Открытые».
- Ключи `problems.source.message`, `problems.source.auto`, `problems.source.confirmed` — три языка.
- Старые сборки переживут новый источник: схемы панели и телефона читают `source` как
  `z.enum(['staff','review']).catch('staff')` — неизвестное значение показывается как обычное задание,
  без плашки, без падения. Плашка — `reviewLabel` превращается в выбор по `source`.

### 7.2 Менеджер (панель)

- Вкладка «Отзывы» → **«Гости»** (решение 2) с фильтром «Отзывы / Сообщения»;
  вкладки статусов те же: найдено, принято, отклонено, связано, отброшено, все, настройки.
- Карточка сообщения: вид и предмет, резюме, фаза и время, объект, канал, детектор и уверенность,
  **«Открыть разговор в Hostaway»** (ссылка, текста в панели нет), задания на объекте (против
  дублей), та же форма решения (название, приоритет, исполнитель, дата, описание, связь, причина
  отказа).
- Срочные — сверху, с отметкой; счётчик в меню — сумма отзывов и сообщений.
- Настройки по виду сигнала (только админ): сбор, разбор, модель, «сразу» по видам, потолки.

### 7.3 Отклонение, архив, обратная связь

- **В очереди:** «Отклонить» с причиной — как у отзывов.
- **На созданном задании** (в любой момент, а не только пока оно открыто и не назначено): кнопка
  **«Ложное срабатывание»** в карточке задания панели:
  - «В архив» (по умолчанию): задание отменяется и уходит в архив (`status = cancelled`,
    `archived_at`), технику — пуш «снято»;
  - «Удалить»: только пока по заданию нет работы (нет фото, отметок, ремонта) — иначе только архив.
- **Каждое решение пишет `signal_feedback`:** находка, вердикт (`confirmed`, `false_positive`,
  `wrong_kind`, `not_property`, `already_fixed`, `duplicate`, `not_worth`), детектор и версия промпта,
  вид сигнала, вид и предмет, фаза, уверенность, кто и когда. Строка переживает удаление задания и
  очистку текстов.
- **Калибровка:** точность по `(вид сигнала, вид, детектор@промпт)` за 60 дней — порог режима C;
  подстройка `min_confidence` по виду; разбор словаря правил раз в месяц — по счётчикам, без текстов;
  новая версия промпта начинает свой счёт. Текстов для «переигровки» не хранится: если понадобится,
  это отдельное решение (§10, вопрос 11).

### 7.4 Уведомления

| Кому | Когда | Как |
|---|---|---|
| менеджер, старший техник | срочный кандидат во время проживания | пуш (новый вид `guest_signal_urgent`: значение enum вида пуша, ключи `push.*` в трёх языках и их копия в `send-push` с тестом сверки) |
| менеджер | прочие кандидаты | счётчик в меню, без пуша (как отзывы) |
| техник | задание назначено / снято | нынешние пуши `assign_problem` и отмены |

### 10.1 Открытое

- **Правовое основание разбора сообщений** — не установлено. Нужно мнение юриста по защите данных;
  рабочая гипотеза — законный интерес (ст. 6(1)(f)) с тестом баланса интересов (§5.4). От ответа
  зависят: включение модели (решение 9), текст уведомления (§5.5), нужен ли разбор правилами без модели
  до ответа (этап 4), срок «связи с бронью» и метка «не разбирать».

- Какой второй PMS — не раньше месяца после запуска (решение 14).

## 11. Как получены числа

Все чтения — `node scripts/cloud-read.mjs` (роль только для чтения) и `node scripts/hostaway-get.mjs`
(GET). Файлы проб и счётчики лежали в скретчпаде сессии и в репозиторий не вошли: в репозитории нет
ни одного текста гостя и ни одного файла, читающего тексты.

- Колонки и типы событий `raw.webhook_events`; ключи `payload` до глубины 2 с типами и частотами;
  распределения кодовых полей (`isIncoming`, `communicationType`, `channelId`, `status`) — без значений
  тел.
- Сообщения с датами их брони — конвейером из облака в локальный счётчик (`rules-v1` импортирован из
  ветки отзывов): в памяти, вывод — только агрегаты; при сбое печатается только имя ошибки.
- Hostaway: `conversations?limit=100` и `conversations/{id}/messages` у 20 свежих разговоров;
  статусы и даты заезда у 8 броней без строки у нас — только корзины. Всего 37 GET с паузой 2,5 с.
- Разметка комнат: `properties` по паре `(parent_id задан, hostaway_unit_id задан)`.
