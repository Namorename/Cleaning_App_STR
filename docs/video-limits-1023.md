# Пределы видео: копия в шаге против настроек компании (23.10)

Продолжение `docs/video-upload-1022.md`, ветка `video-upload-1022`. Чтение облака — только
`scripts/cloud-read.mjs`, стенд — в откатываемых транзакциях; в облако ничего не записано.

## 1. Причина

22.10 в 14:47 UTC компания поставила 180 с / 140 МБ / 4500 кбит/с, в 19:07 — 180 с / 140 МБ /
2500 кбит/с. Размер и битрейт телефон и сервер читают из `hosts` в момент действия. Длина — нет:
берётся меньшее из двух чисел, и второе — **копия, которую шаг снял с процесса при старте уборки**.

| Где | Что | Файл и строка |
|---|---|---|
| Настройки компании | `hosts.video_max_sec / video_bitrate_kbps / video_max_mb`, пишет менеджер через `update_host_settings` | `supabase/migrations/20261003170000_video_limits.sql:50`, `:100` |
| Шаг процесса | `workflow_steps.max_video_sec`, поле панели «Макс. длина видео» | `20260905110200_workflow_templates.sql:128`; панель `apps/web/src/features/workflow/step-row.tsx:146` (main); пишет `save_workflow_template` — `20260907130000_workflow_step_translations.sql:197` |
| Копия в начатой уборке | `task_steps.max_video_sec`, снимается один раз, когда уборка уходит в работу | триггер `tasks_snapshot_workflow` — `20260905110300_task_steps.sql:159`; копирование — `20260907130000_workflow_step_translations.sql:93` |
| Сервер | `add_task_media`: размер — `hosts` сейчас (`:125`), длина — `least(coalesce(копия, компания), компания)` | `20261010100000_video_from_gallery.sql:143` |
| Телефон | читает `hosts` при открытии шага, если копии больше 5 мин (`use-host.ts:23`, `[stepId].tsx:111`), иначе с диска; длина — то же `min(копия ?? компания, компания)` | `features/media/schema.ts` `videoLimits`; `record-gate.ts:86`; `[stepId].tsx:208`; отказ галереи — `features/video/gallery-video.ts` |

В облаке (чтение 23.10, 00:20 UTC): компания 180 с / 2500 / 140 МБ; в шаблоне `0f0951a9` видео-шаг
обязательный, своя длина **120 с** (шаблон сохранён 20.10 в 22:06); до этого шаги копировали **90 с**.
Итог: каждая уборка — и начатая, и новая — держит 120 (или 90) с, а 180 компании не действует нигде.

**Что видит горничная.** Видео из галереи длиннее копии телефон отклоняет до отправки:
«Это видео длиннее 90 с. Выберите покороче или снимите на камеру.» (`video.galleryTooLong`).
Камера останавливается на копии, подсказка шага — «Запишите одно видео до 120 с». Если бы телефон
пропустил, сервер ответил бы `serverErrors.videoTooLong` — «Видео длиннее 90 секунд».

**Воспроизведение.**
- Стенд, откатываемая транзакция (`scratchpad/video-1023/repro_snapshot.sql`, 8 проверок):
  - уборка A стартует при 90 с в процессе — копия 90;
  - менеджер ставит процессу 120, компании 180 / 140 МБ — копия A остаётся 90;
  - уборка B стартует после этого — копия 120;
  - видео 150 с: A → `videoTooLong {"limit": 90}`, B → `{"limit": 120}`;
  - 100 МБ на 100 с в B проходит: размер читается сейчас;
  - после опустошения копии A то же видео проходит.
- Телефон: новый тест `record-gallery.test.tsx` на старом коде — копия 90 и компания 180, видео
  150 с показывает «Это видео длиннее 90 с…».

## 3. Решение

**Единый источник — настройки компании в момент действия**, для каждой незавершённой уборки:
- открытие шага — подсказка и камера;
- выбор файла из галереи;
- регистрация на сервере (`add_task_media`).

Копия в шаге больше ничего не ограничивает. Завершённое не трогается:
- выполненный шаг сервер отклоняет (`stepCompleted`);
- выполненную уборку — тоже (`stepNotFound`);
- данные завершённых не меняются ни миграцией, ни разовой правкой.

| Путь | Что даёт | Риск |
|---|---|---|
| Только телефон (OTA) | телефон перестаёт брать копию | без сервера опасен: телефон пропустит 150 с, сервер откажет при регистрации — хуже, чем сейчас |
| Только разовая правка данных | копии начатых уборок пусты → и старый телефон, и нынешний сервер берут число компании; работает сразу, без кода | новые уборки снова копируют 120 из процесса, пока менеджер не очистит поле «Макс. длина видео» (или не выйдет миграция) |
| Миграция (черновик) | сервер берёт только компанию; новые старты не копируют длину (null) — старые телефоны в поле тоже берут компанию | запись в облако по слову; откат готов |
| Телефон по OTA после миграции | телефон считает так же, как сервер, и не зависит от поля процесса | только JS; preview, затем field |

Выбрано: все три слоя, в порядке ниже. Новой нативной сборки не нужно.

**Если настройки недоступны или поменялись во время записи:**
- Телефон берёт последнюю прочитанную копию настроек: перечитывает при открытии шага, если ей
  больше 5 минут, иначе берёт её с диска.
- Если настройки не читались ни разу — камера ждёт («Настройки видео ещё не получены…») и не
  угадывает: угаданная длина длиннее настроек компании — это видео, которое сервер откажет после
  ожидания.
- Камера держит пределы, с которыми открылась (`record.tsx`, `openedWith`).
- Предел — числа компании в момент регистрации на сервере. Зарегистрированный файл больше не
  перепроверяется: `confirm_task_media` пределов не смотрит.
- Поднятый предел действует сразу. Сниженный — тоже: видео длиннее нового предела сервер
  откажет с новым числом, горничная переснимет.

## 4. Порядок выката (каждый шаг — словом владельца)

1. **Поле «Макс. длина видео» в процессе.** Менеджер очищает его у видео-шага: Настройки →
   Процесс → шаг «Видео» → пусто → Сохранить.
   - Это обычное действие в панели, без кода.
   - После него новые уборки копируют пусто, то есть получают число компании.
   - Первым — чтобы список правки ниже больше не рос.
   - После миграции поле ни на что не влияет.
2. **Разовая правка 8 уборок в работе.**
   - Команда: `npx supabase db query --linked -f docs/one-off-writes/video-limits-1023-unstick.sql`.
   - Затем проба: `node scripts/cloud-read.mjs docs/rollout/video_limits_1023_probe.sql`.
   - Вне 03:00–04:40 UTC. Действует сразу на все телефоны (шаги перечитываются при открытии,
     `staleTime` 30 с).
   - 7 уборок из 8 закроются 24.10 в 03:30 UTC: правка помогает только до этого.
   - Если между чтением 18:15 UTC и правкой стартует ещё уборка с копией 120 (поле процесса ещё не
     очищено), её в списке нет — нужен свежий список.
3. **Миграция `20261023100000_video_limits_live`.**
   - Убрать страж.
   - Сверить голову облака (`docs/rollout/remote_head.sql`); сухой прогон должен назвать один этот
     файл.
   - `db push`.
   - Проба: md5 `add_task_media` = bf208d8c, `snapshot_task_steps` = dd81ff14.
4. **OTA телефона на preview, затем после проверки на field.** Последний коммит ветки — 35d3615
   (потолок 150 МБ).

Старый и новый телефон одинаковы после шагов 1–3:
- копии пусты или null;
- старый телефон считает `min(null ?? компания, компания)` = компания;
- сервер — компания;
- новый телефон — компания.

OTA раньше миграции допустим, только если шаги 1 и 2 сделаны и поле процесса пусто.

Почему старым телефонам null не вредит:
- в поле только сборка 1.2.0 — все 17 активных push-токенов на 23.10, 9 Android и 8 iOS;
- код каждой сборки 1.2.0 (iOS 0505011, 6e181a1, 58dea4b; Android e7f65d8, dab5237) уже считает
  «копия или компания» (615af8e);
- сборки до 615af8e считали «копия или 30 с»; в поле их нет.

Миграция по времени новее припаркованных 20261017100000 и 20261017110000 (база знаний, отзывы).
Их push после этой — с `--include-all`, проверить на сухом прогоне.

## 7. 20 истёкших уборок

13 на 22.10 днём, 14 в чтении 00:20 UTC, 20 после ночной задачи 23.10.

Горничная их не видит: телефон показывает только открытые статусы
(`apps/mobile/src/features/tasks/api.ts:68`). Добавить видео в истёкшую нельзя: `add_task_media` →
`stepNotFound`. Инструментов у менеджера нет:
- в панели (main) нет «завершить», «вернуть в работу» или «пропустить шаг»;
- `waive_task_step` никто не вызывает, а истёкшие уборки она отклоняет
  (`20260907120200_error_keys.sql:357`).

Менять статус можно только прямой записью: офис может любой переход, проверка обязательных шагов
на него не действует (`20261003130000_head_tech_dispatch.sql:350`).

| Вариант | Что нужно | Статистика и аналитика (`20261015110000_analytics.sql`) |
|---|---|---|
| **Оставить** | ничего | в «запланировано» в свой день и в колонке «истекло» (`:472`); не «выполнено»; минут нет. Честная запись сбоя |
| **Вернуть в работу** | запись `status = 'in_progress'` + пустая копия; горничная добавляет видео *той* уборки из галереи и завершает **в тот же день**: в 03:30 UTC её снова закроет ночная задача | «выполнено» в день завершения (`done_day` = дата `completed_at`, `:144`), не в день уборки; минуты (старт 18–22.10 → сейчас) > 360 — вне медианы и среднего (`:150`); исполнитель — горничная; в журнале «возвращена» → «выполнена». Видео, снятое сейчас, — не доказательство той уборки |
| **Закрыть с отметкой** | запись: шаг `waived_at` + причина, уборка `done`, исполнитель указан явно (под `db query` нет `auth.uid()`) | «выполнено» днём закрытия, а не 18–22.10; минуты вне медианы (если не задать `duration_override_min`); из колонки «истекло» уходят закрытые |
| **Отменить** | запись `status = 'cancelled'` | уходит из «запланировано» в «отменено»; скрывает сбой |

Предложение: оставить. Если у конкретной горничной есть видео той уборки, — вернуть в работу по
одной, в рабочий день, с её подтверждением. Скрипт под выбранный вариант — после слова.
