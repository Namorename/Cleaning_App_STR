# Обнуление перед запуском — проект

**Статус: только проект, ничего не выполнено** (2026-09-23). Решение владельца:
перед запуском всё прошлое обнуляется целиком — задачи с датой до дня запуска и
всё, что на них держится. Накопленные дубли `expired` (3 890 по замеру
2026-09-23) уходят вместе с ним, отдельной чистки не будет, уникальный индекс
не ставится (`docs/f10-plan.md`, «Решения владельца», 2). Ответы владельца на
вопросы проекта вписаны 2026-09-23 (раздел «Решения владельца» в конце); открыт
один — тестовые учётки.

Ниже **L** — день запуска: первый день, когда горничные работают в приложении
по-настоящему. Дата запуска — день, когда готов «Минимум запуска» (раздел
ROADMAP). На следующий день после запуска владелец на месте: даёт слово и
проверяет результат. Все даты — по Праге (108 объектов `Europe/Prague`, 2
`Europe/Berlin`, пояса совпадают).

Числа «сегодня» — проба `docs/rollout/prelaunch_probe.sql` (облако,
2026-09-23, только счётчики). К дню L они вырастут; сухой прогон (шаг 1)
перемеряет их на L+1.

## 2. Когда стирать: генератор и вчерашние уборки

Таблица `tasks` — память генератора о том, какие брони уже обслужены. Удалённая
уборка делает бронь снова «должной», и генератор рождает её заново, если день
не просрочен: `task_is_stale` = дата раньше `сегодня − 1` (отсрочка —
`task_grace_days() = 1`, `20260904120100:28-59`; граница рождения —
`20260923120000:277-331`).

- **Стирать в день L нельзя.** Вчерашний день L−1 ещё в отсрочке. Первый же
  вызов генератора, окно которого его накрывает, вернёт все уборки L−1: ночной
  прогон в 03:15 UTC (окно сегодня−7…+90) или любая пачка вебхука (каждые две
  минуты, 124–179 пачек в сутки). В 03:30 UTC на L+1 метёлка закроет их как
  `expired`, и в чистой истории навсегда останутся строки L−1. А сами уборки L−1
  в день L ещё могут делаться.
- **Стирать на L+1, после ночной метёлки.** С 00:00 по Праге L−1 уже просрочен,
  и граница рождения его не пропустит. После `expire-stale-tasks` (30 3 UTC)
  все уборки до L — конечные, ни один проход генератора их не пишет. Исключение —
  ремонты: метёлка их не трогает, поэтому они удаляются явно. Момент — после
  того, как `cron.job_run_details` покажет успех метёлки, например 04:00 UTC
  (06:00 по Праге летом, 05:00 зимой) или позже, когда владелец на месте. Мимо
  окон 03:10–03:35, 03:50 и 04:25–04:40 UTC: в 04:30 идёт
  `purge-task-media-daily` по тем же строкам и файлам, в 03:50 (с окна 3) —
  `purge-webhook-events` по той же `raw.webhook_events`, что и шаг 4.7.
- **Крон не гасить.** На L+1 рождать нечего, а `unschedule` удаляет задание,
  и вернуть его можно только полным определением (`docs/units-plan.md`,
  «Эксплуатация выката»). Забытое возвращение молча остановит вебхуки.
- **Если день L должен начаться без истории**, то в два прохода, оба после
  метёлки: на L — всё `≤ L−2` (уже просрочено), на L+1 — `L−1`.
- **Ещё один класс для сухого прогона:** брони с выездом `≥ L`, которых сейчас
  «обслуживает» только строка раньше L (`done`/`in_progress` на старой дате
  брони, сдвинутой после уборки). После стирания они получат новую уборку на
  новую дату — это правильно, но число надо знать заранее.

## 3. Файлы: сначала файл, потом строка

Клиент объекты не удаляет, удаляет только ретеншн (CLAUDE.md, «Медиа уборки»).
Им и пользуемся. Ветка `deleted_at is not null` в `task_media_to_purge` делает
строку «должной» сразу, без условий, во всех версиях функции.

1. `update public.task_media set deleted_at = now()` для строк удаляемых задач и
   удаляемых поломок, где `deleted_at is null`.
2. Позвать `select public.invoke_edge_function('purge-task-media')`. Функция
   удаляет файлы через Storage API сервисной ролью, по 200 строк, до 2 000 за
   прогон, и ставит `purged_at`.
3. Проверить: у всех строк набора `purged_at` есть, в `storage.objects` нет ни
   одного объекта по их `storage_path`.
4. Только после этого удалять строки.

Окно 2 к запуску будет в облаке (решение 8), поэтому в набор входят и фото
сообщений на ветках удаляемых задач и поломок (`task_media.message_id →
chat_messages cascade`, путь `host/chat/<thread>/…`): иначе каскад оставит их
файлы сиротами. Сухой прогон считает их отдельной строкой.

## 4. Порядок

1. **Сухой прогон с числами** — читающая проба (только счётчики, без
   персональных полей), на L+1 после метёлки, до копии:
   - задачи `< L` по статусу и типу, ремонты среди них;
   - `task_steps`, строки `task_media` по владельцу и состоянию, объекты
     бакета по их путям;
   - ветки и сообщения чата на этих задачах и поломках;
   - поломки и заявки, в том числе заведённые тестовыми учётками;
   - живые назначенные задачи и привязки тестовых учёток;
   - класс «бронь `≥ L`, обслуженная строкой `< L`»;
   - события вебхука к удалению по статусу — с окна 3 крон уже удалил
     `processed`/`skipped` старше 30 дней, счёт покрывает последний месяц;
   - прогноз ночного `past_bound`: брони с выездом L−5…L−1 в разрезе
     `_wanted` (по комнате из `reservation_units`, иначе по листингу; статусы
     `new`/`modified`, не блок, объект активен).

   Основа — `docs/rollout/prelaunch_probe.sql`, к нему добавляются метки для
   L.
2. **Копия, не таская имена гостей на локальную машину.**
   - **Архивная схема в облачной базе.** `create table archive_prelaunch.<имя>
     as select …` под `postgres` для удаляемых строк: `tasks`, `task_steps`,
     `task_media`, `chat_threads`, `chat_messages`, `chat_reads`, `problems`,
     `supply_requests` с позициями и удаляемые `raw.webhook_events` (только
     последние 30 дней: старше крон окна 3 удалил без копии — решение владельца
     2026-09-24). Данные не
     покидают сервер. Схема закрыта как `raw`: `revoke` у `anon`,
     `authenticated` и `public` — на схему и на каждую таблицу поимённо, затем
     проверка `information_schema.role_table_grants` в облаке. CTAS не
     копирует ограничения, индексы и гранты — для отката строки вставляются
     обратно в порядке внешних ключей.
     **Решение 7:** схема разовая, **без отдельной миграции** — сознательное
     исключение из правила «схема меняется только миграциями»: это копия
     данных на месяц, а не часть схемы приложения, и локальному стеку она не
     нужна. **Удаляется через 30 дней** после создания. Дата создания и дата
     удаления записываются сюда, в раздел «Журнал» ниже, в день выполнения.
   - **Файлы не копируются** (решение 7): ≤ 9 фото тестовых уборок, 1,4 МБ, без
     имён гостей.
   - **Платформенный бэкап** — убедиться в Dashboard → Database → Backups, что
     после сухого прогона есть свежий. Это страховка от катастрофы, а не
     выборочный откат: восстановление откатывает весь проект, файлов бакета в
     нём нет.
   - **Локальный дамп — нет.** Он потащил бы имена гостей (`raw.*`,
     `reservations.guest_name`); прецедент 12.09 — 269 МБ сырых броней на
     локальной машине, удалены после.
3. **Слово владельца** — по числам сухого прогона и проверке копии.
4. **Выполнение**, одним скриптом в окне §2:
   1. §3: файлы задач и поломок через ретеншн, проверка;
   2. `begin`;
   3. ремонты удаляемых поломок;
   4. поломки (каскад: их фото, уже без файлов, и ветки чата);
   5. задачи `scheduled_date < L` (каскад: шаги, медиа, ветки задач);
   6. три тестовые заявки Марии (с позициями — каскадом);
   7. события вебхука `processed` и `skipped`, полученные до L;
   8. тестовый шаг `photos_after` убран из стандартного шаблона ещё до L
      (иначе его унаследует каждая уборка дня L) — здесь только проверить, что
      его нет;
   9. `commit`;
   10. привязки тестовых учёток сняты до L (выше, «Учётки») — здесь только
       проверить; сами учётки — по ответу на вопрос 5, через Admin API.
5. **Проверка после** — счётчики:
   - задач `< L` — 0;
   - `storage_objects_without_row` — 0 (сирот нет);
   - строк `task_media` без файла, не отмеченных `purged_at`, — 0;
   - архивная схема закрыта для клиентов, `role_table_grants` для `anon` и
     `authenticated` не сдвинулись;
   - первый ночной `raw.generator_runs` после стирания: строка есть,
     `past_bound` ≈ прогнозу (ночью L+2 он считает выезды L−5…L−1, дальше
     убывает на день каждую ночь);

   Пачки вебхука, чей диапазон захватывает старые выезды, покажут большой
   `past_bound` — это «отказано в рождении», не дефект.

## 5. Чистка `raw.webhook_events` после запуска — проект миграции

Пункт «Минимума запуска» (решение 4). В журнале вебхука копятся полные брони
Hostaway с именами и телефонами гостей: 24 221 событие за 28 дней, около 870 в
сутки, и ничто их не удаляет. Обработчику нужны только `pending` — он берёт
очередь по статусу и перечитывает бронь из API, полезную нагрузку старых
событий не читает никто (`20260827200000:111-131`,
`process-webhook-events/index.ts`).

- **Одна небольшая миграция**, по образцу `purge-generator-runs`
  (`20260923120000:435-441`): план на чистом SQL, без pg_net и Edge Function.
  ```sql
  -- The journal keeps whole Hostaway bookings, guest names and phones included.
  -- The processor reads only pending rows; processed and skipped ones are
  -- history nobody reads after a month. Failed rows stay: they are the only
  -- record of a booking the API would not give.
  create index webhook_events_settled_received_idx
    on raw.webhook_events (received_at)
    where status in ('processed', 'skipped');

  select cron.schedule(
    'purge-webhook-events',
    '50 3 * * *',
    $$delete from raw.webhook_events
        where status in ('processed', 'skipped')
          and received_at < now() - interval '30 days'$$
  );
  ```
- **Время** — 03:50 UTC: после сверки 03:15, метёлки 03:30 и чистки следа
  03:45, до ретеншна медиа 04:30. В установившемся режиме в журнале около
  26 тысяч строк.
- **Тест** — свой набор `supabase/tests/webhook_retention.sql` (окно 3; образец —
  `purge-generator-runs`, `supabase/tests/task_generation.sql:371-373`): задание одно и
  с этим расписанием; его команда, исполненная в тесте, удаляет старое
  `processed` и старое `skipped` и оставляет старые `failed` и `pending`, а
  также свежее `processed`.
- **Выкат** — по правилам CLAUDE.md: `db:reset` → `test:rls` → `db:types`,
  застава с полным списком сухого прогона. После push заданий крона станет
  семь. Общее правило `docs/units-plan.md` («Эксплуатация выката») и README
  правятся тем же коммитом; у окна 3 своя проверка
  `docs/rollout/postpush_window3.sql`, ждущая семь. Файлы прошлых выкатов
  (`postpush_package.sql`, старые предполёты) — история, их не трогают.
  Миграция — `20260924160000_webhook_events_purge.sql`, едет в окне 3
  (`docs/window3-plan.md`).
- **Чистка до запуска** — отдельно, разовым удалением в окне обнуления (§4,
  шаг 4.7): крон старше 30 дней не тронул бы последний месяц до запуска.
- `raw.hostaway_reservations` (тоже с именами гостей) — не здесь: это зеркало
  броней и источник переигровки; его ретеншн — F24.
