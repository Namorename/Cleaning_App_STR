## Порядок и слова

Схема всегда раньше панели. Миграции идут по возрастанию времени в имени: CLI откажет, если в облаке есть
миграция новее той, что нужно применить. Поэтому части идут строго по номерам. Если часть пропускается, а
потом понадобится, её файлу дают новое время, миграцию проверяют заново, а стопку выше пересобирают.

| Слово | Что произойдёт | `HEAD_WANT` | `LIST_WANT` |
|---|---|---|---|
| **«выкатывай правку темы»** | Охраняемый `db push`, затем fast-forward `main` на коммит части 1 | `20261110120000` | `20261110200000_problem_theme_by_hand.sql` |

### Застава `db push`

Рецепт — `docs/rollout/property-quality-1106.md`, шаг 1. Push идёт из дерева, стоящего ровно на коммите части
(`git worktree add --detach <путь> <коммит части>`, в нём нужен `supabase/.temp` с pooler-url). В дереве с
частями выше сухой прогон назовёт и их файлы, и застава закроется — так и должно быть. Проверка и push — одной
командой, у вызова Bash `timeout` 600000. Окно 03:00–04:40 UTC не задевать.

```bash
HEAD_WANT=...   # из таблицы слов
LIST_WANT="..." # из таблицы слов, ровно один файл
SHA_WANT=...    # из таблицы ниже
[ "$(sha256sum supabase/migrations/$LIST_WANT | cut -d' ' -f1)" = "$SHA_WANT" ] &&
[ "$(node scripts/cloud-read.mjs docs/rollout/remote_head.sql |
     node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{try{process.stdout.write(String(JSON.parse(s)[0].head))}catch{}})")" = "$HEAD_WANT" ] &&
[ "$(npx supabase db push --linked --skip-vault --dry-run --output-format json |
     node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{try{process.stdout.write(JSON.parse(s).migrations.join(' '))}catch{}})")" = "$LIST_WANT" ] &&
npx supabase db push --linked --skip-vault
```

| Миграция | `SHA_WANT` (sha256 файла в коммите, LF) |
|---|---|
| `20261110200000_problem_theme_by_hand.sql` | `15b360983a338a96606f2bf58d731f00f4c1e74c5c34d07510ba791f9b2f1af1` |
| `20261110210000_cleaning_comment_themes.sql` | `e8a94420ca1b2ac6f311e7d5a9e9a9e38bc935c420b7726a83cc11d97a2a37b0` |
| `20261110220000_resolution_plans.sql` | `0873a83ffe03b70ac872fa67a74f13910c9613f8d0aa54d91c496d64dd831057` |

Часть 2 берёт короткую блокировку `hosts` и `issue_facts` (колонки и индекс), поэтому её push — между тиками
чтения истории и чатов, как push чатов (`docs/rollout/guest-chats-1110.md`). Её `refresh_property_quality` —
тело из `20261106120000` (чаты и закрытие его не меняли) плюс блок комментариев; откат возвращает это тело
дословно.

Часть 3 запускает ремонты вставкой в `problems`. Триггер закрытия (`20261106125000`) смотрит только на
`update` статуса и архива, так что запуск его не задевает, а ремонт из плана закрывается обычным
`resolve_problem`, где можно назвать, кто выполнил. Числа запуска (`baseline`, из `quality_theme_rows`) и эффект (часть 5, из
`issue_facts`) считают только `reviews`, `found` и `reported`: чаты (`messages`, слой `guest_message`) в них
не входят.

Функции Edge в этом этапе не меняются, деплой не нужен.

Новый `push` не появляется. Запуск плана с ремонтами даёт главному технику по одному `problem_new` на задание,
как и обычные задания: десять ремонтов — десять уведомлений. Приоритет плана ночью срочным не считается.

## Откат

Откаты идут от верхней выкаченной части вниз.

| Часть | Как |
|---|---|
| 1 | `git revert` коммита части 1, затем `problem-theme-hand-rollback.sql` и `migration repair --status reverted 20261110200000 --linked`. Темы, заданные руками, остаются обычными строками |
| 2 | Сначала выключить. `cleaning-comment-themes-rollback.sql` возвращает ночной пересчёт дословно и снимает колонки, затем `migration repair --status reverted 20261110210000 --linked` |
| 3 | Сначала часть 4. `resolution-plans-rollback.sql` откажет, если планы запускались: журнал планов пропал бы. Созданные задания, проверки и заявки остаются обычной работой. Значение `plan` в `problem_source` не удаляется, читатели принимают его за `staff`. Затем `migration repair --status reverted 20261110220000 --linked` |
| 4 | `git revert -m 1` коммита части 4 в `main`. Запущенные планы живут в базе, их работа — на своих экранах |
| 5 | `git revert -m 1` коммита части 5, затем `resolution-plan-effect-rollback.sql` и `migration repair --status reverted 20261110230000 --linked`. Числа запуска остаются в `baseline` |

Коммиты частей — слияния, поэтому `git revert` части 1 тоже идёт с `-m 1`. Запись в облако и
`db query --linked` — только по слову. Откаты репетированы на временной базе.

## Связка с themes-v2

Ветка `themes-v2-1106` (миграция `20261106130000_quality_shown_detector.sql`) в стопку не входит и не выкачена.
Перед словом «деплой тем v2» её миграцию надо пересобрать: новое время после стопки (после последней выкаченной
части), `quality_theme_rows` — от текущего тела из чатов (`20261110120000`) с полями `messages` и
`messages_prev`, `refresh_property_quality` — от тела части 2 с блоком комментариев. Старая копия в v2 тихо
убрала бы из «Качества» и чаты, и комментарии.
