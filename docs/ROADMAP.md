(`docs/cleanflow-spec.md`). Порядок внутри волны — порядок исполнения; номер — только
идентификатор, поэтому нумерация внутри волны не монотонна.

- [x] **F16. Конструктор процесса уборки** — шаблон на хост и тип задачи (`workflow_templates` / `workflow_steps`) с переопределением целиком на объект и наследованием через `parent_id`; снимок шагов в `task_steps` при старте, правка шаблона идущие задачи не трогает; обязательные шаги блокируют завершение в `guard_task_transitions`, менеджер снимает требование с причиной (`waive_task_step`); запись прогресса только через идемпотентные RPC; `save_workflow_template` готов для редактора F10. Стартовый сид — мягкий: все шаги необязательные. В приложении живые типы `task_note`, `confirmation`, `cleaner_comment`; фото, чек-лист, инвентарь и пожелания зарезервированы в enum и подключаются в F8/F7/F17/F20 без изменения схемы. Шёл **перед** F7: чек-лист — один из шагов, а не самостоятельный экран
- [x] **F7. Чек-листы** — модули и пункты **на объект** (`checklist_modules` / `checklist_items`, не на тип объекта), копирование из другого объекта (`copy_property_checklist`, копии независимы), наследование от родительского объекта. Живёт шагом `checklist` внутри движка F16, а не отдельным экраном: при старте задачи модули и пункты уходят снимком в `config` шага, ответ — `{checked_item_ids}`, пункт можно пометить необязательным (`is_optional`) — остальные держат шаг. Объект без чек-листа шага не получает, как задача без заметки не получает `task_note`. Правка чек-листа идущие уборки не трогает. Редактор — в F10 через `save_property_checklist`; в стартовый шаблон шаг не добавлен, менеджер включает его сам. Названия модулей и пунктов хранятся с переводами (`title` + `title_i18n`) и падают на язык компании (`hosts.default_language`), когда перевода нет; поля редактора переводов — в F10
- [x] **F8. Фото и видео** — шаги `photos_before` / `photos_after` / `video` движка F16 ожили. Файл — две вещи: объект в приватном бакете `task-media` и строка `task_media`, которая говорит, чей он, какому шагу отвечает и дошёл ли (`uploaded_at`). Телефон сначала регистрирует файл (`add_task_media` → путь `host/task/id.ext`), грузит ровно на этот путь (политика бакета сверяет со строкой), потом подтверждает (`confirm_task_media` проверяет, что объект есть). Все три вызова идемпотентны — цепочка переигрывается с начала после потери сети; очередь на диске, ретраи, загрузки по одной. Шаг завершается из таблицы, а не из ответа телефона: `complete_task_step` собирает `media_ids` загруженных, не удалённых файлов, незавершённая загрузка держит шаг. Лимиты шага (`min/max_photos`, `max_video_sec`) с дефолтами сервера (1..10 фото, 30 с). Только камера, без галереи; фото сжимается до 1600 px JPEG 0.8, видео до 30 с и 720p там, где платформа даёт (iOS). Retention 90 дней после закрытия задачи: крон + Edge Function `purge-task-media` удаляет объекты, строки остаются с `purged_at`. Не сделано: ручная сборка/OTA (за владельцем), фоновая загрузка при закрытом приложении (iOS background session — F13), настройка «разрешить галерею» у менеджера (F10), просмотр видео в приложении (только длительность)
