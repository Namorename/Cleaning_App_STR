## Что изменилось против записи в ROADMAP

- **iOS обязателен к L** (решение владельца 2026-09-27). iPhone — основная масса
  телефонов горничных. Аккаунт Apple Developer владелец заводит сейчас.
- **Шаг «принять» идёт вместе с F11** (решение владельца). Сегодня его нет нигде:
  страж переходов его запрещает, телефон кнопки не знает (раздел 2).
- **Экран «Настройки»** (дополнение владельца 2026-09-28, раздел 3):
  - уведомления по отдельности, выбор хранится на сервере;
  - состояние системного разрешения;
  - язык;
  - смена пароля.
- **Горизонт в 7 дней ломает событие «новая уборка»** (1.1). Это новая находка,
  нужно решение.
- **SDK 58 в бете с 15.09.** В нём push на переднем плане показывается по
  умолчанию. Мы остаёмся на SDK 57 и пишем обработчик явно. Подъём SDK — натив,
  его место в сборке редизайна (5.3).
- **Сборка для горничных — одна, после редизайна** (без изменений). Сборки F11
  тестовые: APK на телефон владельца и iOS в TestFlight для внутренней проверки.

**Найдено в работе, к решению владельца (2026-09-28):**
- **Очередь действий без связи на деле не копит.** `onlineManager` TanStack ни к
  чему не подключён: NetInfo или `expo-network` в приложении нет, а слушатель по
  умолчанию (`window.addEventListener('online')`) в React Native не работает —
  телефон для TanStack всегда «в сети». Поэтому действие без связи не встаёт на
  паузу, а после одного повтора через секунду падает с ошибкой; на паузу оно
  уходит, только если приложение свернули в эту секунду. Это старое поведение, не
  F11, но обещание «нажала на лестнице — уйдёт, когда появится связь»
  (`lib/query-client.ts`) сейчас не выполняется ни для ходов уборки, ни для шагов,
  ни для чата. Варианты:
  - **(а) без сборки, OTA:** сетевую ошибку считать признаком офлайна —

сотруднику с токеном — сколько уборок у него сегодня и сколько вошло в неделю
сегодня (день = местное сегодня + 7). Пусто — не шлём. Одна на человека в день
(уникальный индекс).

**Свёртка — в функции отправки, на TypeScript**, чистая функция с тестами. SQL
выдаёт группу `(получатель, ключ свёртки)`, только когда созрела её **последняя**
строка (`max(send_after) <= now()`): новое событие по той же уборке отодвигает
отправку. Порядок старшинства внутри группы:
- последнее — отмена или снятие, а в группе было назначение или новая: ей ничего
  не успели сказать → не шлём ничего; иначе шлём последнее;
- в группе есть назначение или новая → одно «назначена/новая» с итоговым днём;
- переносы → один, «откуда» первого и «куда» последнего; совпали → ничего;
- иначе — окно.

Аренда `claimed_until`. `DeviceNotRegistered` из тикета или квитанции удаляет
токен.

## 1. События

### 1.1 Горизонт: что горничная вообще видит

Уборку генератор создаёт до 90 дней вперёд. Горничная видит задачу только в
пределах `task_horizon_days() = 7` (`20260904140000_task_horizon.sql:21-27`): каждая
клиентская политика `tasks` содержит `not task_is_beyond_horizon`. Считается она в
**поясе листинга** (`properties.timezone`, там же `:48-51`), с отсрочкой 1 день.

**Правило для всех событий по уборкам:** push идёт, только если старый **или**
новый день уборки попадает в окно `[сегодня − 1, сегодня + 7]` в поясе листинга.
Проверка — через те же `task_is_beyond_horizon` и `task_grace_days`, без новой
арифметики. Примеры:
- перенос с +30 на +31 — тишина;
- с +30 на +2 — push: уборка вошла в неделю;
- с +2 на +30 — push: уборка ушла из её списка.

**Отсюда вопрос о «новой уборке».** Большинство уборок рождается за горизонтом, и
push при создании о них не нужен. Горничная узнаёт о них, когда они входят в
неделю, а это ход времени, а не событие в базе. Варианты:
- **(а) Утренняя сводка** (предлагаю): раз в день в 07:00 по Праге — «Сегодня 2
  уборки; на неделе появились 3 новые». Один push в день, по крону.
- **(б) Только события внутри недели:** новая уборка в пределах 7 дней (бронь
  «на завтра»), без сводки.
- (а) и (б) совместимы: (б) — срочное, (а) — фон.

### 1.2 События, которые назвал владелец

**Кто действует** (`auth.uid()` читает `request.jwt.claims`; проверено критиком):
- генератор вызывают только `process-webhook-events` и `sync-reservations`
  секретным ключом, `EXECUTE` у него только у `service_role`. Никакой путь
  менеджера не зовёт его внутри своей транзакции, поэтому `auth.uid()` там пуст;
- метёлка (`pg_cron`) — тоже пуст;
- `save_task`, `cancelLiveTask`, `assign_problem`, `set_property_status` — `uid`
  менеджера;
- горничная сама себе push не шлёт.

| Событие | Кому | Откуда в коде | Условие |
|---|---|---|---|
| **Новая уборка** | назначенной горничной | генератор, `inserted` (`20260927120000_pinned_rooms.sql:746-760`); менеджер — `save_task` | внутри недели; иначе — сводка |
| **Уборка отменена** | исполнительнице, если старый статус не `done`, `cancelled`, `expired` (в том числе `in_progress`: менеджер может отменить идущую работу) | генератор `dropped` (`:891-907`); менеджер — `cancelLiveTask` (любой открытый статус, `cancel-live-task.ts:5,28`), `set_property_status`; ремонты — `cancel_problem`, `archive_problem` | внутри недели. `expired` от метёлки push не даёт |
| **Уборка перенесена — за бронью** | исполнительнице | генератор `moved` (`:781-817`, другой день; сюда же выезд, поправленный задним числом) и `relocated` (`:624-680`, другая комната) | внутри недели. `accepted` при смене дня уже возвращается в `assigned` (`:789-794`), и текст просит принять заново |
| **Уборка перенесена менеджером** | исполнительнице | `save_task` с `p_expected_date` (`:415-434`) | внутри недели |
| **Назначение** | новой исполнительнице | `save_task` (`:440-468`), проход генератора `taken` (`:857-870`), `assign_problem` (ремонт — технику, «работа») | внутри недели |
| **Сообщение в чате** | аудитории ветки, кроме автора | `send_message` (`20260924110000_chat_rpc_race.sql:172-252`) | всегда; ветки `direct` — после слоя 6 |

Из ROADMAP (`:356-358`):
- **Свободная уборка** (`claim`) — горничным листинга, когда неназначенная уборка
  появилась или освободилась внутри недели.
- **Бронь отменена во время уборки** — сегодня этого не видит никто: генератор
  `in_progress` и `paused` не трогает (`:640, 802, 896`). Нужен триггер на
  `reservations.status`. Upsert синхронизации переписывает все колонки
  (`20260912130000:158-170`), поэтому нужно условие
  `when (old.status is distinct from new.status)`.

Push не идёт на правки колонок, которые не меняют ни статус, ни день, ни
комнату, ни исполнителя, ни окно (заметка, длительность и т.п.).

**Аудитория ветки чата** (вопрос 6). `chat_participates` для ветки уборки
пускает менеджеров, исполнительницу **и всех горничных, привязанных к листингу**
(`20260918120000_chat.sql:178-185`). Push всем на каждое сообщение — шум.
Предлагаю:
- ветка уборки — исполнительнице и тем, кто уже писал в ветке;
- ветка задания — автору задания и исполнителю ремонта;
- менеджерам push не идёт: у панели опрос (ROADMAP `:374`).

**Кандидаты при этом обязаны быть участниками прямо сейчас.** Писавшая могла
потерять привязку к листингу, уборка могла уйти за горизонт, учётку могли
отключить. `chat_participates` узнаёт вызывающего только через `auth.uid()`
(`chat.sql:171-174`), а триггер работает от имени автора. Поэтому:
- правило участия выносится в ядро с профилем в параметре:
  `chat_participates_as(profile, …)` и `cleans_property_as(profile, property)`;
- политики и RPC остаются обёртками над ядром с `auth.uid()`;
- аудитория = кандидаты, отфильтрованные ядром. Фильтр повторяется при отправке
  (`claim_push_batch`);
- тест держит: кандидат, не прошедший ядро, push не получает;
- то же ядро нужно для push о свободной уборке (кто видит очередь `claim`);
- `EXECUTE` у `authenticated` на ядра отозван.

### 1.4 Свёртка, срок жизни, тихие часы, срочность

- **Свёртка.** Строка outbox получает `send_after = now() + 60 s`. Отправитель
  берёт строки одного получателя по одной уборке и шлёт итоговое состояние.
  - Уборку перенесли и вернули — не шлёт ничего.
  - Несколько сообщений в ветке — одно «3 новых сообщения».
  - На телефоне `collapseId` (iOS) и `tag` (Android) равны id уборки или ветки:
    новое уведомление заменяет прежнее.
- **Срок жизни считается от `send_after`, а не от создания строки:**
  `expire_at = send_after + 30 мин`. Иначе всё, что отложено тихими часами,
  умирало бы неотправленным. Просроченное помечается, а не шлётся — после
  простоя функции не придёт пачка устаревших push.
- **Тихие часы** (вопрос 3). Генератор назначает пачкой в 03:10–03:35 UTC — это
  05:10–05:35 по Праге сейчас и 04:10–04:35 после 25.10. Предлагаю 21:00–07:00 по
  Праге:
  - у несрочного `send_after` ставится на 07:00;
  - срочное идёт сразу. Срочное — отмена, перенос, снятие, бронь отменена во время
    уборки, когда уборка **сегодня или завтра**.
- **Пояс для тихих часов и сводки.**
  - У `hosts` колонки пояса нет (`database.types.ts:329-338`), `cron.timezone` —
    GMT. Пояс держит одна функция с константой `Europe/Prague` и комментарием;
    колонка `hosts.timezone` появится с мультитенантностью (F25).
  - Сводка идёт кроном раз в час с проверкой местного часа, чтобы переход на зимнее
    время её не сдвигал.
- **Срочность на телефоне** (вопрос 4):
  - Android: каналы `urgent` (высокая важность, звук) и `general` (обычная);
  - iOS: `interruptionLevel: time-sensitive` для срочного — пробивает режимы
    фокусировки, пользователь может это выключить. Entitlement
    `com.apple.developer.usernotifications.time-sensitive` одобрения Apple не
    требует, EAS включает его сам (capability sync). Это натив, решается до
    сборки;
  - `sound: 'default'` в каждом сообщении: без поля iOS показывает push
    беззвучно. Android звук берёт из канала;
  - «Критические» уведомления iOS требуют одобрения Apple — не предлагаю.

## 2. Шаг «принять»

**Что сейчас.**
- `accepted` есть в enum, в схеме телефона и в `OPEN_STATUSES`.
- Уже понимают `accepted` и не требуют правок (проверено критиком):
  - генератор;
  - метёлка;
  - зеркало заданий (`accepted` → задание `assigned`);
  - снимок шагов (срабатывает на любой переход в `in_progress`);
  - фильтры панели и подпись «Принята».
- Страж `guard_task_transitions` (`20260908120000_task_start_window.sql:66-72`) даёт
  исполнителю только `unassigned→assigned`, `assigned→in_progress`,
  `in_progress→done`.
- На телефоне `TaskAction = claim | start | finish`, `availableAction` отдаёт одно
  действие (`schema.ts:118-132`). `startTask` идёт только из `assigned`
  (`api.ts:204-206`).

**М2 — сервер.**
- Страж: исполнителю разрешены `assigned→accepted` и `accepted→in_progress`, окно
  старта — то же.
- **`accepted` сбрасывается в `assigned`,** когда меняется то, что она принимала:
  - `save_task` при передаче другой горничной
    (`20260927120000_pinned_rooms.sql:440-449`, сейчас статус сохраняется);
  - `save_task` при переносе дня менеджером — так уже делает генератор при смене
    дня (`:789-794`), а ручной перенос сейчас оставляет `accepted`;
  - `assign_problem` при новом исполнителе ремонта (`20260923130000:325`,
    `else t.status`).
  - На каждый случай — SQL-тест.
- **Свободная уборка:** взяла сама — значит, приняла? (вопрос 5) Если да,
  `WITH CHECK` политики `claim` (`20260905094000_tenant_host_id.sql:245-247`)
  пускает `accepted`, и `claimTask` пишет `accepted`. Иначе ей нужно два нажатия
  подряд, и «не приняты на завтра» засоряется.
- **Архивация объекта и `accepted` — решение владельца** (вопрос 5б).
  - Сейчас это **намеренное** правило: «accepted counts as started», принятая
    остаётся за горничной (`20260924170000_archive_cancels_midstay.sql:88-89`).
    Три функции должны говорить одно (`:13-15`: `set_property_status`,
    `property_open_cleanings`, `open_cleanings_by_listing`), тест
    `property_units.sql:539-542` это держит.
  - Пока `accepted` никто не пишет, правило ничего не стоит. С кнопкой «Принять»
    почти каждая назначенная уборка станет `accepted`, и архивация объекта
    перестанет отменять их.
  - Предлагаю отменять и `accepted` (с push «уборка отменена»), поменяв все три
    функции, число в диалоге и тест вместе.

**Т1 — телефон.**
- Запись: `update … set status = 'accepted' where id = … and status in
  ('assigned','accepted')`. Повтор после потери сети совпадёт со своей строкой, и
  страж пропустит переход в тот же статус.
- 0 строк остаётся **отказом**, как у `moveTask` (`api.ts:177-182`): уборку могли
  отдать другой, отменить или унести за горизонт.
- `startTask` — из `assigned` или `accepted`. `availableAction` отдаёт список: у
  `assigned` — «Принять» и «Начать», когда откроется окно.
- Ключ мутации `['tasks','accept']` регистрируется до восстановления кэша. Тест
  ключей мутаций и ключи i18n на трёх языках.
- **Обязательность** (вопрос 5): «принять» — сигнал менеджеру, а не замок.
  «Начать» доступна и без принятия, иначе забывшая нажать горничная не сможет
  работать у двери.
- Кнопку «Принять» прямо в уведомлении не делаем: действие без открытой сессии —
  отдельная работа после L.
- Т1 — чистый JS: `main` и OTA после `db push`, без сборки.

## 3. Экран «Настройки»

Внешний вид минимальный, п.5 перекрасит.

### 3.1 Уведомления по отдельности — выбор на сервере

- **Переключатель на каждый вид события** (список — раздел 1 после ответов на
  вопросы 7): новая уборка, отменена, перенесена, назначение, сняли с уборки,
  окно изменилось, свободная уборка, бронь отменена во время уборки, сообщение в
  чате, утренняя сводка. Все включены по умолчанию.
- **Хранится на сервере:** `push_preferences(profile_id, muted push_kind[],
  updated_at)`.
  - Хранится список **выключенных**. Новый вид события после L придёт всем без
    переноса данных.
  - `push_kind` — тот же enum, что у outbox.
- **Запись** — `set_push_preference(p_kind, p_enabled)`. Передаётся значение, а не
  «переключить», поэтому повтор после потери сети даёт тот же итог. Мутация
  `offlineFirst`, как остальные.
- **Чтение** — `fetchMyPushPreferences`:
  - `select` своей строки, RLS `profile_id = auth.uid()`;
  - в `READERS` теста select;
  - на диске через `readCached`, новый ключ схемы с `.default`;
  - вид, которого старый бандл не знает, отбрасывается через `.catch`.
- **Выбор проверяет рассылка, а не телефон.** `claim_push_batch` отбрасывает
  строки, чей вид у получателя выключен, **в момент отправки**. Выключение
  действует и на то, что уже стоит в очереди.
- **Два слоя.** Системные настройки (разрешение, каналы Android) горничная меняет
  в самом телефоне; мы их только показываем (3.2). Переключатели событий —
  наши, на сервере.

### 3.2 Уведомления запрещены в системе

### 3.3 Язык — переиспользуем то, что есть

- **Факт, который расходится с формулировкой задачи:** выбора языка при первом
  запуске на телефоне сейчас **нет**.

- **Переиспользуем, второго механизма нет:**
  - колонку `profiles.preferred_language`. Выбор горничной и выбор менеджера — одно
    поле, побеждает последний; панель показывает текущее значение;
  - `applyLanguage()` (`i18n/index.ts:68-73`);

  - три пункта ru / en / cs;
  - сразу `applyLanguage()`, не дожидаясь сети;

    и страж колонку не замораживает, но одна точка с проверкой enum не расширяет
    то, что клиент пишет в `profiles` напрямую.
- Push идёт на том же языке автоматически: сервер берёт `preferred_language`

### 3.4 Смена пароля, пока горничная вошла

- Форма: текущий пароль, новый, повтор.
- **Только онлайн**, очереди нет: без сети — «Нужна сеть».
- **Порядок** (уточнён 2026-09-28 исследованием `wf_1d913c27-94a`):
  1. `signInWithPassword(email сессии, текущий)` — это и есть проверка текущего
     пароля. Неверный — «Текущий пароль неверный» (`invalid_credentials`).
     Повторный вход даёт **новую сессию**, а «Secure password change» требует
     кода из письма, только если сессии больше 24 часов (`session.CreatedAt`,
     supabase/auth v2.197.0 `internal/api/user.go#L154-L165`).
  2. `updateUser({ password: новый, current_password: текущий })`. Текущий пароль
     рядом с новым нужен отдельной настройке «Require current password» (GoTrue
     v2.190+), пока она выключена, он ничего не меняет.
  3. **Другие входы закрывает сам Auth** — `UpdatePassword` зовёт
     `LogoutAllExceptMe` (v2.197.0 `internal/models/user.go#L459-L462`; опыт: две
     сессии до смены, одна после). Собственный `signOut({ scope: 'others' })`
     убран: он мог только упасть и сказать «выйти на других устройствах не
     удалось», что было бы неправдой. Решение 15 держит сервер.
- **Ошибки — по коду GoTrue, в ключи i18n:** `weak_password`, `same_password`,
  `over_request_rate_limit`; `current_password_invalid` и
  `current_password_required` — «Текущий пароль неверный»;
  `reauthentication_needed` — «Вход нужно подтвердить заново. Нажмите «Сменить
  пароль» ещё раз» (бывает, только если обновление токена обогнало вход шага 1;
  второе нажатие проходит). Неизвестная — общая переведённая фраза, серверный
  текст мелко под ней (правило `CLAUDE.md`).
- **Длина:** `minimum_password_length` локально 6 (`supabase/config.toml:182`).
  Облачное значение сверить; клиент проверяет ту же длину до отправки.
- **`secure_password_change`:** локально `false` (`supabase/config.toml:232`).
  Облако — Dashboard → Authentication → Providers → Email.
  - **Включить можно — смену пароля в «Настройках» это не ломает** (проверено
    2026-09-28 на отдельном GoTrue v2.195.0 с флагом, без SMTP): сессия старше
    25 часов получила `reauthentication_needed`, а порядок «Настроек» (вход →
    смена) прошёл. Путь «код из письма» приложение не использует. Флаг читается

    `manage-staff`) и вход в обоих приложениях он не трогает.
  - Облако — v2.197.0 или его сборка (по `auth.schema_migrations`); правило там
    то же, что в v2.195.0 и в master.
  - Проверить на облаке учёткой, которую назовёт владелец: на телефоне, вошедшем
    больше суток назад, сменить пароль в «Настройках» — ждём успех и выход на
    других устройствах.
- Менеджер после смены пароль не знает — и не должен. Сброс остаётся у него

## 4. Схема и функция отправки

### М1 — получатель

- **`push_tokens`:**
  - колонки: `token` (уникален, формат `ExponentPushToken[…]`), `profile_id`,
    `host_id`, `platform` (`ios` | `android`), `language` (язык устройства —
    запасной), `app_version`, `created_at`, `updated_at`;
  - `register_push_token(p_token, p_platform, p_language, p_app_version)` —
    `definer`, upsert по токену. На общем телефоне токен **переходит** к тому, кто
    вошёл. У профиля не больше 5 токенов;
  - `unregister_push_token(p_token)` удаляет только свой токен;
  - права: у `authenticated` ничего, клиент ходит только через RPC. Матрица
    `table_grants.sql` сегодня не умеет таблицу без прав (`:100-105`, `privs not
    null`) — тест расширяется пустой строкой прав в той же миграции.
- **`push_preferences`** (3.1): `select` своей строки, запись только через RPC.
- **`set_my_language(p_language)`** (3.3).
- Неактивный профиль push не получает: фильтр в `claim_push_batch`, токен не
  удаляется.

### М3 — outbox, аудитория, триггеры, кроны

- **`raw.push_outbox`** в схеме `raw`, закрытой клиентам.
  - В строке нет текста: получатель, вид события, id уборки или ветки, ключ i18n,
    параметры подстановки (jsonb), срочность, `send_after`, `expire_at`, аренда
    (`claimed_until`), `sent_at`, тикет Expo, попытки.
  - Правило «текст не хранится на сервере» в базе соблюдено. Отступление одно:
    функция отправки сама переводит ключ на язык сотрудника (вопрос 1).
- **Outbox нужен,** потому что `invoke_edge_function` шлёт пустое тело
  (`20260827210000_scheduled_jobs.sql:55`).
- **Триггеры на `tasks` — два, уровня оператора.**
  - `after insert` с `new table` и `after update` с `old table`/`new table`; одна
    функция ветвится по `TG_OP`.
  - Один триггер на `insert or update` с таблицами переходов PostgreSQL не
    принимает; `update of <колонки>` с ними тоже (опыт критика на PG 17.6).
  - **Функции — `security definer` с `set search_path = ''`**, как
    `guard_task_fields`. Иначе после выката любая запись в `tasks` от горничной или
    менеджера падает на «permission denied for schema raw», даже без единого
    токена (опыт критика). SQL-тест: переход горничной при установленной М3.
  - Проходы генератора — отдельные операторы (`20260927120000:624-907`), поэтому
    за прогон триггер срабатывает 6 раз. На пустых проходах таблицы переходов
    пусты, это дёшево.
  - Строки пишутся **только для получателей с токеном**. До первой регистрации
    триггер ничего не пишет.
  - **Замер:** 97-дневный прогон генератора с триггерами и без, парами вперемежку,
    после ANALYZE (урок 26.09), в бюджете 8 с (`20260923120000:107-109`).
- **Триггер на `chat_messages`** — построчный `after insert`, аудитория 1.2. Фото
  приходят после строки (`media_expected`); если текста нет — ключ «прислал
  фото».
- **Триггер на `reservations`** — `after update of status`, построчный, с `when`
  (1.2).
- **RPC функции отправки** (`service_role`; `EXECUTE` у `authenticated` отозван —
  по умолчанию он выдаётся, `20260926100000_grants_hygiene.sql:108-109`):
  - `claim_push_batch()` —
    - `for update skip locked` и **аренда**: `claimed_until = now() + 2 мин`,
      арендованные строки пропускаются. Одной блокировки мало: она кончается с
      коммитом RPC, ещё до вызова Expo, а прогоны могут перекрыться (таймаут
      `pg_net` 120 с, повторы на 429);
    - фильтры: `send_after <= now()`, не просрочено, профиль активен, вид не
      выключен (3.1), для чата — ядро участия (1.2);
    - свёртка;
    - язык: `preferred_language` → язык токена → `hosts.default_language`;
  - `record_push_tickets(…)` — отмечает отправленное;
  - `drop_push_tokens(tokens[])` — для `DeviceNotRegistered`.
  - Тест: две перекрывающиеся выдачи не отдают одну строку дважды.
- **Кроны:**
  - `send-push` раз в минуту. Не раз в 30 с: `cron.log_run` включён, а
    `cron.job_run_details` не чистится нигде; уже сегодня `process-webhook-events`
    пишет туда 720 строк в день;
  - утренняя сводка — раз в час, если взята;
  - чистка `cron.job_run_details` старше 7 дней — раз в сутки.
  - Заданий станет 8–10 против 7. Поправить проверки, которые их считают:
    `docs/rollout/postpush_window3.sql:48,135-141`, `postpush_package.sql:18,43-46`,
    `prelaunch_probe.sql:190`, `window3_probe.sql:184`.
- Чистка отправленных строк outbox старше 7 дней — в самой функции.

### Ф — Edge Function `send-push`

- Шаги: забрать пачку → собрать текст → отправить в Expo → записать тикеты →
  разобрать квитанции → почистить старое.
- **Expo Push API:**
  - `https://exp.host/--/api/v2/push/send`, до 100 сообщений в запросе, gzip;
  - `priority: high` — на Android обычный приоритет спит в Doze, на iOS
    «normal» Apple может не доставить;
  - `sound: 'default'`;
  - `channelId`, `collapseId`, `tag`, `threadId`, `interruptionLevel`;
  - на 429 и 5xx — повтор с растущей паузой.
- **`DeviceNotRegistered`** — и в тикете, и в квитанции → удалить токен.
  `InvalidCredentials` и `MismatchSenderId` — в лог ошибкой: это сломанные ключи
  FCM или APNs. Квитанции — через 15 минут, до 1000 id за запрос.
- **Токен доступа Expo** («enhanced security») — секрет функции
  `EXPO_ACCESS_TOKEN`. Без него любой, узнавший токен устройства, может слать на
  него push от имени проекта (подробности — 7.6).
- **Тексты.**
  - Ключи `push.*` живут в общих `locales/{ru,en,cs}.json`, тест паритета держит
    три языка.
  - Функция берёт копию только `push.*` в своей папке, не в `_shared`: правка
    `_shared` требует передеплоя всех функций. Тест сверяет копию с `locales`.
  - Дата — в поясе листинга, формат — как `formatDay` панели.
  - Названия — объект (листинг) и имя автора сообщения.
- **Тесты** — `deno test` с подменой `fetch` через `fetchImpl`, как в
  `_shared/hostaway.ts:36,73`: пачки по 100, 429, тикеты и квитанции, свёртка,
  язык, выключенный вид события.
- `verify_jwt` остаётся включённым: функцию зовёт только крон секретным ключом.

- **Тесты:** мок `expo-notifications` в `jest.setup.ts`; новые `fetch*` — в

## 7. Android: что нужно от владельца (Firebase и FCM)

Бесплатно: FCM ничего не стоит ни на Spark, ни на Blaze. Mac не нужен.

**Где запускать команды.** `eas-cli` без терминала сам уходит в неинтерактивный
режим и падает на первом вопросе: «Input is required, but stdin is not readable»
(`eas-cli` `commandUtils/flags.js`, `prompts.js`; в оболочке Claude Code
`stdin.isTTY` пуст). Поэтому:
- команды **с меню или входом** — в **своём окне** PowerShell или Windows Terminal,
  из папки `apps/mobile`;
- через `!` в этой сессии — только команды, где всё задано флагами.

1. **Firebase:** https://console.firebase.google.com → «Add project» → имя
   («STR Ops») → Google Analytics можно выключить.
2. **Приложение Android:** значок Android → package name **`cz.strops.cleaner`**
   (ровно так, `app.json:16`) → Register app → скачать **`google-services.json`**.
   Шаги с SDK Firebase пропустить: Expo делает их сам.
3. **Файл в EAS, не в репозиторий** (всё флагами, можно через `!`):
   `npx eas-cli env:set --name GOOGLE_SERVICES_JSON --type file --value ./google-services.json --visibility secret --environment preview --environment production`.
   Файл потом держать вне репозитория.
4. **Ключ сервисного аккаунта (секрет!):** Firebase → шестерёнка → Project
   settings → Service accounts → «Generate new private key» → JSON. Не в
   репозиторий и не в чат.
5. **Ключ в EAS** — в своём окне: `npx eas-cli credentials -p android` → профиль
   `preview` → Google Service Account → «Manage your Google Service Account Key
   for Push Notifications (FCM V1)» → Set up → «Upload a new service account key».
   - Или без терминала: expo.dev → проект → Credentials → Android → FCM V1 service
     account key.
   - Ключ хранится в EAS на идентификатор приложения. После загрузки файл
     удалить.
6. **Токен доступа Expo для отправки** — после деплоя функции (шаг 7 выката).
   - **Переключатель «Enhanced security» — на уровне аккаунта**
     (expo.dev → аккаунт `namorenames-team` → Settings → Access tokens) и
     действует на все проекты аккаунта.
   - Токен — от **робота** (robot user) с наименьшей ролью, которой хватает на
     отправку (проверить одним `curl`), а не личный. Личный токен даёт власть над
     всеми учётными данными, сборками и отправками аккаунта.
   - Токен владелец ставит секретом функции в Supabase. Переключатель включается
     **после** деплоя функции с токеном: с ним Expo отвергает push без токена
     (`UNAUTHORIZED`).

### 8.1 Аккаунт Apple Developer

- $99 в год, Apple ID с двухфакторной проверкой.
- **Частное лицо или организация** (вопрос 10):

### 8.2 Ключ APNs

- **(а) Пусть EAS создаст ключ сам** (предлагаю). При первой `eas build -p ios`
  CLI спросит «Setup Push Notifications for your project?» — «да». EAS создаст
  ключ APNs, сохранит у себя и включит Push у App ID (capability sync). Файл
  `.p8` владельцу не достаётся и потеряться не может.
- **(б) Вручную**, если EAS не справится:
  - https://developer.apple.com/account → Certificates, IDs & Profiles → Keys → «+»;
  - имя → Apple Push Notifications service (APNs) → Configure → окружение
    **Sandbox & Production**, тип **Team Scoped** → Continue → Register;
  - **Download — `.p8` скачивается один раз**. Записать Key ID и Team ID;
  - в своём окне `npx eas-cli credentials -p ios` → Push Notifications → загрузить
    `.p8`, Key ID, Team ID;
  - ключ годится для всех приложений аккаунта и не истекает.
- **Окружение.** TestFlight и ad hoc работают с **production** APNs. Плагин ставит
  `aps-environment: development`, Xcode при сборке выпуска меняет его на
  `production`.

### 8.3 Сборка iOS в облаке EAS — без Mac

- Сборка идёт на Mac Expo в облаке. С Windows работают `eas build -p ios` и
  `eas submit`; локальная сборка iOS на Windows невозможна.
- **Первая сборка — в своём окне владельца:**
  `npx eas-cli build -p ios --profile <профиль TestFlight>`. Дальше:
  - вход Apple ID и код 2FA;
  - выбор команды;
  - EAS регистрирует bundle id `cz.strops.cleaner`, создаёт сертификат
    распространения (один на аккаунт) и профиль (12 месяцев), включает Push;
  - ключ APNs — 8.2(а).
- **Первая отправка — тоже в своём окне, с Apple ID.** Создание записи
  приложения в App Store Connect ключ API не поддерживает (`eas-cli`
  `ensureAppExists.js`).
  - Имя записи берётся из `submit.<профиль>.ios.appName`, иначе из `name` —
    «STR Ops Клинер».
  - Имя должно быть уникальным во всём магазине. Если оно занято, `eas-cli`
    молча добавит случайный хвост. Поэтому `appName` задаётся заранее (вопрос 10),
    или запись создаётся руками в App Store Connect.
- **Дальше — без интерактива, ключом App Store Connect API:**
  - один раз Account Holder нажимает «Request Access» в App Store Connect →

    Manage your API Key» создаст его сам;
  - им работают следующие `eas build` и `eas submit` без 2FA.

  - 15 сборок iOS и 15 Android в месяц, очередь низкого приоритета, одна сборка за
    раз, 45 минут на сборку;
  - сверх квоты — ждать первого числа месяца;
  - EAS Update — 1 000 активных устройств в месяц.
  - Нам хватает. Если очередь станет мешать — Starter $19 в месяц.

### 8.4 TestFlight: проверка, раздача, 90 дней

- **Отправка:** `eas submit -p ios` или `--auto-submit` у `eas build`. В TestFlight
  сборка появляется через 10–15 минут. `eas submit` сам заводит внутреннюю группу
  «Team (Expo)».
- **Внутренняя группа — проверка в F11:**
  - до 100 человек, ревью Apple нет;
  - тестировщик — **пользователь App Store Connect** (Admin, App Manager,
    Developer или Marketing). Владелец — Account Holder, он уже тестировщик;
  - если iPhone для проверки не владельца, его хозяин добавляется в Users and
    Access (вопрос 10).
- **Внешняя группа — горничные, после редизайна (п.6):**
  - до 10 000 человек, приглашение по почте или публичной ссылкой;
  - **первая сборка версии проходит Beta App Review** (обычно меньше суток);
    следующие сборки той же версии — часто без полного ревью;
  - в «Test Information»: описание беты, почта для отзывов, **ссылка на политику
    конфиденциальности** (Apple требует её у всех приложений; точный перечень
    полей сверить в App Store Connect) и **демо-учётка для рецензента**
    (правило 2.1) — вопросы 11 и 17;
  - горничной нужны Apple ID и приложение TestFlight: ставит TestFlight →
    открывает ссылку → «Установить».
- **90 дней.** Каждая сборка в TestFlight живёт 90 дней. Потом установленная
  сборка **перестаёт открываться** — это остановка работы горничной, а не
  неудобство.
  - OTA продлевает только JavaScript: новый бинарник нужен раз в ≤90 дней, даже
    если натив не менялся.
  - **Напоминание в двух слоях** (вопрос 12):
    - дата сборки и крайний срок — в ROADMAP («Эксплуатация»), у владельца —
      событие в календаре на 75-й день;
    - в рецепт OTA (перед каждым `eas update` уже сверяется `migration list`)
      добавляется строка: «дней с последней iOS-сборки для поля > 75 → сначала
      пересборка».
  - Годовые сроки рядом: членство Apple и профиль распространения — 12 месяцев.
    Тоже в календарь.
- **Правило 2.2 App Review:** бета в TestFlight должна быть «предназначена для
  публичного распространения». Внутреннее приложение годами на TestFlight — серая
  зона. Путь на потом — **Unlisted** (8.7).

### 8.5 Проверка на настоящем iPhone

Две проверки, обе обязательны.

**В F11 — сборка 1.1.0 из внутренней группы TestFlight:**
1. Первый запуск: экран-пояснение, системный запрос, «Разрешить».
2. Токен появился в `push_tokens` (платформа `ios`).
3. Push в трёх состояниях: приложение на экране, в фоне, **выгружено
   смахиванием**. Со звуком.
4. Нажатие на холодном старте открывает нужную уборку или ветку чата; «сняли с
   вас» ведёт в список.
5. Срочный push проходит «Фокус» и «Не беспокоить», если взят time-sensitive.
6. Экран блокировки при «Показ миниатюр: Когда разблокировано» и «Всегда».
7. «Настройки»: выключенный вид события не приходит; при запрете в системе —
   плашка и переход в настройки iOS; смена языка меняет и язык push; смена
   пароля.
8. OTA доходит до iOS-сборки (два холодных запуска).
9. После выхода push этой горничной на телефон не приходят.
10. Камера и галерея: новые строки разрешений.
11. Событие Sentry с читаемым стеком, если Sentry взят.
12. Почта от Apple после загрузки (манифест приватности) — прочитана и учтена.

**Перед раздачей горничным (п.6) — гейт.**
- Та же проверка на финальной сборке из **внешней** группы TestFlight — путь, которым
  пойдут горничные.
- Лучше на iPhone горничной, а не владельца: другая версия iOS, другие настройки.
- Без отметки «проверено на iPhone» ссылка горничным не рассылается. Строка в
  ROADMAP, п.6.

### 8.6 Чем iOS отличается от Android

| Что | iOS | Android |
|---|---|---|
| **Разрешение** | системный запрос **один раз за установку**; после отказа — только сам человек в Настройках | Android 13+: у новой установки выключено до запроса; после **второго** «Запретить» запрос больше не показывается; Android 12 и ниже — разрешено сразу |
| «Тихое» разрешение | provisional: без запроса, но только Центр уведомлений, без звука — не для срочного | нет |
| **Приложение выгружено** | обычный push показывает система; «тихий» фоновый push после смахивания не доставляется и дросселируется (2–3 в час) — мы его не используем | обычный push показывает система; после «Остановить» в настройках — ничего до ручного запуска; у Xiaomi и подобных — ещё экономия батареи |
| **Приоритет** | «normal» Apple может не доставить — шлём `high` | «normal» ждёт выхода из Doze — шлём `high`; FCM понижает `high`, если push неделями не показываются |
| **Звук** | только если в push есть `sound` (`default` или файл из бинарника < 30 с); беззвучный режим глушит | задаёт **канал**, после создания не меняется |
| Срочность | `time-sensitive` пробивает «Фокус» (entitlement) | важность канала; «Не беспокоить» — по исключениям пользователя |
| **Экран блокировки** | «Показ миниатюр»: всегда / когда разблокировано / никогда — выбирает пользователь | `lockscreenVisibility` канала и настройки системы |
| Группировка | `threadId` | `tag` (замена) |
| Значок на иконке | число из push (`badge`) | не во всех лаунчерах |
| На переднем плане | на SDK 57 без обработчика не показывается | так же |
| Токен | переживает переустановку | переустановка может сменить |

Для Android-телефонов горничных (Xiaomi и т.п.) — памятка «Автозапуск» и «Без
ограничений» батареи в п.6, вместе с раздачей.
