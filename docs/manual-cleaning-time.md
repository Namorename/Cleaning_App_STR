# Ручное время уборки

Шаг 2 плана выката (`docs/rollout-plan-1028.md`). Ветка `manual-time-1029` от `main`
`a167849`, миграция `20261027120000_manual_cleaning_time.sql` — **черновая, со стражем**:
`db push` и `db:reset` на ней останавливаются, пока владелец не скажет «пушим».

## 1. Зачем

Время уборки из брони считает сервер, и любой пересчёт затирает правку менеджера. Теперь
менеджер (или админ) задаёт время одной уборки вручную, и оно выше автоматики: пока уборка
стоит на том же дне, ни вебхук, ни ночная сверка, ни генератор его не трогают. Одна кнопка
возвращает время брони.

## 2. Где время определяется сейчас (до ветки)

**Поля `tasks`:**

| Поле | Что это |
|---|---|
| `scheduled_date` | день уборки; у уборки из брони — день выезда |
| `time_from` | «начать не раньше»: выезд гостя (`reservations.check_out_time`, иначе час листинга) |
| `time_to` | «закончить до»: заезд следующего гостя в тот же номер, иначе час заезда листинга |
| `due_at`, `priority`, `guests_count` | следующий заезд: срок, срочность (SDT), сколько гостей |
| `pinned_arrival`, `pinned_departure`, `pinned_rooms` | ручной перенос дня (20260926160000, 20260927120000) |

**Кто пишет время уборки из брони:**

- **Генератор** `generate_cleaning_tasks` (последнее тело — `20260927120000_pinned_rooms.sql`).
  - Вызывают его `process-webhook-events` (cron каждые 2 минуты, окно — выезды пачки вебхуков) и
    `sync-reservations` (каждую ночь в 03:15 UTC, от недели назад до 90 дней вперёд).
  - Проходы:
    - вставка новых уборок;
    - перенос в другой номер (relocate);
    - **переназначение (reschedule)** — для неперенесённой уборки пишет день, `time_from`, `time_to`,
      `priority`, `due_at`, `guests_count` из брони при любом расхождении;
    - **освежение (refresh)** — перенесённой менеджером уборке каждый прогон пересчитывает окно на её
      день;
    - отмена.
  - Окно считают две функции с одним правилом: `reservation_cleaning_window` (для дня выезда) и
    `cleaning_turnover_on` (для любого дня).
- **`save_task`** (последнее тело — `20261003110000_tech_rules.sql`). У уборки из брони время,
  присланное панелью, игнорируется: сохранение «оставляет окно сервера». При переносе дня окно
  пересчитывается на новый день.
- **`guard_task_fields`** (последнее тело — `20261003130000`) не даёт исполнителю менять время и день.
- **Ни одна функция** не позволяла менеджеру закрепить время: «время, набранное в панели, не
  удержится» — так прямо было написано в форме (`task-form.tsx`, `hasServerWindow`).

**Кто время читает:**

- **Панель:**
  - `fetchTasks`, `fetchTasksBetween`, `fetchTask` (`TASK_COLUMNS`);
  - строка списка (`task-row.tsx`);
  - плашка календаря (`task-chips.tsx`);
  - форма: время уборки из брони только для чтения.
- **Телефон:**
  - `TASK_COLUMNS` в `apps/mobile/src/features/tasks/api.ts`;
  - карточка (`task-card.tsx`) и экран уборки (`task-detail.tsx`);
  - **кнопка «Начать»** открывается в `scheduled_date + time_from` (`startNotBefore`). Сервер
    проверяет то же самое (`task_start_not_before`, `serverErrors.startTooEarly`).
- **Push:** `push_on_task_change` уже шлёт исполнителю `cleaning_window`, когда у назначенной или
  принятой уборки меняются `time_from`/`time_to` в тот же день и в том же номере — только на
  сегодня и завтра (20261003160000).

Поэтому ручное время встаёт **в те же `time_from`/`time_to`**, а не в новые колонки рядом:
- все читатели — телефон, push, кнопка «Начать», календарь, API — получают его без правок;
- новая колонка только **помечает**, что время ручное, и генератор с `save_task` эту пометку уважают.

## 3. Как устроено

### 3.1 Схема

| Что | Где |
|---|---|
| `tasks.manual_time_on date` | день, на который менеджер задал время; null — время из брони |
| `tasks.manual_time_lost_on date` | день ручного времени, которое снято сменой даты; панель показывает пометку |
| `tasks_manual_time_booking_cleaning` | пометка ставится только уборке из брони (`type = 'cleaning'`, `reservation_id` не null) |
| `tasks_manual_time_one_mark` | одна из двух пометок, не обе |
| `task_event_kind` + `time_set`, `time_auto`, `time_dropped` | виды событий журнала |

### 3.2 RPC

| Функция | Кто | Что делает |
|---|---|---|
| `set_cleaning_time(p_task_id uuid, p_time_from time, p_time_to time, p_expected_date date default null)` | менеджер, админ | пишет время и ставит `manual_time_on` = день уборки; снимает `manual_time_lost_on`; повтор тех же часов ничего не пишет |
| `clear_cleaning_time(p_task_id uuid, p_expected_date date default null)` | менеджер, админ | возвращает окно брони на текущий день (`cleaning_turnover_on`) и снимает обе пометки; на уборке с одной пометкой «снято» только убирает пометку |
| `lock_cleaning_for_time` | никто из клиентов | общие проверки двух RPC |
| `journal_cleaning_time` | триггер | журнал |

**Отказы** (ключи i18n):

| Ключ | Когда |
|---|---|
| `serverErrors.managerOnly` | не менеджер и не админ |
| `taskNotFound` | уборка чужой компании или не найдена |
| `cleaningTimeNotFromBooking` | уборка создана вручную: её время и так никто не перезаписывает |
| `taskClosed` | уборка закрыта |
| `cleaningTimeStarted` | уборка уже в работе |
| `taskMovedMeanwhile` | панель открыта на другом дне |
| `cleaningTimeInvalid` | нужны оба времени, и начало раньше конца |

**Права:**
- `authenticated` — `execute` только на две RPC;
- `anon` — ничего;
- исполнительница не может поменять пометки прямой записью (`guard_task_fields`);
- роли — те же, что правят уборки через `save_task` (`is_manager()`: manager, admin); старший техник не может.

### 3.3 Генератор и `save_task`

- **Переназначение.** Если `manual_time_on` равен новому дню, время не сравнивается и не
  пишется. Если день меняется, пишется окно нового дня, `manual_time_on` → null,
  `manual_time_lost_on` → старый день.
- **Освежение перенесённой уборки.** Время с пометкой не трогается; срок, срочность и число
  гостей освежаются, как раньше.
- **Вставка** (бронь снова живая после отмены). Новая строка берёт ручное время последней
  отменённой уборки той же брони и места, если день тот же. Если день другой — получает
  пометку «снято».
- **Смена номера** внутри листинга ручное время сохраняет: день тот же.
- **`save_task`.** Сохранение без смены дня держит время. Смена дня снимает его и ставит
  пометку (cause `manager`).
- **Строки без пометки** генератор сравнивает и пишет ровно как раньше.
  - Проверка набора: второй прогон подряд — `rescheduled = 0`.
  - Проверка облака — §6.

### 3.4 Журнал

Ручное время пишет свой триггер рядом с `journal_task_change`, в ту же `task_events`.
- **`time_set`** — время задано или изменено. Автор — менеджер.
- **`time_auto`** — менеджер вернул время брони.
- **`time_dropped`** — время снято сменой дня. Cause — `manager`, если день сменил менеджер,
  иначе `booking_changed`; у генератора автор пустой.

`params`:
- `date` — день после изменения;
- `from_date` — день до, если он менялся;
- `manual_on` — на какой день было ручное время;
- `from`, `to` — окно до и после;
- `carried: true` — на вставке, когда бронь снова живая.

Перенос дня пишется раньше сброса времени. Одно снятие пометки «снято» в журнал не пишется: часы не меняются.

### 3.5 Панель

- **Форма уборки из брони, пока её не начали** (`task-form.tsx`, `manual-time-note.tsx`):
  - кнопка «Задать время вручную» открывает поля;
  - «Сохранить» зовёт `save_task`, затем `set_cleaning_time` на день, который оставило сохранение;
  - пока время ещё не сохранено, кнопка «Не задавать вручную» возвращает поля как было.
- **Ручное время:**
  - текст «Время задано вручную…»;
  - кнопка **«Вернуть время по брони»** — один вызов `clear_cleaning_time`, форма закрывается.
- **Время снято сменой даты:**
  - рамка с текстом «Время было задано вручную на {дату}, но дата уборки изменилась — время снова
    считается по брони»;
  - кнопка «Понятно» снимает пометку.
- **Начатая уборка:** поля только для чтения, без кнопок.
- **Строка списка:** рядом со временем «вручную» или «время сброшено: дата изменилась».
- **Плашка календаря:**
  - «· вручную» после времени;
  - «время сброшено» — в подписи плашки (подсказка и экранный диктор).
- **Журнала** в панели пока нет нигде (ни у одной уборки): события лежат в `task_events` для
  дашборда и будущей истории.

### 3.6 Телефон

**Правок нет, OTA не нужна.** Горничная видит время, заданное менеджером: телефон читает те же
`time_from`/`time_to`. Кнопка «Начать» откроется в это время.

Об изменении она узнаёт тем же путём, что и сейчас:
- push `cleaning_window`, если уборка у неё (назначена или принята) и она на сегодня или завтра;
- иначе — при следующем обновлении списка (возврат в приложение, push по другой уборке, через
  30 с на экране).

Нового пути я не придумывал.

## 4. Решение при смене даты (для Романа)

**Ручное время действует, пока дата уборки не менялась** — как предложено.

**Если день уборки меняется** — неважно, кто его сменил:
- бронь сдвинула выезд;
- изменение брони отменило ручной перенос дня;
- менеджер перенёс день в панели.

**Тогда:**
- ручное время снимается, на новый день ставится время брони;
- в `manual_time_lost_on` остаётся день, на который было ручное время;
- в журнал пишется `time_dropped`;
- панель показывает заметную пометку, пока менеджер не нажмёт «Понятно» или не задаст время
  заново.

**Почему так безопаснее:** время на пятницу после позднего выезда ничего не говорит о субботе, где
свои гости. Перенести старые часы на новый день молча — значит отправить горничную не в то время.

**Что сохраняет ручное время:**
- смена номера внутри листинга (день тот же);
- изменения часов выезда и заезда в брони;
- появление или отмена следующего гостя (срок и срочность при этом обновляются);
- повторное сохранение формы на тот же день.

**Бронь отменили, а потом вернули:**
- новая уборка берёт ручное время, если день тот же;
- если день другой — получает пометку «снято».

## 10. Что проверить руками

**В панели** (после выката, на любой будущей уборке из брони):
1. Открыть уборку из брони.
   - Время только для чтения, есть кнопка «Задать время вручную».
   - Нажать, поставить, например, 12:00–14:30, сохранить.
2. В списке у времени должно быть «вручную», в календаре — «· вручную».
3. Подождать 2–3 минуты (прогон вебхуков) или следующую ночь: время то же.
4. Открыть снова: «Время задано вручную…».
   - «Вернуть время по брони» — форма закрывается, время снова из брони, пометок нет.
5. Отказы:
   - время с концом раньше начала — «Сохранить» не активна, текст под полями;
   - на уборке в работе кнопок нет.
6. Смену даты бронью вручную не воспроизвести — её проверяет набор SQL (§7).
   Если случится в жизни: в форме рамка «Время было задано вручную на …», в списке
   «время сброшено: дата изменилась», «Понятно» убирает.

**На телефоне** (горничная, чья уборка на сегодня или завтра):
1. Менеджер задаёт ей время.
   - Приходит push про новые часы.
   - На карточке и экране уборки — новое время.
2. Кнопка «Начать» не открывается раньше нового `time_from`.
   - Если время сдвинули раньше — открывается раньше.
3. На уборку через 3+ дня push не придёт: время обновится при следующем открытии списка.
