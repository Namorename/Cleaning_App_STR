# STR Ops

Операционная система для компании краткосрочной аренды: автоматические задачи на
уборку из броней Hostaway, чек-листы с фотофиксацией, репорты о поломках,
статистика по объектам.

## Состав

| Путь | Что это | Статус |
|---|---|---|
| `apps/mobile` | Expo-приложение для клинеров и техников | F5 |
| `apps/web` | Next.js веб-панель менеджера | F10 |
| `packages/shared` | Общие типы, генерируемые типы БД | ✅ |
| `supabase/migrations` | Миграции схемы (источник правды) | F1 |
| `supabase/functions` | Edge Functions: синк Hostaway, вебхуки | F2 |
| `docs/ROADMAP.md` | Дорожная карта по фичам | ✅ |

## Требования

- Node.js >= 22 (см. `.nvmrc`)
- Docker Desktop — нужен для локального стека Supabase

## Установка

```bash
npm install
cp .env.example .env      # заполнить реальными ключами
```

### Веб-панель менеджера

```bash
cp apps/web/.env.example apps/web/.env.local   # NEXT_PUBLIC_SUPABASE_URL и NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
npm run web                                    # http://localhost:3000
npm run test:web && npm run typecheck:web
```

Вход только для ролей `manager` и `admin` (роль читается из `app_metadata`);
остальных панель отправляет на `/login`. Переводы у панели и приложения
общие: `packages/shared/src/i18n/locales`. Деплой — Vercel: Root Directory
`apps/web`, те же две переменные `NEXT_PUBLIC_*` в настройках проекта, и
включённый переключатель «Include source files outside of the Root Directory
in the Build Step» — без него Vercel не видит `packages/shared` и корневой
`package-lock.json`, установка идёт не из корня монорепо, и сборка падает на
`module-not-found`. Install Command и Build Command оставить по умолчанию:
Vercel сам находит корневой lock-файл с workspaces и ставит зависимости из
корня. `@str-ops/shared` объявлен в зависимостях `apps/web` и перечислен в
`transpilePackages` — пакет отдаётся сырым TypeScript.

## Работа с секретами

Единственный источник правды — корневой `.env`, он **только серверный**.

- `SUPABASE_SECRET_KEY` используется исключительно в Edge Functions и скриптах.
  В бандл Expo или Next.js он не попадает никогда.
- Мобильному приложению отдаются только `EXPO_PUBLIC_SUPABASE_URL` и
  `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` через `apps/mobile/.env` (появится в F5).
- Ключи Hostaway живут только на сервере — приложение к Hostaway не ходит.

## Планировщик

Задания `pg_cron` дёргают Edge Functions по HTTP через `pg_net`. Адрес и ключ
лежат в Vault, а не в миграции: они разные для локального стека и облака,
а ключ вообще нельзя коммитить. Задать один раз на каждое окружение:

```sql
-- локально (адрес Kong внутри docker-сети)
select vault.create_secret('http://supabase_kong_<ref>:8000', 'edge_function_base_url');
-- в облаке
select vault.create_secret('https://<ref>.supabase.co', 'edge_function_base_url');

select vault.create_secret('<service-role-key>', 'edge_function_key');
```

Без них задание падает с внятной ошибкой в `cron.job_run_details` — молча
ничего не делать оно не будет.

Расписание: разбор журнала каждые 2 минуты, синхронизация объектов в 03:00,
сверка броней в 03:15 (после объектов — бронь нового листинга иначе отложится),
закрытие просроченных уборок в 03:30 (после сверки — перенесённой брони нужно
сперва пересчитать дату, иначе метёлка закроет задачу, которая уже не опоздала).
Последнее задание — обычная SQL-функция `public.expire_stale_tasks()`, не Edge
Function, поэтому Vault ему не нужен. В 04:30 — ретеншн медиа: Edge Function
`purge-task-media` забирает у `task_media_to_purge()` файлы задач, закрытых
больше 90 дней назад (и снятые горничной до завершения шага), удаляет объекты
из бакета `task-media` и помечает строки `purged_at`; сами строки остаются.

## Письма сотрудникам

Учётки заводит Edge Function `manage-staff`. Отдельного почтового провайдера
в системе нет: пароль кладётся в `user_metadata` под ключом `initial_password`,
дальше `resetPasswordForEmail` просит auth-мейлер отправить шаблон **Recovery**,
и сразу после ответа значение затирается. В открытом виде пароль живёт ровно
одну HTTP-операцию.

Из этого следуют две настройки в облачном проекте, без которых письма не ходят.

**1. Свой SMTP.** Встроенная рассылка Supabase для работы не годится: она
доставляет только на адреса участников проекта (горничная письма не получит)
и ограничена парой писем в час. Authentication → Emails → SMTP Settings,
включить Custom SMTP и заполнить:

| Поле | Что вписать |
| --- | --- |
| Sender email | адрес на своём домене, например `no-reply@<домен>` |
| Sender name | `STR Ops` |
| Host | SMTP-хост провайдера (Resend, Postmark, Brevo, SES — любой) |
| Port | `587` для STARTTLS, `465` для SMTPS |
| Username / Password | выданные провайдером; пароль — в секреты проекта, не в репозиторий |

Домен отправителя должен быть подтверждён у провайдера с SPF и DKIM, иначе
письмо уедет в спам. Там же **Minimum interval between emails** — по умолчанию
он не даёт отправить второе письмо сразу, и второй заведённый подряд сотрудник
останется без письма.

Отдельно Authentication → Rate Limits → лимит на отправку писем: заводской
потолок рассчитан на встроенную рассылку и мал для рабочего дня.

**2. Шаблон Recovery.** Текст письма лежит в репозитории —
`supabase/templates/recovery.html`. Локальный стек берёт его сам (`config.toml`,
блок `[auth.email.template.recovery]`), **а облако не берёт**: там свой
экземпляр в Authentication → Emails → Templates → Reset Password. После правки
файла его надо вставить туда же, целиком.

Заводской шаблон присылает только ссылку — пароля в нём нет, и письмо выглядит
пустым. Обязательны две подстановки:

```
{{ .Email }}                  логин
{{ .Data.initial_password }}  пароль
```

Ключ `initial_password` — это константа `STAGED_PASSWORD` в
`supabase/functions/_shared/staff-password.ts`; тест
`manage-staff/template.test.ts` не даёт им разойтись. Go отрисовывает
отсутствующий ключ как пустоту, без ошибки, поэтому шаблон с чужим именем
переменной даёт ровно то, что видел владелец: письмо пришло, а пароля в нём
нет.

Шаблон один и на новую учётку, и на сброс пароля: два разных разошлись бы по
смыслу при первой же правке.

Если письмо не ушло, учётка и пароль всё равно созданы — панель скажет об этом
и покажет пароль на экране, чтобы менеджер продиктовал его сам.

## Галерея и происхождение снимка

Каждый файл в `task_media` несёт колонку `source`: `camera`, `gallery` или
`unknown`. Это **заявление приложения**, а не доказательство — сервер камеру не
видит, `device_taken_at` тоже приходит от телефона, а сфотографировать чужое
фото с экрана не запретит никакая схема. Ценность в другом: честная сборка
перестаёт молча выдавать подставленный файл за снятый, а тумблер
`hosts.gallery_allowed` перестал быть только клиентским — теперь `gallery`
отбивается на сервере, если компания галерею не открывала.

`unknown` — это «сборка ничего не сказала». Умолчание специально не `camera`:
молчание не должно превращаться в утверждение, тем более в лестное. В панели
такой снимок помечен словами «источник не указан», снимок из галереи — «из
галереи», снятый на месте не помечен никак.

**Порядок включения галереи, и он не переставляется.** В компании с
`gallery_allowed = true` сервер отказывает файлу без объявленного источника
(`serverErrors.mediaSourceMissing`) — иначе старая сборка осталась бы дырой,
через которую даже врать не надо. Значит:

1. собрать и раздать сборку, которая объявляет источник (см. раздел выше);
2. убедиться, что она стоит у всех, кто прикрепляет файлы;
3. и только потом включать тумблер в панели, Настройки → Компания.

Включить раньше — значит оставить не обновившуюся горничную с отказом в поле.

## Язык кода

Комментарии, сообщения об ошибках и логи — на английском. Русские комментарии
в старых файлах переводятся при следующей правке файла.

Текст, который читает сотрудник, на сервере не хранится: приложение говорит на
трёх языках, и язык сотрудника известен только ему. Функция БД поднимает
ошибку тремя частями — английский `message` (уходит в лог, на экран не
попадает), стабильный ключ i18n в `hint` (`serverErrors.<имя>`) и параметры
подстановки JSON-объектом в `detail`. Переводит приложение, через
`serverErrorText()`; ключ, которого сборка не знает, показывается общей фразой
с серверным текстом мелким шрифтом под ней. Переименование ключа — ломающее
изменение: сборка в поле ищет старый.

## Архитектурные решения

| # | Решение | Обоснование |
|---|---|---|
| Р1 | Синхронизация Hostaway на Supabase Edge Functions | Один стек, нечего отдельно хостить; ключи не покидают сервер |
| Р2 | Offline-first в мобильном приложении | Клинеры работают в квартирах без связи |
| Р3 | Двухслойные данные: `raw` JSONB → нормализованные таблицы | Изменения схемы Hostaway не ломают приложение |
| Р4 | Доступ через RLS | Клинер видит только свои задачи |
| Р5 | Медиа в Supabase Storage, не в R2 | На нашем объёме R2 дороже, и теряется интеграция с RLS |
| Р6 | Вебхуки Hostaway + ежесуточная сверка | Задачи создаются за секунды; сверка чинит потерянные вебхуки |
| Р7 | Процесс уборки: шаблон → снимок в `task_steps` при старте задачи | Правка шаблона не меняет идущие уборки; обязательные шаги блокируют завершение в триггере, а не в приложении; прогресс пишется только через идемпотентные RPC, чтобы офлайн-повтор был безопасен |
| Р9 | Названия от менеджера — пара колонок `x` / `x_i18n` с фолбэком на язык компании | Чек-лист пишет менеджер уже после сборки приложения, файлом переводов его не покрыть; хранить одну строку значит показать чешской горничной русский текст. Снимок задачи несёт все языки сразу, поэтому один и тот же отчёт читается и горничной, и менеджером |
| Р8 | Чек-лист на объект, снимок в `config` шага `checklist` | Две квартиры одного дома убираются по-разному, а тип объекта этого не видит; копирование из другого объекта закрывает цену «заполнить 78 раз». Пункты и их id уходят в снимок задачи, поэтому переписанный чек-лист не сдвигает то, что горничная уже отметила |
| Р10 | Медиа: строка `task_media` раньше файла, бакет приватный, клиент только загружает | Политика бакета пускает файл ровно на путь, который ждёт строка горничной; подтверждение проверяет, что объект есть. Три идемпотентных вызова переигрываются после потери сети без дублей. Удаляет файлы только ретеншн (Edge Function), клиент помечает строку — фото это доказательство, пока задача открыта. Владелец строки — шаг задачи или проблема (`problem_id`), конвейер один |
| Р11 | Проблема — репорт, устранение — задача типа `maintenance` | Отдельная сущность для «кто, что, где, насколько срочно», но техник идёт по той же машине шагов, что и горничная: шаблон scope `problem`, снимок при старте, фото, гейт завершения. Статус проблемы следует за задачей триггером, поэтому исполнитель, дата и время хранятся один раз — на задаче |
| Р12 | Заявка на расходники — личная сущность, не проблема | Другой процесс и другой исполнитель (§Д1.2): видна автору и менеджерам, пишется только через RPC, позиции заменяются целиком, пока менеджер не взял её в работу. Склад, поставщики и цены — вне объёма намеренно |

## Правила выката

Миграции, меняющие правила завершения задачи (F16 и дальше), выкатываются
**вместе со сборкой приложения**: `npm run db:push` и сборка или OTA-обновление
в один день. Старая сборка не знает шагов процесса и не сможет завершить
задачу, как только у неё появится обязательный шаг — сервер откажет, а
показать почему приложение не сумеет. Пока пользователи тестовые, риск
нулевой; с реальными горничными правило становится обязательным.

## Сборка приложения горничной

Expo Go этот проект не поднимает — нужна своя сборка. Профили лежат в
`apps/mobile/eas.json`, идентификатор приложения на обеих платформах —
`cz.strops.cleaner`.

| Профиль | Что даёт | Кому |
| --- | --- | --- |
| `development` | dev-client для отладки на устройстве | разработчику |
| `preview` | APK по ссылке или QR, без сторов | горничным на Android |
| `production` | `aab` для Google Play и `ipa` для TestFlight | релиз |

Первый раз, по порядку:

```bash
npx eas-cli@latest login                                  # интерактивно, под аккаунтом владельца
npx eas-cli@latest init --force                           # заводит проект в EAS, пишет projectId
npx eas-cli@latest update:configure                       # прописывает адрес обновлений
npx eas-cli@latest build --profile preview --platform android
```

**Переменные окружения в `eas.json` не хранятся.** Репозиторий публичный, а
`EXPO_PUBLIC_SUPABASE_URL` и `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` хоть и
попадают в бандл, в git не кладутся — заводятся переменными EAS на каждый
профиль:

```bash
npx eas-cli@latest env:set --scope project --name EXPO_PUBLIC_SUPABASE_URL --value "<url>" --environment preview --environment production --visibility plaintext
npx eas-cli@latest env:set --scope project --name EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY --value "<key>" --environment preview --environment production --visibility plaintext
```

Серверные ключи (`SUPABASE_SECRET_KEY`, Hostaway) в EAS не заводятся никогда —
приложение их не видит и видеть не должно.

### Обновления по воздуху

`expo-updates` подключён, `runtimeVersion` равна версии приложения
(`policy: appVersion`, сейчас `1.0.0`). Это значит: правка, которая трогает
только JavaScript, доезжает до установленных приложений одной командой, без
новой сборки и без стора.

```bash
npx eas-cli@latest update --branch preview     --message "что изменилось"
npx eas-cli@latest update --branch production  --message "что изменилось"
```

Ветка обновлений должна совпадать с каналом сборки (`channel` в `eas.json`).

**Нативное изменение по воздуху не доедет**, и версия среды об этом сама не
догадается — её выбираем мы. Правило: тронули нативную часть — подняли
`version` в `app.json` и собрали заново. Нативная часть — это новая
зависимость с нативным кодом, обновление SDK, правка `plugins`,
`permissions`, идентификаторов приложения или иконок. Не поднять версию —
значит предложить установленному приложению обновление, к которому его
нативная часть не готова. Проверить заранее: `npx expo-doctor` и
`npx expo install --check`.

Отпечаток нативной части (`policy: fingerprint`) здесь не работает. EAS
считает его на сервере после `prebuild`, когда каталог `android` уже
сгенерирован, а eas-cli — на чистом дереве до него: в серверном отпечатке
появляется источник `bareNativeDir`, а файлы плагинов конфига исчезают.
Отпечатки расходятся всегда, и сборка падает на фазе
`CONFIGURE_EXPO_UPDATES`. Открытый дефект EAS —
https://github.com/expo/eas-cli/issues/4137.
